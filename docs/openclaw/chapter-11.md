# 11 记忆系统RAG原理完整讲义：从每天的记录到 MEMORY.md，再到跨会话检索

> 本讲沿用第 08、09 讲的顺序：
>
> **第一部分：只用一个连续几天的午饭助手例子，讲清记忆怎样建立、怎样保存、怎样找回和使用，不讲具体代码。**  
> **第二部分：把刚才走过的流程抽象成算法。**  
> **第三部分：最后对照本地源码，逐步解释实现。**
>
> 贯穿全讲的问题是：
>
> **用户昨天说过的话，怎样变成磁盘上的记忆，又怎样成为今天模型回答问题的依据？**

本讲以本地 `OpenClaw-2026.4.22` 的 `memory-core` 插件和内置文件记忆后端为准。第 08、09 讲解释 Pi 的上下文压缩和会话管理；本讲解释 OpenClaw 在此基础上组织的跨会话记忆。

例子中的用户、日期和文件内容均为教学数据。搜索结果、向量和分数用于说明过程，不是一次实际运行的测量结果。

---

## 第一部分：先把一个完整例子讲清楚

## 1. 先看助手第一天刚建立时，究竟有什么

假设我们建立一个午饭助手，给它一个专用的工作目录。

工作目录可以理解为：这个助手长期使用的资料夹。新建聊天不会自动把这个资料夹清空。

刚完成基础设置时，与本例有关的文件如下：

```text
午饭助手的工作目录/
├── AGENTS.md       助手做事时遵守的规则
├── SOUL.md         助手的回答风格
├── USER.md         用户的基本资料
└── TOOLS.md        工具和环境说明
```

这里只列与课堂有关的文件，真实工作目录还可能有其他基础文件。

此时还没有午饭偏好，也没有每天的记忆文件，甚至可以还没有 `memory/` 目录和 `MEMORY.md`。

**建好助手的工作目录，与已经积累了用户记忆，是两件事。**

程序可以先准备基础规则文件；具体的用户记忆，要等用户提供事实、助手选择保存，并且真正写入文件后才形成。

### 1.1 规则先告诉助手：什么值得记，记到哪里

为便于观察，本例在 `AGENTS.md` 中约定：

> 用户明确说“以后记住”的偏好，要保存到当天的每日记忆。  
> 同一天已经有记录时，保留旧内容，追加新记录。  
> 整理长期记忆时，提取以后还适用的事实，写入 `MEMORY.md`。  
> 回答与过去有关的问题前，先查记忆；需要核对时再读原文。  
> 区分“平时如此”和“今天例外”，不要把一次性的要求写成永久偏好。  
> 文件写入成功后，才能告诉用户已经保存。

这些规则可以由工作目录模板提供，也可以按应用需求补充。本例把规则写明，是为了让后面的每一步都有明确依据。

**规则文件说明“如何管理记忆”；记忆文件保存“具体记住了什么”。**

### 1.2 先约定两个名字

后面会反复出现：

| 名字 | 本例的用途 |
|---|---|
| `memory/2026-10-26.md` | 记录 10 月 26 日值得保留的事实和当日事项 |
| `MEMORY.md` | 整理过的长期事实，供以后作为默认背景使用 |

用户口中的 `memory.md`，本讲统一写成惯用名称 `MEMORY.md`。本地实现也兼容小写名称；它不是要求再维护一份独立的长期记忆。

注意，所谓“每日记忆”是一类文件：有需要保存的内容，就按当天日期创建或追加。它不表示每天零点必定生成一个空文件。

## 2. 第一天，用户明确要求记住午饭偏好

假设今天是 **2026 年 10 月 26 日，星期一**。

用户第一次对午饭助手说：

> 以后帮我选午饭，记住我不吃辣，工作日通常控制在 20 元以内。  
> 今天先看看蛋炒饭，只给方案，不要下单。请把长期偏好保存下来。

先不要急着想工具或数据库。我们先判断这句话到底包含什么。

| 用户说的内容 | 应怎样理解 |
|---|---|
| 我不吃辣 | 用户明确要求以后使用的口味偏好 |
| 工作日通常 20 元以内 | 工作日午饭的默认预算，保留“通常”这个条件 |
| 今天先看看蛋炒饭 | 今天的任务安排 |
| 只给方案，不要下单 | 本次任务的执行边界 |

用户要求长期记住的是前两项。

后两项可以作为当天事项记录，但不能因此推断“用户每天都只吃蛋炒饭”或“用户永远不允许下单”。

**形成记忆的第一步，是判断事实的含义和适用范围。**

不是看到一段聊天，就把每句话都变成长期规则。

## 3. 第一天的每日文件，是怎么从没有到有的

### 3.1 模型收到的“生成记忆的 prompt”大概长什么样

这里的 prompt 不只是用户最后说的那一句话，还包括当前请求中提供给模型的记忆规则、日期和工具说明。

把与这次保存有关的部分单独展开，大致如下。**这是结合本例规则写出的中文教学示意，不是源码中某个完整字符串的原文，也不代表全部系统提示。**

```text
【当前日期】
2026-10-26

【工作目录中的记忆规则】
用户明确要求记住的内容，要通过文件工具保存。
当天的记录使用 memory/2026-10-26.md；目录或文件不存在时创建。
文件已经存在时，保留旧记录，追加新内容。
区分长期偏好和当日安排，保留“通常”“今天”等适用条件。
文件写入成功后，再确认已经保存。

【当前用户请求】
以后帮我选午饭，记住我不吃辣，工作日通常控制在 20 元以内。
今天先看看蛋炒饭，只给方案，不要下单。请把长期偏好保存下来。

【相关工具能力】
可以读取已有文件，也可以创建或修改工作目录中的文件。
```

模型根据这些输入，提取出“不吃辣”和“工作日通常 20 元以内”，然后发出文件写入动作。

**日常保存可以在普通对话的执行过程中完成，不一定另外启动一次“只生成记忆”的模型调用。** 也不是模型只输出一段 Markdown，文件就会自行出现；还要执行文件工具。

实际项目中，记忆规则通常有一部分来自工作目录的 `AGENTS.md` 等资料。本例对日期、追加方式和条件保留作了明确约定；对应的实际模板规则放在后面的第 30.4 节对照。

### 3.2 从这些输入，到实际写出的文件

助手根据刚才的规则，决定保存偏好。

此时当天的文件还不存在，所以先建立 `memory/` 目录，再创建：

```text
memory/2026-10-26.md
```

第一次写入后的完整内容如下：

```markdown
# 2026-10-26

## 午饭偏好
- 用户不吃辣。
- 工作日午饭通常控制在 20 元以内。
- 来源：用户明确要求以后记住。
```

这里有三个不同的参与者：

| 参与者 | 负责什么 |
|---|---|
| 用户 | 提供事实，明确提出保存要求 |
| 模型 | 从当前对话中提取事实，决定记忆文本和保存位置 |
| 文件工具及运行程序 | 创建目录，把文本实际写进磁盘文件 |

模型可以生成“要保存什么”，但只有文本真正落盘，才有了跨会话保留的材料。

因此，不能只看助手有没有回答“好的，我记住了”。还要看文件写入是否成功。

**这一步保存的是可阅读的文字，没有修改模型参数，也没有训练一个新模型。**

## 4. 同一天又有事情要记，是再建一个文件吗

假设当天助手继续完成了午饭方案，决定把当日安排也记下来。

它仍然使用 `memory/2026-10-26.md`，保留已有的偏好，追加当天事项。

追加后的完整文件变成：

```markdown
# 2026-10-26

## 午饭偏好
- 用户不吃辣。
- 工作日午饭通常控制在 20 元以内。
- 来源：用户明确要求以后记住。

## 当日安排
- 今天先看蛋炒饭，只给方案，不下单。
```

可以把这个变化理解为：

```text
上午：建立当天文件，记下偏好
  ↓
稍后：保留原记录，追加当天安排
  ↓
一天内有多次记录，仍然放在同一个日期文件里
```

如果把第二次记录直接覆盖到文件上，前面刚记下的偏好就会丢失。

所以“写记忆”不只是选一个文件名，还要区分：首次创建，还是在已有内容后追加。

## 5. 第二天的记忆怎样形成

到了 **2026 年 10 月 27 日，星期二**，用户说：

> 今天接待同事，午饭预算可以到 40 元，还是不要辣。  
> 这只是今天的例外，平时仍然按 20 元以内。只给方案，不下单。把这次安排也记一下。

这次保存的是一个有日期和条件的事件。

因为日期已经变化，助手创建第二份每日文件：

```text
memory/2026-10-27.md
```

当天稍后还讨论了课程安排。保存完成后，这份每日文件的完整内容为：

```markdown
# 2026-10-27

## 接待午饭
- 用户今天接待同事，午饭预算临时放宽到 40 元。
- 用户明确说明：这只是今天的例外，平时仍按 20 元以内。
- 口味仍然不辣；本次只给方案，不下单。

## 课程安排
- 用户今天还讨论了开源软件课程的讲义安排。
```

现在磁盘上有了：

```text
memory/
├── 2026-10-26.md    第一天的偏好和当日安排
└── 2026-10-27.md    第二天的接待例外和课程安排
```

昨天的文件仍然保留，不需要为了今天的 40 元，把昨天的 20 元删除。

因为这两条记录并不矛盾：

```text
平时：工作日午饭通常 20 元以内
10 月 27 日接待同事：这一次可以到 40 元
```

**记忆要保存条件，而不只是保存一个孤立的数字。**

## 6. 已经有每日文件，为什么还要一个 MEMORY.md

假设几个月过去，每天都记录一些事情。

助手会积累很多每日文件，里面既有偏好，也有临时安排、讨论过程和已经结束的任务。

以后每次想知道“这个用户平时怎么吃午饭”，都重新整理几个月的日记，会很费事。

于是我们再维护一份长期记忆：

```text
MEMORY.md
```

它回答的是：

> 从这些经历中，哪些事实以后仍然值得作为默认背景使用？

两类文件的区别可以直接对照本例：

| 问题 | 每日文件 | MEMORY.md |
|---|---|---|
| 用户平时不吃辣 | 记录用户何时提出、何时再次确认 | 整理为长期口味偏好 |
| 工作日通常 20 元以内 | 保留原始说明和当天背景 | 整理为默认预算 |
| 10 月 27 日接待同事可到 40 元 | 保留这次事件及“仅当天”的条件 | 不把 40 元改成长期默认预算 |
| 10 月 26 日先看蛋炒饭 | 保留当天安排 | 不提升为长期偏好 |

**每日文件保留来龙去脉，长期文件保留经过筛选的稳定事实。**

## 7. MEMORY.md 究竟是谁、在什么时候写出来的

在本例中，10 月 27 日晚上，用户明确说：

> 把这两天确认过的长期午饭偏好整理到长期记忆里。今天接待同事的 40 元只是例外，不要变成默认预算。

这就给出了一次具体的整理任务。

### 7.1 整理 MEMORY.md 时，prompt 又大概是什么样

把本例的整理规则、用户要求，以及读取文件后得到的材料放在一起，可以这样理解模型的输入：

```text
【本次整理规则，教学示意】
整理长期午饭偏好，保存到 MEMORY.md。
先读取已有的 MEMORY.md 和相关每日记录。
只提取以后仍适用的事实，合并重复表达，保留来源。
临时安排不要提升为默认偏好；已有的其他长期事实要保留。
整理完成后通过文件工具保存。

【当前用户请求】
把这两天确认过的长期午饭偏好整理到长期记忆里。
今天接待同事的 40 元只是例外，不要变成默认预算。

【读取文件后获得的相关材料】
2026-10-26：用户不吃辣，工作日午饭通常 20 元以内。
2026-10-27：接待同事临时放宽到 40 元，仅限当天；平时仍按 20 元。
```

这里最后一部分要在文件读取结果返回后，才成为模型可见的材料。并不是用户一说“整理”，程序就一定把所有每日文件全文自动塞进输入。

**这也是中文教学示意。本例没有假设源码里存在一段同名的固定“午饭长期记忆生成 prompt”。** 实际的引导来自工作目录规则和本次用户请求，材料来自读取结果。

### 7.2 模型怎样根据提示形成长期文件

助手依次做四件事：

1. 读取两天的每日记录，并确认长期文件是否已经存在。
2. 判断哪些内容以后仍然适用。
3. 去掉重复表达，保留条件和来源。
4. 通过文件工具创建或更新 `MEMORY.md`。

假设长期文件此前不存在，首次形成的完整内容如下：

```markdown
# 长期记忆

## 午饭默认偏好
- 用户不吃辣。
- 工作日午饭通常控制在 20 元以内。
- 来源：2026-10-26 明确提出，2026-10-27 再次确认。
```

注意，源头是两天的记录，但产物不是把两份文件直接拼起来。

```text
10 月 26 日：不辣、通常 20 元、今天先看蛋炒饭
10 月 27 日：不辣、平时仍 20 元、今天接待可 40 元
  ↓ 读取、判断适用范围、去重、整理
MEMORY.md：不辣、工作日通常 20 元以内
```

如果 `MEMORY.md` 已有其他长期事实，更新时要保留它们，修改相关条目，不能用午饭偏好覆盖整份长期记忆。

整理完成后，两份每日文件仍然保留。以后追问“40 元是哪天、因为什么”，仍然要回到每日记录找依据。

### 7.3 这不是每天晚上必然发生的自动合并

本例采用用户明确发起的整理任务，让长期文件的来源和写入时机都能看清楚。

实际应用也可以安排其他整理任务；本地版本还有可选的后台记忆整理能力。但它们需要各自的触发规则，不能仅凭存在每日文件，就断言系统每天自动生成或更新 `MEMORY.md`。

**文件名不会自己完成整理。一定要有某个任务读取材料、形成文本，再执行写入。**

## 8. 到第二天结束，记忆到底长什么样

现在工作目录变成：

```text
午饭助手的工作目录/
├── AGENTS.md
├── SOUL.md
├── USER.md
├── TOOLS.md
├── MEMORY.md
└── memory/
    ├── 2026-10-26.md
    └── 2026-10-27.md
```

这三份记忆文件是怎样形成的，现在已经可以逐一回答：

| 文件 | 触发原因 | 谁决定内容 | 谁实际写入 |
|---|---|---|---|
| 10 月 26 日每日文件 | 用户要求保存偏好，随后记录当天安排 | 模型根据对话和记忆规则提取 | 文件工具 |
| 10 月 27 日每日文件 | 用户要求记录接待午饭，随后记录课程事项 | 模型保留事件、日期和例外条件 | 文件工具 |
| MEMORY.md | 用户要求整理两天的长期偏好 | 模型读取记录后筛选、去重和归纳 | 文件工具 |

此时我们只完成了“把记忆存下来”。

还没有回答后半个问题：

> 第三天开一个新聊天，助手怎样找到这些内容？

## 9. 写完文件，为什么还要建立索引

只有三份短文件时，逐份阅读当然可以。

但假设后来有了三百份每日记录，用户今天只问午饭，程序没有必要把所有课程安排、项目讨论和历史午饭全部塞进模型。

所以系统会为允许检索的记忆文件建立一份便于查询的目录。

这份目录就是**索引**。

```text
Markdown 原文件
  ↓ 读取和分段
若干可以搜索的文本片段
  ↓
保存片段文字、文件路径和原文行号
  ↓
建立关键词索引；有可用的向量服务时，再建立语义检索所需的向量
```

**原文件负责保存可读的事实；索引负责帮助程序找到相关片段。**

索引不是另一份由助手编写的长期总结，也不会因为建了索引，就自动把每日记录整理进 `MEMORY.md`。

## 10. 索引到底是什么：先看文件，再看里面的记录

先回答一个最具体的问题：

> 索引是一个文件夹吗？切出来的每个片段，又是一个新文件吗？

**本讲使用的内置后端，把记忆的检索数据主要保存在一个 SQLite 数据库文件里，文件名以 `.sqlite` 结尾。切出来的片段是数据库里的记录，不是另外创建的一批 Markdown 文件。**

先把 SQLite 理解成一种“把多张数据表保存在文件里”的数据库即可。程序可以向这些表里添加记录、更新记录和执行查询，不需要我们手工编辑这个文件。

### 10.1 先在磁盘上分清：笔记放哪里，检索数据放哪里

前面例子的原始记忆仍然是这三份可阅读的笔记：

```text
午饭助手的工作目录/
├── MEMORY.md
└── memory/
    ├── 2026-10-26.md
    └── 2026-10-27.md
```

内置后端还会维护一份数据库。按默认状态目录和默认存储规则，它的位置是：

```text
~/.openclaw/memory/<agentId>.sqlite
```

这里的 `~` 表示用户主目录，`<agentId>` 表示助手的标识。例如标识为 `main`，文件就是 `main.sqlite`。状态目录和数据库路径都可以配置，以上不是当前电脑的实测路径。

为了看清两者的位置，假设使用默认工作目录，助手标识为 `main`，可以画成：

```text
用户主目录/
└── .openclaw/
    ├── workspace/                 助手的工作目录
    │   ├── MEMORY.md              人和助手可阅读的长期笔记
    │   └── memory/                每日笔记文件夹
    │       ├── 2026-10-26.md
    │       └── 2026-10-27.md
    │
    └── memory/                    存放检索数据库的目录
        └── main.sqlite            程序维护的数据库文件
```

注意这里有两个不同位置的 `memory/`：工作目录里的那个装每日笔记，状态目录里的那个装数据库。不能只看最后一级目录名，要看完整路径。

### 10.2 数据库里先保存“这段话来自哪里”

程序读取原始笔记，把文字切成片段，然后将每个片段保存成数据库中的一条记录。

假设 `memory/2026-10-27.md` 很短，全文形成一个片段。它对应的记录可以简化成下面这样：

| 这一条记录保存的内容 | 本例的值 |
|---|---|
| 片段编号 | C3，课堂用的示意编号 |
| 来源文件 | memory/2026-10-27.md |
| 开始行 | 1 |
| 结束行 | 9 |
| 片段原文 | 从“# 2026-10-27”到当天课程安排的那段完整文字 |
| 片段向量 | 有向量服务时，由这段文字生成的一串数字 |

这里保存的“片段原文”是原文件中的文字，不是模型另外编写的摘要。

因此，磁盘上并不会因为这个片段再多出一个 `C3.md`。**C3 只是数据库里某条记录的课堂编号。**

如果一份长笔记切成十个片段，就对应多条片段记录；这些记录可以指向同一份原文件的不同位置。

### 10.3 打开 SQLite 数据库，具体会看到哪些表、哪些行

如果用数据库查看工具打开 `main.sqlite`，可以把里面的主要结构理解为：

```text
main.sqlite                      一个数据库文件
├── files                        记录哪些原文件已被索引
├── chunks                       保存切出来的片段及其来源、向量等
├── chunks_fts                   全文检索表，启用且可用时存在
├── embedding_cache              向量计算缓存，启用时存在
├── meta                         索引运行需要的元信息
└── chunks_vec                   向量加速检索表，相应扩展可用并初始化后存在
```

**这里画的是一个文件内部的表，不是文件夹下面又有六个文件。** 数据库查看工具会把表中的记录显示成一行一行的格子。

下面按本地实现的字段名，展示几行教学数据。片段 ID、Hash 和模型名称使用简短代号，时间、大小和向量数值也是假设值，并非实际数据库导出。

#### 第一张表：files，一行对应一个原文件

| path | source | hash | mtime | size |
|---|---|---|---:|---:|
| MEMORY.md | memory | H-M | 1793102400000 | 240 |
| memory/2026-10-26.md | memory | H-26 | 1793016000000 | 330 |
| memory/2026-10-27.md | memory | H-27 | 1793102400000 | 420 |

把其中第三行翻译成人话，就是：

> 程序已经处理过 `memory/2026-10-27.md`；当时它的内容标记是 H-27，修改时间是这个毫秒时间戳，文件大小是 420 字节。

各列的含义：

| 列名 | 记录什么 |
|---|---|
| path | 原文件相对于工作目录的路径 |
| source | 来源类别；本例都是记忆文件，所以值为 `memory` |
| hash | 根据文件内容计算的标记，用于比较内容有没有变化；真实值比 H-27 长 |
| mtime | 文件修改时间，以毫秒时间戳保存 |
| size | 文件大小，单位是字节 |

**这张表主要记录文件状态，正文片段放在下一张表。** 以后再同步时，程序可以对比内容 Hash 等信息，判断文件是否需要重新处理。

#### 第二张表：chunks，一行对应一个片段

先看它最容易理解的几列：

| id | path | source | start_line | end_line | text（仅展示部分原文） |
|---|---|---|---:|---:|---|
| C1 | MEMORY.md | memory | 1 | 6 | - 用户不吃辣。<br>- 工作日午饭通常控制在 20 元以内。 |
| C2 | memory/2026-10-26.md | memory | 1 | 9 | - 用户不吃辣。<br>- 工作日午饭通常控制在 20 元以内。 |
| C3 | memory/2026-10-27.md | memory | 1 | 9 | - 用户今天接待同事，午饭预算临时放宽到 40 元。<br>- 用户明确说明：这只是今天的例外，平时仍按 20 元以内。 |

为避免表格过宽，`text` 列只展示了片段中的部分原文。**实际保存的是对应范围的完整片段，包括标题、空行和其他条目，不是上表显示的两句摘录。**

读第三行就能知道：

> C3 这个片段，来自 `memory/2026-10-27.md` 的第 1～9 行，里面包含接待同事临时放宽预算的记录。

`chunks` 还保存下面这些列。为了排版，把同一张表的其余列单独画出来，仍用 `id` 对齐；这不是另外一张表：

| id（用于对齐） | hash | model | embedding | updated_at |
|---|---|---|---|---:|
| C1 | HC-1 | demo-embedding | [0.12, -0.31, 0.08] | 1793102460000 |
| C2 | HC-2 | demo-embedding | [0.11, -0.29, 0.09] | 1793102460000 |
| C3 | HC-3 | demo-embedding | [0.45, -0.10, 0.27] | 1793102460000 |

这里：

- `hash` 标记的是这个片段的内容，与 `files.hash` 标记整份文件不同。
- `model` 表示生成向量时使用的模型身份；`demo-embedding` 是教学代号。
- `embedding` 保存片段向量，在这张普通表中以 JSON 数组文本保存。这里用虚构的三维数组展示形状，真实维度由实际模型决定。
- `updated_at` 表示这条片段记录写入或更新的时间，以毫秒时间戳保存。

如果没有向量 Provider、只建关键词索引，本地这条路径会将 `model` 写为 `fts-only`，`embedding` 写为 `[]`；片段文字和来源仍然可以保存。

再强调一次：**`files` 的一行表示一份文件，`chunks` 的一行表示一段文字。** 本例三个文件都很短，刚好各形成一个片段；如果某份文件被切成十段，就会有十条片段记录指向同一个 `path`。

#### 第三张表：chunks_fts，为关键词搜索准备

全文检索可用时，还会保存对应的全文检索记录。下面只列其中几列：

| id | path | start_line | end_line | text（仅展示部分原文） |
|---|---|---:|---:|---|
| C1 | MEMORY.md | 1 | 6 | - 用户不吃辣。 |
| C2 | memory/2026-10-26.md | 1 | 9 | - 工作日午饭通常控制在 20 元以内。 |
| C3 | memory/2026-10-27.md | 1 | 9 | - 用户今天接待同事，午饭预算临时放宽到 40 元。 |

真实表还包含 `source`、`model` 列；这里的 `text` 同样只是为了展示而截短，实际写入完整片段。

SQLite 的全文检索模块会据此维护专门的搜索结构。搜索“接待同事”时，程序可以从全文检索表取得相关候选，再用 C3 这样的片段 ID 和来源信息识别结果。

`chunks_fts` 不是“关键词一列、片段编号一列”的手工对照表。下一小节那种画法，只是为了说明关键词怎样帮助定位片段。

#### 把三张表连起来看一次

```text
files 第三行
  这份原文件：memory/2026-10-27.md
  ↓ 通过相同的 path 对应
chunks 的 C3 记录
  保存了该文件第 1～9 行的完整片段，以及向量等数据
  ↓ 同一片段也写入全文检索表
chunks_fts 的 C3 记录
  为这个片段提供关键词搜索能力
  ↓ 搜索命中后返回来源
memory_get 读取原文件需要的行
```

这个对应关系不表示一定定义了数据库外键，也不表示每次搜索都要按图中的顺序依次查询三张表；它是在说明同一份资料在不同表里分别保存什么。

本节先看表和数据的样子，不需要读建表或查询代码。真实字段的定义，以及记录怎样写入，放在后面的第 31 节对照。

### 10.4 光有片段记录，还要有帮助搜索的结构

假设数据库里有一万条片段记录。我们想找“接待同事的午饭预算”，程序还需要一种高效定位相关记录的方法。

可以先把关键词索引想成书后的关键词目录。下面只是帮助理解的示意，不是实际数据库格式：

| 可查的词 | 可能相关的片段编号 |
|---|---|
| 午饭 | C1、C2、C3 |
| 接待同事 | C3 |
| 课程 | C3 |

查询时，程序利用这些搜索结构取得候选，再结合匹配和排序规则筛选结果。真实的分词和匹配方式由后面的检索实现决定。

如果启用了语义搜索，数据库中还会保存片段向量等数据，让程序能比较“查询的意思”和“片段的意思”是否接近。数值怎样产生、怎样比较，后面再讲。

所以，前文口中的“记忆索引”，是对**这套可检索数据及搜索结构**的统称。它主要持久保存在数据库文件中；不只是一个文件夹，也不只是列出几个文件名。

### 10.5 “建立索引”就是程序生成和更新这些数据

把刚才的过程连起来：

```text
已有原文件：memory/2026-10-27.md
  ↓ 程序读取文字
切成一个或多个片段
  ↓
向 main.sqlite 写入片段原文、来源路径和行号等记录
  ↓
建立或更新关键词搜索结构
有向量服务时，再保存向量并准备相应检索数据
```

这整个处理过程，就叫建立或更新索引。

以后执行 `memory_search` 时，程序主要查询这些已经准备好的检索数据，返回相关片段及其来源；需要核对原文时，`memory_get` 再按文件路径和行范围读取原笔记。

**原笔记是内容来源，数据库是程序为搜索准备的派生数据。** 两者更新是前后两步，所以才会有下一节要讲的“文件已经改了，搜索结果却暂时还是旧的”。

### 10.6 回到具体文件：程序怎样切块，切完保存什么

**这里的“切块”由程序完成。切完得到的仍是原文片段，并没有再让对话大模型把每块压缩成摘要。**

先给刚才的两份每日文件标上行号。行号只是课堂标注，不写进文件正文；空行也占一行。

10 月 26 日文件：

| 行号 | 内容 |
|---:|---|
| 1 | # 2026-10-26 |
| 2 | 空行 |
| 3 | ## 午饭偏好 |
| 4 | 用户不吃辣。 |
| 5 | 工作日午饭通常控制在 20 元以内。 |
| 6 | 来源：用户明确要求以后记住。 |
| 7 | 空行 |
| 8 | ## 当日安排 |
| 9 | 今天先看蛋炒饭，只给方案，不下单。 |

10 月 27 日文件：

| 行号 | 内容 |
|---:|---|
| 1 | # 2026-10-27 |
| 2 | 空行 |
| 3 | ## 接待午饭 |
| 4 | 用户今天接待同事，午饭预算临时放宽到 40 元。 |
| 5 | 用户明确说明：这只是今天的例外，平时仍按 20 元以内。 |
| 6 | 口味仍然不辣；本次只给方案，不下单。 |
| 7 | 空行 |
| 8 | ## 课程安排 |
| 9 | 用户今天还讨论了开源软件课程的讲义安排。 |

#### 先看默认预算：短文件可以整份成为一个片段

本地默认的切块目标是每块约 400 个估算 token，相邻块的重叠目标约 80 个估算 token。这里用的是长度估算，不是对所有模型都精确的 token 数。

这几份文件都很短，放得进默认预算，所以前面的数据库例子按“每个文件各形成一个片段”展示：

| 教学编号 | 来源文件 | 原文范围 | 主要内容 |
|---|---|---|---|
| C1 | MEMORY.md | 第 1～6 行 | 整理过的默认偏好 |
| C2 | memory/2026-10-26.md | 第 1～9 行 | 首次提出偏好和当天安排 |
| C3 | memory/2026-10-27.md | 第 1～9 行 | 接待同事的例外和课程事项 |

真实片段边界取决于文件长度和分段配置。课堂编号 C1、C2、C3 只用于追踪来源；这里忽略文件末尾换行可能对应的空行。

以后搜索命中 C3，程序不仅知道“接待午饭可以到 40 元”，还知道它出自哪份文件、哪几行。

有了来源，助手才能进一步核对“这到底是长期预算，还是一次例外”。

#### 再把预算缩小，实际走一遍如何切成两块

为让这份短文件也出现切点，下面临时改用更小的**教学预算**：每块约 80 个估算 token，重叠约 20 个估算 token。前面的数据库示例仍按默认预算理解，不把这次演示的两块混进原来的 C3 记录。

程序的基本做法是：

1. 按换行读出各行，保留原始行号。
2. 估算每行占用的长度，逐行往当前片段中加入。
3. 加下一行会超出预算时，先输出当前片段。
4. 从刚输出的片段末尾保留一些重叠原文，再继续加入后面的行。
5. 文件结束时，输出最后一个片段。

对本例这份中文文件，程序会给部分中文字符增加长度权重，再统一使用“约 4 个加权字符对应 1 个估算 token”的额度。于是本次教学的片段额度为 320，重叠目标为 80。**这不表示 80 个中文字符等于 20 个真实 token。**

把第 1～9 行按源码的估算方式逐行累计，包含每行的换行额度，得到：

| 原文行号 | 内容提示 | 本行加权长度 | 从第 1 行开始累计 |
|---:|---|---:|---:|
| 1 | 日期标题 | 13 | 13 |
| 2 | 空行 | 1 | 14 |
| 3 | 接待午饭标题 | 20 | 34 |
| 4 | 接待同事，临时预算 40 元 | 84 | 118 |
| 5 | 只限当天，平时仍按 20 元 | 97 | 215 |
| 6 | 不辣，只给方案，不下单 | 69 | 284 |
| 7 | 空行 | 1 | 285 |
| 8 | 课程安排标题 | 20 | 305 |
| 9 | 当天讨论课程讲义安排 | 83 | 388 |

**第一块怎样形成？** 第 1～8 行累计 305，没有超过片段额度 320。如果再加入第 9 行，累计就到 388，超过额度。因此先输出第 1～8 行，暂时不加入第 9 行。

**重叠部分怎样选择？** 从第一块末尾往前保留：第 8 行占 20，第 7 行占 1，再加第 6 行占 69，累计 90，已达到重叠目标 80。因此整行保留第 6～8 行。实际重叠可以超过目标，因为这里尽量按整行保留。

**第二块怎样形成？** 带着保留的第 6～8 行，加入尚未处理的第 9 行，长度为 90 + 83 = 173。此时文件结束，输出第二块。

最终两块如下。编号仍然只是教学代号：

| 片段 | 保存的原文范围 | 与上一块重叠的范围 |
|---|---|---|
| C3-a | 第 1～8 行 | 无 |
| C3-b | 第 6～9 行 | 第 6～8 行 |

这也说明切点不一定落在“一个主题刚好结束”的位置：第一块甚至带上了第 8 行的课程标题。这个基础切块过程主要按长度和行处理，**没有让模型理解全文后决定主题边界**。

如果某一行本身过长，程序还会把长行继续分段，片段边界不一定只落在换行处。上面九行都不需要走长行分段，所以可以逐行手算。

#### 切完之后，数据库里保存的是哪段文字

以第二块 C3-b 为例，它的 `text` 就是第 6～9 行的原文拼接：

```text
- 口味仍然不辣；本次只给方案，不下单。

## 课程安排
- 用户今天还讨论了开源软件课程的讲义安排。
```

程序同时记录它来自 `memory/2026-10-27.md`，开始行是 6，结束行是 9。它不会把这四行另写成“用户讨论了午饭和课程”这样的摘要。

原文件仍然完整保留。切块只是为检索生成原文片段；重叠会让部分文字在不同片段中重复，所以这一步甚至可能增加数据库中保存的文本总量。

### 10.7 切块、生成向量和大模型压缩，是三个不同动作

切块以后，本例的内置文本索引主线是：

```text
记忆 Markdown 原文
  ↓ 程序按长度、行和重叠规则切块
原文片段 + 来源路径 + 行号
  ├─ 为片段建立关键词全文索引
  └─ 有向量服务时：将片段交给 Embedding 模型，得到数值向量
  ↓
保存可检索的数据，片段原文继续保留
```

Embedding 虽然也可能调用模型服务，但它返回的是一串数字，用来比较语义相似程度；它不会在这条路径中输出一段更短的中文摘要，也不会用向量替换片段原文。实际向量调用还可能因缓存命中而省略。

| 动作 | 谁完成 | 输入 | 产物 |
|---|---|---|---|
| 为记忆索引切块 | 普通程序 | Markdown 原文 | 分段后的原文、路径、行号等 |
| 生成 Embedding | Embedding 模型或可复用的缓存 | 片段原文 | 数值向量，用于语义检索 |
| 第 08 讲的 Compaction 摘要 | 对话大模型 | 待压缩的会话材料 | 更短的文字摘要 |
| 前面整理 MEMORY.md 的任务 | 模型结合文件工具 | 每日记录等资料 | 筛选、归纳后的长期文字事实 |

因此，前面确实有“模型从聊天中整理记忆”的过程；那发生在形成每日文件或整理长期文件时。**到了这里给已有记忆文件建索引，并不是再把每个切块交给对话大模型压缩一次。**

后续搜索时，程序找回相关片段，模型再结合原文和当前问题回答。重叠只能减少条件被切散的影响，不能保证每个条件都完整落在同一块里，必要时仍要读取上下文原文。

## 11. 索引怎样建立，建好后大概是什么样

第 10 节看了数据库里的表。现在把这些表“从没有内容到能够搜索”的过程走一遍。

**建立索引，就是程序读取记忆文件，把原文片段、来源信息和搜索所需的数据写入 SQLite；不是让模型再写一份记忆摘要。**

### 11.1 第一次建立：从三份笔记到可检索的数据库

仍然使用前面的三份文件，并按默认预算各形成一个片段：

```text
MEMORY.md
memory/2026-10-26.md
memory/2026-10-27.md
```

假设内置记忆后端首次初始化，还没有建立过索引，可以把后续同步理解成下面这些工作：

| 步骤 | 程序具体做什么 | 本例留下的东西 |
|---:|---|---|
| 1 | 打开或创建当前 Agent 的 SQLite 数据库，准备所需的表 | main.sqlite 中有 files、chunks 等表结构 |
| 2 | 扫描允许检索的记忆路径 | 找到上面三份笔记 |
| 3 | 获取文件内容和状态，计算内容 Hash，并与已有记录比较 | 第一次没有旧记录，三份都需要处理 |
| 4 | 按第 10.6 节的方法切块，保留原文和行号 | 得到 C1、C2、C3 三个片段 |
| 5 | 有可用的 Embedding Provider 时，计算或复用片段向量 | 为三个片段取得可用于语义比较的数字数组 |
| 6 | 写入片段、可用的向量及全文检索记录，更新文件状态 | 对应到 chunks、chunks_fts、files 等表 |

这些是整体工作的阅读顺序；处理某一份文件时，源码会先写它的片段等记录，再更新它的文件状态，不必等所有文件都处理完才统一写表。

全文检索模块会根据写入 `chunks_fts` 的文字维护内部搜索结构。向量加速可用时，程序还会准备 `chunks_vec` 中对应的向量记录。

**片段向量在建索引时准备；今天的问题所对应的查询向量，要等搜索时才生成。两者的输入不同。**

没有向量 Provider 时，也可以走已有的关键词索引路径：保存片段原文，建立可用的全文检索记录，向量字段保持为空。

### 11.2 直接看索引数据：Hash、片段记录和 Embedding 长什么样

下面直接展示数据库查看工具中可能看到的数据，不再只写“某文件的 Hash”或“某片段的向量”。

**Hash 和大小使用前面三份笔记内容实际计算；Embedding 使用明确标注的教学数值，没有调用真实 Embedding 服务。** 这里不是从用户已有的 `main.sqlite` 导出的记录。

#### files 表：Hash 就是这样一长串十六进制字符

本地实现对文本内容使用 SHA-256，输出的是 **64 个十六进制字符**，也就是下面这种由数字和 a～f 组成的字符串。

为使结果可复算，下面取前面最终版本的三份笔记，使用 UTF-8 编码、LF 换行，并且文件末尾不额外加换行。展示 `files` 中的三列：

| path | hash（完整值） | size（字节） |
|---|---|---:|
| MEMORY.md | 926843372b9a5a60f484f2aaed9fdd68c8a187f3f1fce161066911f98669d4cf | 171 |
| memory/2026-10-26.md | 4f97eb4eb2bf726a13557440f23930a14731cc35c62f1ef9240c031258673480 | 215 |
| memory/2026-10-27.md | 5a96b5c8193ecc6f02c968c32b4e0a36233fdeb8ff9f1cb9ab0765c1046e2420 | 312 |

这三行的 `source` 都是 `memory`；修改时间等字段的格式已在第 10.3 节展示。第 10 节的 H-M、H-26、H-27 只是简写，真实 Hash 的外观就是上面这样。

**Hash 是程序根据文字计算的内容标记，不是模型生成的摘要，也不是 Embedding。** 程序把新算出的 Hash 与 `files.hash` 比较，帮助判断内容是否变化。

空格、换行方式、末尾是否有换行都会影响输入内容，因此也会影响 Hash；拿不同换行版本计算，不能期待结果与上表相同。

#### Embedding 就是一串浮点数，三条记录可以长这样

继续使用第 10.3 节的三维教学值，把 `chunks` 的部分列横着看：

| 教学编号 | path | embedding（数值形状示意） |
|---|---|---|
| C1 | MEMORY.md | [0.12,-0.31,0.08] |
| C2 | memory/2026-10-26.md | [0.11,-0.29,0.09] |
| C3 | memory/2026-10-27.md | [0.45,-0.10,0.27] |

**数组中的每个数字是向量的一个分量，不直接表示“预算”“辣度”这样的业务字段。** 这里特意只用三维展示形状；真实向量由实际模型生成，维度由模型决定，可能有数百或数千个分量，不能从原文凭空填出。

在普通 `chunks` 表的 `embedding` 字段中，这个数组以 JSON 文本保存。向量扩展可用时，`chunks_vec` 还会保存对应的向量数据，供扩展查询；该扩展中的向量采用二进制表示，数据库查看器不一定直接显示成上面的数字数组。

**Hash 用来识别内容变化；Embedding 用来比较语义相似程度。两者都像一串数值，但用途和计算方式完全不同。**

#### chunks_fts 表：原文和来源也会有对应记录

假设全文检索已启用且可用，将 C3 这行的几个字段展开，可以看到：

| 字段 | 具体值 |
|---|---|
| id | 7ea5c298420be36e5bfd51913b4a15993d135bed78b0f99a142e53d3421f6c9f |
| path | memory/2026-10-27.md |
| source | memory |
| model | demo-embedding |
| start_line / end_line | 1 / 9 |
| text | 与上面 C3 的完整片段文字相同，这里不重复展开 |

全文检索模块根据这些文字建立内部搜索结构。**这张表里不是拿 Hash 或 Embedding 去做关键词匹配，而是利用片段文字进行全文检索。**

#### 为什么 chunks 和 chunks_fts 都保存原文

**`chunks` 保存完整片段记录；`chunks_fts` 为同一批片段提供专门的全文搜索能力。** `fts` 是 Full-Text Search，即全文检索。

| 表 | 保存什么 | 主要用途 |
|---|---|---|
| `chunks` | 片段 ID、原文、来源、行号、Hash、模型和 Embedding 等 | 保存完整片段记录，支持向量检索等操作 |
| `chunks_fts` | 同一片段的 ID、原文、来源、行号和模型等 | 通过 SQLite FTS5 进行关键词匹配和相关性排序 |
| `chunks_vec` | 片段 ID、向量 | 向量扩展可用并完成初始化时，提供向量查询 |

以 C3 为例，`chunks.text` 与 `chunks_fts.text` 都会保存“用户今天接待同事，午饭预算临时放宽到 40 元”等完整片段文字。但向 `chunks_fts` 写入文字时，**SQLite 的 FTS5 模块还会维护供全文检索使用的内部索引结构**，概念上可以理解为按词项定位相关记录。

**上面的表格展示的是记录字段，没有把背后的全文索引结构画出来。** 所以，不能因为两张表都能看到相同的 `text`，就认为它们的搜索能力和用途完全一样。具体怎样分词、能否匹配某段中文，还受 tokenizer 和查询表达影响。

本地建表定义中，`chunks_fts` 是通过 `USING fts5(...)` 创建的虚拟表。**`text` 用来建立全文索引；`id`、`path`、行号等列标为 `UNINDEXED`，作为结果标识、来源或过滤信息保存，不参与全文分词索引。** 这些字段的定义可对照 [memory-schema.ts](/source/?file=8f2c56c8464d2e77da.ts#L66)。

#### 关键词检索实际查哪张表

**关键词检索直接查 `chunks_fts`。** 下面是常规全文匹配路径的教学简化 SQL，省略模型和来源等过滤条件：

```sql
SELECT id, path, start_line, end_line, text,
       bm25(chunks_fts) AS rank
FROM chunks_fts
WHERE chunks_fts MATCH ?
ORDER BY rank ASC
LIMIT ?;
```

**这里的两个 `?` 都是参数占位符，执行 SQL 时由程序按出现顺序绑定具体值：**

- `MATCH ?`：第一个参数是处理后的搜索词或全文检索表达式，用来确定查什么。
- `LIMIT ?`：第二个参数是本次最多取多少条候选记录，用来限制结果数量。

例如，对上面这段简化 SQL，假设 `stmt` 是准备好的查询语句，程序这样传入两个参数：

```ts
stmt.all("memory", 10);
```

查询效果相当于：

```sql
WHERE chunks_fts MATCH 'memory'
ORDER BY rank ASC
LIMIT 10;
```

也就是搜索匹配 `memory` 的文本块，按相关性排序，最多取 10 条候选。`?` 本身不是要搜索的问号，也不需要手工拼接成 SQL 字符串；数据库会把传入的值绑定到对应位置。这里的 10 是检索阶段的候选数，后续融合、筛选后最终返回多少条，由后续流程决定。

例如第 15.1 节的简单查询“20”，会在全文检索结构中寻找匹配词项，再按文本相关性取得候选。

**关键词路径可以直接从 `chunks_fts` 命中记录中取出原文、路径和行号，不必再去 `chunks` 查一遍。** 这就是这张全文检索表除了 `text`，还保存片段 ID、路径和行号的意义。实际查询见 [manager-search.ts 的 searchKeyword](/source/?file=1fb006b402c03a7668.ts#L273)；特殊短中文路径等细节放到第 32.3 节展开。

#### 向量检索和混合检索又查哪些表

向量检索比较的是查询向量与片段向量，使用另一条查询路径：

| 运行条件或搜索方式 | 实际使用哪些表 | 怎样取得结果 |
|---|---|---|
| 有查询向量，向量扩展可用 | `chunks_vec` 与 `chunks` | 在向量表中查候选，并按片段 ID 关联 `chunks`，取得原文、路径和行号 |
| 有查询向量，向量扩展不可用 | `chunks` | 读取保存的 Embedding，由程序计算相似度并排序 |
| 混合检索，两路均可用 | 关键词路径使用 `chunks_fts`；向量路径使用上述相应表 | 两路分别找候选，再按片段 ID 合并与打分 |
| 没有 Embedding Provider，全文检索可用 | `chunks_fts` | 走关键词专用路径，不要求同时进行向量检索 |

**没有向量扩展，与没有 Embedding Provider 是两种情况：前者仍可能读取 `chunks.embedding` 做相似度计算；后者走可用的关键词检索路径。** 向量查询实现见 [manager-search.ts 的 searchVector](/source/?file=1fb006b402c03a7668.ts#L121)。

因此，**混合检索不是固定地“先查 `chunks`，再查 `chunks_fts`”，而是文字匹配与向量匹配分别取得候选，最后融合结果。** 同一片段在两路都命中时，可以用相同的片段 ID 识别并合并。

搜索命中后，`memory_get` 仍是按返回的路径和行号读取原始 Markdown 文件，供后续核对；这与查询数据库中的候选片段是两个环节。

所以“索引已经建好”在这个例子中的具体含义是：

> 三份文件已经被处理；它们的片段和来源位置已进入数据库；关键词搜索能利用全文检索数据，有可用向量时也能进行语义检索。

**这时模型还没有收到今天的搜索结果。建索引只是在为后续查询准备数据。**

### 11.3 文件变化后，怎样更新已有索引

假设助手向 10 月 27 日文件追加了一条新记录：

```text
文件工具把新内容写入 memory/2026-10-27.md
  ↓
文件监听发现变化，标记“需要同步”，并安排后续处理
  ↓
同步时重新读取文件，发现内容 Hash 与 files 中保存的不同
  ↓
重新处理这份变化的文件，生成当前的片段和必要的向量
  ↓
清理该文件失效的旧片段、全文检索及向量记录，写入新记录
  ↓
更新 files 中这份文件的 Hash、修改时间和大小等状态
```

未变化的其他文件，在不需要全量重建的同步中可以跳过；已删除的文件，其旧索引记录也需要清理。

**监听到文件变化，不等于索引已经更新完。标记变化、读取处理、写入数据库，是连续但分开的动作。**

同步还可以由会话启动、搜索或手动操作等触发，具体取决于配置和运行状态。

### 11.4 为什么文件刚写完，搜索可能还是旧结果

**文件写入与索引更新不是同一个操作。** 在新文字已经落盘、数据库尚未更新的时间段内，搜索可能暂时使用旧索引。

本地内置实现对**完全没有索引内容的首次搜索，会尝试先等待一次同步**；已有索引时，搜索触发的更新也可能在后台进行。

为了继续观察主要流程，**以下假设三份文件都已同步进索引，记忆工具也正常可用。**

## 12. 第三天，新 Session 从哪里开始

到了 **2026 年 10 月 28 日，星期三**，用户新建一个聊天。

这次仍然使用同一个助手、同一个工作目录。

要同时看两份状态：

```text
新 Session 的聊天消息：没有前两天的对话

工作目录中的记忆：MEMORY.md 和前两天的每日文件仍然存在
```

**新 Session 的活动消息可以是新的，同一工作目录中的记忆文件仍然保留。** 这就是跨会话记忆的起点。

第 09 讲的 Session 保存了原来那次聊天怎样进行；本讲的记忆文件则把值得复用的事实整理出来，让另一次聊天也有机会取得。

两者可以同时存在，但不是同一份东西。

用户今天的完整请求是：

> 另外，我上次接待同事时放宽到了多少？为什么那次可以放宽？先给方案，不要下单。

|---|---|

| 今天可以到 30 元、不要下单 | 当前用户消息 |

不能只找回一个“预算数字”就结束，因为这里有三个不同时间范围。

## 13. 新会话是不是一开始就要搜索全部记忆

先区分两条进入上下文的路径。

### 13.1 路径一：启动时提供一部分背景

本例使用允许提供长期记忆的主会话，并假设 `MEMORY.md` 在字符预算内完整进入启动上下文。

于是第一轮模型请求已经可以包含：

> 用户不吃辣，工作日午饭通常控制在 20 元以内。

这属于启动上下文提供的材料。

它不代表磁盘上的所有文件都已经被模型读过。尤其是每日文件：是否作为近期材料提供，还要看具体的启动流程和配置，不能只因它放在 `memory/` 里，就断言每次必定全文注入。

### 13.2 路径二：针对问题搜索，再把结果交给模型

本例要问“上次接待同事”的金额和原因。

这些细节没有被整理进 `MEMORY.md`，所以还需要从每日记录找回来。

此外，本例记忆规则要求回答历史问题前先检索。即使模型已经见到了长期偏好，也应按规则核对相关记录。

```text
启动背景：先提供一部分长期资料

按需检索：根据今天的问题，找回相关的历史片段
```

**启动资料注入与按需检索，是记忆进入当前模型上下文的两条路径。** 两条路径可以共同服务同一次回答。

## 14. Memory Search 的第一步：明确今天要找什么

### 14.1 先由模型判断：缺少哪些历史事实

再看用户今天的问题：

> 按我平时的午饭偏好给方案，今天预算可以到 30 元。另外，我上次接待同事时放宽到了多少？为什么那次可以放宽？先给方案，不要下单。

模型需要把它拆成“需要查过去的内容”和“这次已经明确给出的要求”：

| 当前问题中的表达 | 模型要做的判断 | 是否需要查询历史 |
|---|---|---|
| 按我平时的午饭偏好 | 需要确认长期口味、默认预算 | 需要，按召回规则核对 |
| 上次接待同事时放宽到了多少 | 需要找那次接待事件中的预算金额 | 需要，金额正是待查事实 |
| 为什么那次可以放宽 | 需要找到事件背景和例外条件 | 需要，不能凭猜测解释 |
| 今天预算可以到 30 元 | 当前任务预算已经给出 | 直接采用，不必通过历史来确定 |
| 先给方案，不要下单 | 当前任务的执行边界 | 直接遵守 |

**“要查什么”由模型根据当前任务缺少的历史事实来确定；今天已经说清的 30 元，不需要再从记忆里找一个替代值。**

### 14.2 搜索词从哪里来：由当前问题组织成查询

模型接着把待查内容概括成适合检索的表达：

| 待查内容 | 可以用于查询的表达 | 这组表达的来源 |
|---|---|---|
| 平时吃午饭有什么偏好 | 午饭、口味、工作日预算 | 对“平时的午饭偏好”的概括 |
| 上次接待午饭的预算与原因 | 接待同事、临时放宽 | 对“上次接待同事时放宽预算”的概括 |

**这一步的查询内容由模型根据当前问题组织。** 搜索词可以摘取用户的原词，也可以用相近表达概括待查问题，并不是固定写在程序里的这几个词。

这里的“组织查询”不等于预先知道答案。模型可以根据问题写出“接待同事、预算放宽”，但**不能在查到记录前，凭空把待查金额 40 元当成已经确认的事实**。

本例使用的工具叫：

```text
memory_search
```

模型可以发起下面这次查询，这里仍只用自然语言展示参数含义：

| 项目 | 本例的选择 |
|---|---|
| 要查什么 | 用户的午饭口味、平时预算，以及接待同事时的预算例外 |
| 搜索词 | 午饭 口味 工作日预算 接待同事 临时放宽 |
| 最多返回几项 | 3 项 |

上面的“搜索词”实际是模型交给工具的一段**查询文本**。进入程序后，它会被用于关键词检索和查询向量生成；关键词分支还会按自身规则处理查询表达。

这组查询只是本例的一种选择。模型也可能拆成两次搜索：先查“午饭偏好”，再查“接待同事 预算”。如果第一次结果不足，还可以收窄或改写查询。

### 14.3 模型和搜索程序分别负责哪一步

```text
当前用户问题
  ↓ 模型理解：需要找平时偏好，以及上次接待午饭的事件
模型组织查询文本，并发出 memory_search 工具调用
  ↓ 搜索程序接到 query
查询数据库中的全文检索数据和可用的向量数据
  ↓
返回相关片段，再交给模型理解和使用
```

**模型负责决定要查的事实、组织查询和调用工具；搜索程序负责执行检索、打分和返回材料。**

不是运行程序看到用户说了“上次”两个字，就绕过模型直接查询数据库。

## 15. Memory Search 怎样找出相关片段

假设本例已经配置好向量服务，并启用混合搜索。先把两种搜索和第 10、11 节的表对应起来：

| 搜索方式 | 查询拿什么去比较 | 主要使用哪些表 | 返回什么 |
|---|---|---|---|
| 关键词搜索 | 查询中的文字与片段文字的匹配 | chunks_fts | 片段 ID、来源、行号、文字片段和文本相关性分数 |
| 语义搜索 | 查询向量与片段向量的相似程度 | chunks_vec 与 chunks，或直接读取 chunks 中的向量 | 片段 ID、来源、行号、文字片段和向量相关性分数 |

**两种方式都在找片段。关键词路径利用文字检索结构，语义路径利用数值向量；`files` 表主要维护文件状态，不是这两种搜索直接比较内容的主要对象。**

### 15.1 关键词搜索：查询文字怎样对应 chunks_fts

第 10.3 节中，程序已经把 C1、C2、C3 的完整片段文字写入 `chunks_fts`。这张全文检索表还带有片段 ID、文件路径和行号等来源字段。

为了单独看清关键词搜索，先用一个更简单的查询 **“20”** 演示。本例启动资料中已有默认预算 20 元；这次单独演示不替换第 14 节的完整查询。

原文中的 20 两侧有空格，可以在本例采用的常规全文分词路径下作为独立数字词项匹配。简化地看，会找到：

| chunks_fts 中的记录 | 原文中的相关文字（摘录） | 这个简单查询能匹配的依据 |
|---|---|---|
| C1 | 工作日午饭通常控制在 20 元以内。 | 包含数字词项 20 |
| C2 | 工作日午饭通常控制在 20 元以内。 | 包含数字词项 20 |
| C3 | 这只是今天的例外，平时仍按 20 元以内。 | 包含数字词项 20 |

实际执行过程可以理解为：

```text
程序接到查询文本
  ↓ 整理查询表达
交给 SQLite 的全文检索模块，在 chunks_fts 中查匹配记录
  ↓
按全文相关性排序，再转换为后续流程使用的文本分数
  ↓
从命中的记录直接取出 id、path、行号和文字片段
```

**关键词搜索不是先让大模型逐行阅读 `chunks_fts`，而是由程序调用数据库的全文检索能力完成匹配与排序。** 普通全文匹配路径采用 BM25 等排名信号；特殊回退路径还会有相应评分处理。

#### 回到第 14 节那段较长的查询，会怎样

第 14 节给出的查询是“午饭 口味 工作日预算 接待同事 临时放宽”。本地常规关键词查询构造会将多个词项按“同时满足”的方式组合。

**因此，查询词多，不等于更容易命中。** 例如笔记写的是“不吃辣”，查询里却有“口味”；或者原文将“工作日”和“预算”分开表达，都可能导致严格文字匹配找不到结果。

中文文字怎样成为可匹配词项，还受 tokenizer 配置影响。默认分词不能一概理解为“任意中文子串都能命中”；本地也提供 trigram 等相关路径，并对特定短中文查询作处理。

所以这次完整查询的关键词候选**可能为空**，并不保证一定找出 C3。模型可以通过后续调用缩短查询；没有向量 Provider 的关键词专用路径，也有自己的查询放宽逻辑。

### 15.2 语义搜索：查询向量怎样对应 chunks 和 chunks_vec

用户今天可能说“口味”，旧记录写的是“不吃辣”；今天问“上次为什么能多花一些”，旧记录写的是“接待同事，预算临时放宽”。

语义搜索要比较的是这两段表达的数值表示：

1. **建索引时**，片段原文已经经过 Embedding，向量保存在 `chunks.embedding`；向量扩展可用时，也写入 `chunks_vec`。
2. **这次搜索时**，程序将第 14 节的查询文本交给兼容的 Embedding 模型，得到查询向量 Q。
3. 比较 Q 与数据库中片段向量的相似程度，选出候选，再返回这些片段的原文和来源。

沿用第 10.3 节的虚构三维数据，可以把参与比较的记录画成：

| 片段 ID | chunks 中保留的内容提示 | 参与语义比较的片段向量 |
|---|---|---|
| C1 | 长期午饭默认偏好 | [0.12, -0.31, 0.08] |
| C2 | 第一次提出的午饭偏好 | [0.11, -0.29, 0.09] |
| C3 | 接待同事的预算例外 | [0.45, -0.10, 0.27] |

这里的向量仅展示数据形状，不据此手算本讲的实际搜索排名。查询向量也是一串数字，不是“午饭→C1”这样的文字目录。

#### 路径 A：向量扩展可用，查 chunks_vec，再对应 chunks

```text
本次查询文本 → Embedding → 查询向量 Q
  ↓
利用 chunks_vec 的向量查询取得邻近候选并计算相关性
  ↓ 通过相同的片段 id，对应到 chunks
取得原文、path、start_line、end_line 等
  ↓
返回带向量相关性分数的片段结果
```

**`chunks_vec` 提供向量检索，`chunks` 提供对应片段的文字和来源信息。** 本地这条查询会把两者按 ID 关联起来。

#### 路径 B：向量扩展不可用，直接读取 chunks 的向量

```text
从 chunks 读取符合来源和模型条件的片段及 embedding
  ↓
程序比较查询向量 Q 与各片段向量的余弦相似度
  ↓
排序、截取候选，返回原文片段及来源
```

**没有向量加速扩展，不一定等于不能做语义搜索：只要已有可用的 Embedding，内置后端也可以在程序中计算相似度。** 这与“根本没有向量 Provider、只做关键词搜索”是两种情况。

查询和片段必须采用可比较的向量空间。语义相近有助于召回，但不保证所有相关事实都一定命中，也不会自动验证片段里的事实是否适用于今天。

### 15.3 两路候选合起来，再筛选

**两路结果通过片段 ID 对齐。同一个 C3 同时被两路找到时，合并它的文字分数和向量分数；只被一路找到时，另一路分数按 0 处理。** 然后再排序和筛选。

本地融合还可能采用已启用的时间衰减、多样性重排等配置。整个过程不要求两路都有命中；第 14 节的较长查询即使没有严格关键词命中，也可能取得语义候选。

下面以“关键词候选为空，但语义检索找回三块”为例。假设向量分数分别为 0.90、0.86、0.80，按默认向量权重 0.7 参与融合，得到下面的教学分数，保留两位小数。这组数值不是实际运行结果：

| 返回顺序 | 来源 | 行范围 | 教学分数 | 片段主要内容 |
|---:|---|---|---:|---|
| 1 | memory/2026-10-27.md | 1～9 | 0.63 | 接待同事可到 40 元，仅当天例外 |
| 2 | MEMORY.md | 1～6 | 0.60 | 不吃辣，工作日通常 20 元以内 |
| 3 | memory/2026-10-26.md | 1～9 | 0.56 | 用户最初提出的偏好 |

**这里的分数只用于表示相关性排序，不是“这条记忆为真的概率”。**

也不要把这条混合搜索路径理解成所有环境的必经过程：没有向量服务时，本地内置后端在全文索引可用的条件下，也可以只做关键词搜索。

### 15.4 再用表把整个搜索过程对齐一次

| 环节 | 用到的资料或表 | 这一步回答的问题 |
|---|---|---|
| 模型组织查询 | 当前用户问题、召回规则和已有背景 | 这次缺少哪些历史事实，要用什么表达去查？ |
| 关键词检索 | chunks_fts | 哪些片段满足本次文字匹配？ |
| 语义检索 | chunks_vec 与 chunks，或 chunks 的 embedding | 哪些片段的向量与查询向量接近？ |
| 合并和筛选 | 两路返回的候选记录 | 最终保留哪些片段？ |
| 精确读原文 | 原始 Markdown 文件 | 命中位置的完整条件究竟是什么？ |
| 模型回答 | 工具结果与当前用户要求 | 历史事实应该怎样用于今天的任务？ |

**模型负责提出问题和理解结果；数据库及检索程序负责找到片段；原始文件保留可核对的事实来源。**

## 16. 搜索返回后，为什么还要 Memory Get

搜索结果通常带有：

- 来源文件路径；
- 片段起止行号；
- 相关性分数；
- 一段命中的文字。

这些信息首先解决的是：

> 去哪里找可能相关的资料？

但片段文字可能被截短，也可能混有其他事情。为了核实接待午饭的条件，助手再使用：

```text
memory_get
```

这次读取请求用自然语言表达就是：

> 读取 `memory/2026-10-27.md`，从第 3 行开始，连续读取 4 行。

根据前面的文件内容，精确取得：

```text
## 接待午饭
- 用户今天接待同事，午饭预算临时放宽到 40 元。
- 用户明确说明：这只是今天的例外，平时仍按 20 元以内。
- 口味仍然不辣；本次只给方案，不下单。
```

此处的“今天”是 **10 月 27 日那份记录中的今天**，不是现在 10 月 28 日。

文件日期、事件原因和“只是今天的例外”共同确定了这条事实的适用范围。

两种工具的分工是：

| 工具 | 解决的问题 |
|---|---|
| memory_search | 哪些片段可能与当前问题有关？ |
| memory_get | 某份文件指定位置的原文具体写了什么？ |

**`memory_get` 已经有准确的文件路径和行范围，不需要再做一次语义搜索。**

已知路径时也可以直接读取；在本例中，路径是先通过搜索发现的。

## 17. 找到了文件，不等于模型已经看到文件

这一段最容易被一句“系统检索了记忆”带过去，需要把中间过程展开。

### 17.1 第一次模型请求：模型先提出搜索

模型此时看到：

```text
助手规则和记忆工具说明
启动时提供的长期偏好
用户今天的问题：今天 30 元；询问上次接待同事的安排
```

模型输出一个动作：调用 `memory_search`。

### 17.2 程序执行搜索，把结果作为工具消息放回会话

程序执行索引检索，拿到刚才的路径、行号和片段。

它把结果作为工具返回消息，加入当前 Session。

**到这里，搜索结果已经成为下一次模型请求可以使用的上下文材料。**

### 17.3 第二次模型请求：模型看到搜索结果，再提出读取

模型现在能看到搜索命中的文件和片段，因此决定进一步读取 10 月 27 日的第 3～6 行。

它输出一个动作：调用 `memory_get`。

### 17.4 程序执行读取，再把原文放回会话

程序读取对应的四行文字，作为新的工具返回消息加入当前 Session。

### 17.5 第三次模型请求：结合三种时间范围回答

这次模型同时看到：

| 材料 | 含义 |
|---|---|
| 长期偏好 | 不吃辣，工作日通常 20 元以内 |
| 历史原文 | 10 月 27 日因接待同事临时放宽到 40 元 |
| 当前要求 | 10 月 28 日这次可以到 30 元，只给方案，不下单 |

于是可以先回答：

> 你平时不吃辣，工作日午饭通常控制在 20 元以内。上次是 10 月 27 日接待同事，临时放宽到了 40 元，并明确只限当天。今天按你这次提出的 30 元预算筛选不辣的午饭，只给方案，不下单。

接着，助手根据已经恢复的条件查询今天的菜单和库存。假设当前查询结果为：

| 午饭 | 当前价格 | 口味 | 当前库存 | 今天能否选择 |
|---|---:|---|---|---|
| 牛肉面 | 30 元 | 不辣 | 有货 | 可以，符合今天的 30 元预算 |
| 鸡腿饭 | 20 元 | 不辣 | 售罄 | 不可以，当前无货 |
| 蛋炒饭 | 10 元 | 不辣 | 有货 | 可以，符合预算 |

助手最终可以给出完整方案：

> 今天可以选 30 元的不辣牛肉面，也可以选 10 元的蛋炒饭；鸡腿饭虽然符合预算，但当前售罄。按你今天放宽到 30 元的要求，建议牛肉面作为一个可选方案，尚未下单。你平时的默认预算仍是 20 元；上次接待同事的 40 元只限 10 月 27 日。

这样，历史偏好已经影响了今天的筛选，当前预算也得到了正确采用。

**这里“先检索相关记忆，再把检索结果放入模型上下文，辅助生成回答”的过程，就是 RAG（Retrieval-Augmented Generation，检索增强生成）。**

第 [12 讲：互联网 RAG](/openclaw/chapter-12)会把资料来源换成网页，继续解释搜索、读取、证据整理和带来源回答的完整过程。

记忆模块提供历史依据；今天有没有鸡腿饭、价格是多少，来自当前的菜单和库存信息。不能把昨天的库存也当成今天仍然有效的记忆。

## 18. 为什么今天不能直接沿用搜索分数最高的 40 元

搜索分数最高，只表示这份材料与“接待同事”这个问题很相关。

它不意味着这份材料中的所有要求都适用于今天。

本例有三个预算：

| 金额 | 时间和适用条件 | 今天怎样使用 |
|---:|---|---|
| 20 元 | 工作日通常采用的默认预算 | 作为长期背景 |
| 40 元 | 10 月 27 日接待同事，仅当天 | 回答历史问题，不沿用为今天预算 |
| 30 元 | 用户今天明确提出 | 作为今天筛选午饭的预算 |

因此，需要把两个工作分开理解：

```text
检索：把相关材料找回来
  ↓
模型理解：结合日期、条件和当前要求，判断今天应该怎样使用
```

**检索分数不会替模型处理“通常”“仅当天”“从今以后”这些条件。**

同样，**今天允许 30 元也不表示长期默认预算已经永久修改。** 只有用户表达了长期变更意图，才应该相应更新长期事实。

## 19. 今天的过程结束后，还会不会产生新记忆

如果用户要求保存今天的安排，或者记忆规则判断它值得保留，助手可以创建：

```text
memory/2026-10-28.md
```

记录“本次临时预算 30 元”等当天事实。

如果没有值得新增的内容，也不必为了日期变化，强行创建一份文件。

`MEMORY.md` 中的长期默认预算仍然可以是 20 元，因为用户今天说的是“今天预算可以到 30 元”。

如果另一天用户明确说：

> 从今以后，工作日午饭默认预算改成 25 元。

那才是长期偏好发生变化。助手应记录这次变更，并在适当的长期记忆更新任务中把默认预算改成 25 元，同时保留必要的来源和变更时间。

这样，历史记录负责解释“以前发生过什么”，长期文件负责表达“当前默认是什么”。

## 20. 如果用户没有主动说“记一下”，还有什么保存机会

前面的主线都是用户明确发起保存或整理。

还有一种容易与它混淆的情况：当前聊天很长，快要进行第 08 讲的上下文压缩。

假设当前对话里出现了值得长期保留、但还没有落盘的事实。压缩前，宿主可以安排一次额外的记忆整理运行，这叫 **Memory Flush**。

可以把它理解为：

> 旧对话快要离开当前活动上下文了，先检查有没有值得写进每日记忆的事实。

它的主线仍然是：

```text
检查当前对话中尚未保存的重要事实
  ↓
模型整理成文字
  ↓
通过文件工具追加到当天的每日记忆
```

如果没有新内容可存，可以不写。

本地版本对此次 Flush 有明确边界：**写入当天的每日文件；已有内容只追加；此次运行把 `MEMORY.md` 等基础资料视为只读。**

### 20.1 这次额外运行，真的有专门的记忆生成 prompt

这与前面的普通保存任务不同：宿主会提供专门的压缩前保存提示。

假设这次发生在 10 月 27 日，默认任务提示可以译写成下面这样。**规则对应源码的默认 Flush prompt，下面使用中文解释，并将日期替换为教学日期；不是逐字的英文原文。**

```text
现在进行压缩前的记忆保存。

将需要持久保存的记忆，只写入 memory/2026-10-27.md。
memory/ 目录不存在时可以创建。

在本次保存中，将 MEMORY.md、DREAMS.md、SOUL.md、TOOLS.md、
AGENTS.md 等基础或参考文件视为只读，不要覆盖、替换或修改它们。

如果当天文件已经存在，只追加新内容，不覆盖已有记录。
不要创建带时分的其他版本，始终使用当天的标准日期文件名。
如果没有内容需要保存，回复 NO_REPLY。
```

宿主还会附加一段系统提示，其核心意思是：

> 当前会话接近自动压缩，请把需要持久保留的记忆写入磁盘。遵守当天文件、只追加和参考文件只读等要求；通常不需要面向用户回复。

这些提示与当前会话可用的对话上下文一起交给模型，模型再判断有哪些尚未保存的重要事实，并执行文件写入。

所以这里不是只把一句“请保存记忆”孤立地发送给一个完全没有上下文的模型；要保存的事实来自这次运行能看到的会话材料。

### 20.2 三种保存任务，对应三种提示来源

所以要区分：

| 动作 | 本例中会做什么 |
|---|---|
| 用户说“记住我的偏好” | 可以在普通对话中立即保存，不必等上下文满 |
| 压缩前 Memory Flush | 检查尚未保存的事实，追加每日记忆 |
| 整理长期记忆 | 筛选每日记录中的稳定事实，创建或更新 MEMORY.md |

三者不是同一个触发器，也不是同一个写入任务。

## 21. 用一条时间线走完前半讲

```text
刚建立助手
  工作目录中先有规则和基本资料，尚无本例的用户记忆
  ↓
10 月 26 日
  用户要求记住：不辣、工作日通常 20 元
  模型提取事实，文件工具创建当天记忆
  当天再有事项，保留原记录并追加
  ↓
10 月 27 日
  接待同事临时 40 元，明确仅当天
  文件工具创建第二天的记忆，保留例外条件
  ↓
10 月 27 日晚
  用户发起长期整理
  模型读取两天记录，筛选、去重

  ↓

  扫描允许检索的记忆文件

  建关键词索引，有条件时生成片段向量
  ↓
10 月 28 日的新 Session
  旧聊天消息没有自动变成今天的活动消息
  工作目录和索引仍然保留

  ↓
用户今天提问
  今天 30 元；追问上次接待同事的预算和原因
  ↓

  ↓

```

到这里，应该已经能回答四个问题：

1. 每日文件如何形成？由具体保存任务提取当天事实，再通过文件工具创建或追加。
2. `MEMORY.md` 如何形成？由长期整理任务读取材料、筛选归纳，再通过文件工具更新。
3. `memory_search` 做什么？从索引中找出相关片段，返回来源、行号和文字。
4. 记忆何时真正被模型使用？在启动资料或工具返回内容进入模型请求后，模型才能据此回答。

## 第二部分：把例子抽象成算法

## 22. 先分清五种状态，避免把所有东西都叫“记忆”

| 状态或产物 | 保存什么 | 主要用途 |
|---|---|---|
| 当前活动上下文 | 本次模型请求实际携带的消息和资料 | 让模型回答眼前问题 |
| Session 记录 | 对话、工具结果、分支和压缩等会话记录 | 恢复和继续特定会话，见第 09 讲 |
| Compaction 摘要 | 当前会话较老内容的摘要 | 缩短活动上下文，见第 08 讲 |
| 每日文件与 MEMORY.md | 可跨会话复用的文本事实 | 持久保存和维护记忆 |
| 检索索引 | 文件信息、文本片段、全文索引及向量等 | 按当前问题找到材料 |

同一句“不吃辣”可能同时出现在多种产物里，但它们的职责不同。

Session 可以保存整段对话；每日文件只提取值得留存的事实；索引从文件派生检索结构；模型使用的是最终进入当前请求的内容。

默认记忆来源是记忆文件。可选的 Session transcript 索引属于额外配置，不能把“Session 已落盘”直接等同于“所有历史会话已经可检索”。

## 23. 写入、整理、索引和召回，是四段相连的流程

```text
日常保存：
对话 → 判断事实和适用范围 → 形成文字 → 创建或追加每日文件

长期整理：
已有记忆 + 新证据 → 筛选、去重、处理变更 → 创建或更新 MEMORY.md

索引同步：
发现文件变化 → 分段 → 更新文本和来源 → 更新全文索引及可用的向量

按需召回：
当前问题 → 搜索查询 → 候选检索 → 合并筛选
    → 返回片段 → 读取所需原文 → 工具结果进入上下文 → 模型回答
```

前两段需要模型理解事实，文件工具负责落盘；索引和检索主要由程序及相应服务执行；最终怎样采用事实，仍然需要模型理解当前任务。

## 24. 索引同步怎样知道哪些文件需要处理

可以把同步过程抽象成：

1. 扫描配置允许的来源，取得文件列表。
2. 读取文件信息和内容 Hash，判断哪些内容发生变化。
3. 无需更新的文件尽量跳过；需要重建时重新处理。
4. 对变化文件切块，保留原文行号和片段 Hash。
5. 更新片段文本、全文索引，以及可用的向量记录。
6. 清理失效的旧记录，更新同步状态和索引元信息。

因此，用户手工修改 Markdown 也可以成为下一次同步的输入。索引不要求文件必须由某个特定模型写出。

同时，写文件和更新索引是两个阶段，所以存在短暂不同步的可能。

首次空索引的等待同步，以及已有索引时的后台同步，需要分别理解，不能概括成“每次搜索都先重建所有文件”。

## 25. 切块怎样工作：手算一个小例子

前半讲的文件很短，这里单独用四行 ASCII 文本演示分块，不改变前面午饭例子的文件内容。

| 行号 | 文本 | 字符数 | 计入换行的估算长度 |
|---:|---|---:|---:|
| 1 | `budget=20.` | 10 | 11 |
| 2 | `spicy=no..` | 10 | 11 |
| 3 | `order=no..` | 10 | 11 |
| 4 | `rice=maybe` | 10 | 11 |

设片段预算为 8 个估算 token，重叠目标为 2 个估算 token。对于这些 ASCII 字符，按每 token 约 4 字符计算：

```text
片段额度 = max(32, 8 × 4) = 32
重叠额度 = 2 × 4          = 8
```

加入前两行后，累计 22；如果加入第三行，会变成 33，大于 32。因此先输出第 1～2 行。

随后从尾部保留重叠：第 2 行估算长度为 11，已经达到目标 8，所以整行保留。

带着第 2 行继续加入第 3 行，累计 22；再加入第 4 行会超额，于是输出第二块。

最终得到：

```text
C1：第 1～2 行
C2：第 2～3 行
C3：第 3～4 行
```

这里的重叠按行保留，因此实际重叠可以超过目标。

这套预算是启发式估算，不是经过真实 Tokenizer 验证的严格上限。中文还会进行字符加权，长行也可能继续分段，不能把这个 ASCII 手算直接套到所有文本。

## 26. Embedding 怎样支持“意思接近”

建立索引时，用 Embedding 模型把每个片段转成向量；查询时，用兼容的模型把查询也转成向量。

为了手算，假设只有二维，而且向量长度都为 1：

```text
查询 q = [1, 0]
片段 a = [0.8, 0.6]
片段 b = [0, 1]

q 与 a 的余弦相似度 = 0.8
q 与 b 的余弦相似度 = 0
```

于是 a 的方向更接近查询。

真实向量一般有更多维度；这里的坐标没有“第一维就是辣度”这样的业务含义。

也不能随意把不同模型的向量放在一起比较。相同文本由不同模型生成的向量，维度和空间含义都可能不同。

为了减少重复计算，系统还可以缓存 Embedding。缓存不能只按文字内容区分，还要带上 Provider、模型和 Provider 身份等信息。

## 27. 混合搜索怎样合并两路候选

沿用本地默认权重的教学计算：

```text
混合分数 = 0.7 × 向量分数 + 0.3 × 文本分数
```

假设两路分数已转换到流程使用的尺度：

| 候选 | 向量分数 | 文本分数 | 混合分数 |
|---|---:|---:|---:|
| A | 0.8 | 0.4 | 0.68 |
| B | 0.6 | 0.9 | 0.69 |
| C | 0 | 0.1 | 0.03 |

按这个分数，B 排在 A 前面。

这些数值与前半讲的示意搜索结果相互独立，只用于手算融合过程。

两路同时命中同一个 Chunk 时，按 Chunk ID 合并，不把它当成两个独立结果。

但要特别区分：`MEMORY.md` 和某份每日文件即使都写了“不吃辣”，也可能属于两个不同 Chunk。**按 ID 合并不是跨文件事实去重。**

若最多需要 3 项结果，候选倍数为 4，就可先为每路准备最多 12 个候选，再融合筛选。本地代码还对候选数量设置了上下限。

候选数大于最终返回数，是为了给排序留下选择空间，不表示把 12 项全文全部送进模型。

## 28. 完整的搜索算法，还要处理哪些分支

内置后端的主线可抽象为：

```text
1. 检查索引是否有内容，空索引时尝试等待首次同步。
2. 规范化查询，空查询或无可检索内容时结束。
3. 按配置触发后台同步，初始化需要的向量服务。
4. 确定候选数、最低分数和最终结果数。
5. 无向量 Provider：若全文索引可用，走关键词搜索。
6. 有向量 Provider：若允许混合搜索且全文索引可用，取得关键词候选。
7. 生成查询向量，召回向量候选。
8. 合并两路分数，应用启用的排序调整。
9. 按阈值和数量输出，符合条件时采用关键词命中回退。
```

关键词分支对查询词怎样分割、怎样匹配，受全文索引的 tokenizer 等因素影响。尤其不能把中文语义召回完全等同于简单的关键词包含关系。

本地还支持两项可选排序调整，默认都关闭：

| 调整 | 目的 |
|---|---|
| 时间衰减 | 对适用的记忆降低较旧记录的排序权重 |
| MMR 多样性重排 | 在保持相关性的同时，减少结果之间的重复 |

它们调整的是检索结果，不会直接改写原文件，也不是事实校验器。

若工具不可用、索引尚未更新、查询没有命中，得到的现象可能不同。不能把这些情况一律解释成“用户从未说过”。

## 29. Flush、Compaction 和长期整理，算法上如何分开

Memory Flush 的 token 门槛可用一个教学公式表示：

```text
触发阈值 = 上下文窗口 - 保留额度 - 提前触发额度
```

例如窗口 100,000、保留 20,000、提前 4,000，对应阈值 76,000。

真实触发还要检查配置、可写条件、当前压缩周期是否已经 Flush 等。本地宿主还有 transcript 大小等辅助触发与去重路径，不能只靠这一个公式解释所有情况。

各动作的产物应分开看：

| 动作 | 主要产物 | 是否等同于生成 MEMORY.md |
|---|---|---|
| Session 持久化 | 会话记录 | 否 |
| Compaction | 当前会话摘要和压缩记录 | 否 |
| Memory Flush | 追加到当天每日文件的事实 | 否，本版本此次 Flush 将长期文件视为只读 |
| 用户发起长期整理 | 经筛选的长期事实 | 可以创建或更新 |
| 可选 Dreaming | 经过额外条件筛选的长期提升结果 | 启用并满足条件时可能更新 |
| 索引同步 | 文本片段、全文索引和向量等 | 否 |

本地的 Dreaming 是可选能力，默认关闭，具有独立的调度和提升条件。它与本例用户发起的整理任务，以及压缩前的 Flush，都应分开理解。

## 30. memory-core 怎样提供记忆能力

### 30.1 插件入口注册什么

先打开 [extensions/memory-core/index.ts](/source/?file=c4729b2f2567e7f5c1.ts)。入口的 `register(api)` 注册 Embedding Provider、记忆能力、两个记忆工具及 CLI 等功能。

记忆能力的注册，源码摘录：

```ts
api.registerMemoryCapability({
  promptBuilder: buildPromptSection,
  flushPlanResolver: buildMemoryFlushPlan,
  runtime: memoryRuntime,
  publicArtifacts: {
    listArtifacts: listMemoryCorePublicArtifacts,
  },
});
```

四个字段分别提供：召回提示的构造函数、压缩前保存计划、运行时入口，以及可列举的记忆产物。

**这里是在登记“宿主可以怎样使用记忆能力”，还没有因为注册成功就执行一次搜索，也没有立即生成用户记忆。**

接着注册搜索工具，源码摘录：

```ts
api.registerTool(
  (ctx) =>
    createMemorySearchTool({
      config: ctx.config,
      agentSessionKey: ctx.sessionKey,
    }),
  { names: ["memory_search"] },
);
```

`memory_get` 采用同样方式调用 `createMemoryGetTool` 注册。工厂收到当前配置和 Session Key，返回适用于本次 Agent 上下文的工具。

这是 **OpenClaw 插件 API**；后面是宿主将工具交给 Pi，而不是把这段代码直接改写成 Pi 的 `pi.registerTool(...)`。

### 30.2 工具怎样定位当前 Agent 和后端管理器

打开 [tools.shared.ts](/source/?file=5246265a457ac7e880.ts)，顺着三个函数读：

```text
createMemoryTool
  → resolveMemoryToolContext
    → 从 config 和 agentSessionKey 确定 agentId
    → 检查该 Agent 是否启用了记忆搜索
  → 返回 name、description、parameters、execute 等字段

搜索工具实际执行
  → getMemoryManagerContext
  → getMemoryManagerContextWithPurpose
  → getMemorySearchManager
  → 内置后端对应 MemoryIndexManager
```

`createMemoryTool` 最后装配工具的源码：

```ts
return {
  label: params.label,
  name: params.name,
  description: params.description,
  parameters: params.parameters,
  execute: params.execute(ctx),
};
```

`execute` 是稍后由通用工具执行链调用的函数。记忆配置不可用时，工具工厂可以返回 `null`，并非所有会话都无条件拥有记忆工具。

后端选择看 [search-manager.ts](/source/?file=6b35bde92ab821805c.ts)。它处理内置后端、QMD 等管理器的选择；本讲继续跟内置的 `MemoryIndexManager`，不展开其他后端。

### 30.3 模型为什么知道应该先搜索

打开 [prompt-section.ts](/source/?file=0990577714cd818f8a.ts)。`buildPromptSection` 根据当前可用工具构造 `Memory Recall` 段落。

当两个工具都可用时，它要求回答以前的工作、决定、日期、人物、偏好或待办前，先执行 `memory_search`，再用 `memory_get` 读取所需行。

**提示告诉模型何时召回；工具定义告诉模型怎样调用；工具的 execute 才负责真正执行。** 这三个环节需要同时对上。

### 30.4 生成记忆的提示在哪里

先对应前半讲的三种情况：

| 场景 | 提示来源 | 保存行为 |
|---|---|---|
| 用户说“记住我的偏好” | 工作目录规则、当前请求和工具说明 | 模型在普通对话中调用文件工具保存 |
| 用户要求整理 MEMORY.md | 整理规则、当前请求和读取结果 | 模型筛选、归纳后更新长期文件 |
| 压缩前 Memory Flush | 专门的默认任务提示和系统提示 | 额外运行中追加当天每日文件 |

日常规则可对照 [AGENTS.md 工作目录模板](/source/?file=dc83ab97ed9ee04842.md) 的 Memory 部分。模板要求用户说“remember this”时更新每日记忆等相关文件，并逐步回顾每日记录，整理值得保留的长期事实。

**普通保存任务不一定另外调用一个统一的“记忆生成函数”；它可以由普通 Agent 循环执行文件工具来完成。** 某个助手实际收到什么，应检查它自己的工作目录规则和最终上下文。

专门的 Flush prompt 在 [flush-plan.ts](/source/?file=964d767cfe8b07ef65.ts)。源码摘录：

```ts
export const DEFAULT_MEMORY_FLUSH_PROMPT = [
  "Pre-compaction memory flush.",
  MEMORY_FLUSH_TARGET_HINT,
  MEMORY_FLUSH_READ_ONLY_HINT,
  MEMORY_FLUSH_APPEND_ONLY_HINT,
  "Do NOT create timestamped variant files (e.g., YYYY-MM-DD-HHMM.md); always use the canonical YYYY-MM-DD.md filename.",
  `If nothing to store, reply with ${SILENT_REPLY_TOKEN}.`,
].join(" ");
```

同一文件的 `DEFAULT_MEMORY_FLUSH_SYSTEM_PROMPT` 是配套系统提示。三条插入规则要求写入当天的 `memory/YYYY-MM-DD.md`、已有文件只追加，并在此次 Flush 中将 `MEMORY.md` 等参考文件视为只读。

`buildMemoryFlushPlan` 采用配置或默认提示，补齐约束，按用户时区替换日期；宿主再把计划交给额外的 Agent 运行。

所以这里的默认 prompt **保存的是每日记忆，不是在此次 Flush 中改写 MEMORY.md**。这些写入完成后，数据库同步才有可处理的原始材料。

## 31. 数据库怎样建立和维护索引

### 31.1 管理器怎样取得数据库连接

打开 [manager.ts](/source/?file=f418791865e3d2784b.ts) 的 `MemoryIndexManager.get`。

它先解析该 Agent 的搜索配置与工作目录，再按 Agent、工作目录、配置和用途组织缓存键。普通调用尽量复用已有管理器，同时处理创建中的请求；状态用途存在独立处理，不能概括成所有调用都使用同一个对象。

构造管理器时，关键动作包括：

```text
保存 cfg、agentId、workspaceDir、settings
  → 打开 SQLite 数据库
  → 初始化全文检索状态并确保表结构存在
  → 准备向量扩展状态、读取索引元信息
  → 普通用途下安装文件监听等同步机制
```

数据库路径由 [memory-search.ts](/source/?file=d3645599de0c7f90d2.ts) 解析，默认位于状态目录的 `memory/<agentId>.sqlite`，也允许配置覆盖。

数据库打开函数在 [manager-db.ts](/source/?file=ba44dd400cb8e3335a.ts)。核心源码：

```ts
const dir = path.dirname(dbPath);
ensureDir(dir);
const { DatabaseSync } = requireNodeSqlite();
const db = new DatabaseSync(dbPath, { allowExtension });
```

随后设置连接的 `busy_timeout = 5000`，减少多进程并发写入时立即因数据库忙而失败的情况。

**数据库连接由内置记忆管理器维护，AgentSession 不需要自己打开 main.sqlite。**

### 31.2 表结构在哪里定义

管理器调用 `ensureSchema`，具体建表定义在 [memory-schema.ts](/source/?file=8f2c56c8464d2e77da.ts)。

下面是源码中的两段建表 SQL；这里只展示 SQL 正文，省去外围 TypeScript 字符串：

```sql
CREATE TABLE IF NOT EXISTS files (
  path TEXT PRIMARY KEY,
  source TEXT NOT NULL DEFAULT 'memory',
  hash TEXT NOT NULL,
  mtime INTEGER NOT NULL,
  size INTEGER NOT NULL
);
```

```sql
CREATE TABLE IF NOT EXISTS chunks (
  id TEXT PRIMARY KEY,
  path TEXT NOT NULL,
  source TEXT NOT NULL DEFAULT 'memory',
  start_line INTEGER NOT NULL,
  end_line INTEGER NOT NULL,
  hash TEXT NOT NULL,
  model TEXT NOT NULL,
  text TEXT NOT NULL,
  embedding TEXT NOT NULL,
  updated_at INTEGER NOT NULL
);
```

把字段与第 11 节的实际数据对齐：

| 结构 | 关键字段 | 负责什么 |
|---|---|---|
| files | path、hash、mtime、size | 记录原文件已经处理到什么状态 |
| chunks | id、text、path、start_line、end_line | 保存可检索的原文片段及其位置 |
| chunks 的向量字段 | model、embedding | 保留片段所属模型和 JSON 文本形式的向量 |
| chunks_fts | text、id、path、source、model、行号 | 使用 SQLite FTS5 提供关键词搜索 |
| embedding_cache | provider、model、provider_key、hash 等 | 复用相同模型身份下的向量计算结果 |
| meta | key、value | 保存索引和运行所需元信息 |
| chunks_vec | id、扩展使用的向量数据 | 向量扩展可用时提供加速查询 |

全文检索表、缓存表和向量表的存在还受启用状态及初始化结果影响。**建好普通 chunks 表，不等于向量扩展已经加载成功。**

### 31.3 文件变化怎样进入数据库

打开 [manager-sync-ops.ts](/source/?file=4da9e012e9d7e837f9.ts)。

文件监听收到新增、修改或删除事件后，标记 dirty，并安排同步；它不会仅在收到事件的那一瞬间，就保证所有数据库记录已经更新完毕。

同步主线如下：

```text
sync
  → 扫描允许的记忆文件，建立当前文件信息
  → 从 files 读取此前的内容 Hash
  → 无需全量重建且 Hash 未变：跳过
  → 新增或变化文件：indexFile
  → 清理已经删除文件的旧记录
```

`syncMemoryFiles` 中的关键判断是：正常增量同步时，已有 Hash 与新 Hash 相同就跳过，否则调用 `indexFile(entry, { source: "memory" })`。

**Hash 用来判断内容是否需要重新处理；不是用来回答“哪段文字和今天问题最接近”。**

### 31.4 indexFile 怎样切块和生成向量

打开 [manager-embedding-ops.ts](/source/?file=4f013d014d75c0ca84.ts) 的 `indexFile`。

无 Provider 的文本路径仍然切块并保存全文检索数据，源码摘录：

```ts
const content = options.content ?? (await fs.readFile(entry.absPath, "utf-8"));
const chunks = filterNonEmptyMemoryChunks(chunkMarkdown(content, this.settings.chunking));
if (options.source === "sessions" && "lineMap" in entry) {
  remapChunkLines(chunks, entry.lineMap);
}
this.writeChunks(entry, options.source, "fts-only", chunks, [], false);
```

有 Provider 时，文本切块后还要满足 Embedding 输入限制，再计算或复用向量，最后调用 `writeChunks`。

切块函数在 [host/internal.ts](/source/?file=9e129d47302a34a2f1.ts) 的 `chunkMarkdown`。它按估算长度、行与重叠预算组织片段；超长行会进一步分段。中文加权来自 [cjk-chars.ts](/source/?file=0d61c8d27e9a92f910.ts)。

它输出原文的关键源码是：

```ts
const text = current.map((entry) => entry.line).join("\n");
const startLine = firstEntry.lineNo;
const endLine = lastEntry.lineNo;
```

**这里直接拼接原文行，没有调用对话模型生成摘要。** 前半讲的“第 1～8 行”和“第 6～9 行”就是这种切块结果。

### 31.5 writeChunks 怎样把记录写进去

仍看 `manager-embedding-ops.ts` 的 `writeChunks`，按以下顺序读：

1. 清理该文件失效的旧片段、全文检索和向量记录。
2. 为当前片段计算 ID。
3. 向 `chunks` 写入正文、行号、内容 Hash、模型和向量等。
4. 向量加速可用且片段有向量时，写入相应向量记录。
5. 全文检索可用时，写入 `chunks_fts`。
6. 更新 `files` 中该文件的状态。

片段 ID 的源码：

```ts
const id = hashText(
  `${source}:${entry.path}:${chunk.startLine}:${chunk.endLine}:${chunk.hash}:${model}`,
);
```

`chunks.embedding` 的写入值使用 `JSON.stringify(embedding)`。没有向量时，这条路径可以写入空数组；它仍然保留片段原文。

**第 11 节展示的 Hash、Embedding 和片段 ID，在这里分别进入不同字段；它们的用途不能互换。**

到此，写入链完成的是：原始文件经过同步，成为可检索的数据库记录。接下来才是某次用户提问触发搜索。

## 32. memory_search 怎样执行查询

### 32.1 工具层接收什么参数

工具定义在 [tools.ts](/source/?file=62a95caf49871ed56d.ts) 的 `createMemorySearchTool`；参数 Schema 在 [tools.shared.ts](/source/?file=5246265a457ac7e880.ts)。

本例的教学调用参数：

```json
{
  "query": "午饭 口味 工作日预算 接待同事 临时放宽",
  "maxResults": 3
}
```

`query` 是模型根据当前问题组织的查询文本。`maxResults` 限制返回项数；`minScore` 可控制最低分数。`corpus` 用来选择语料，本讲跟普通记忆路径，不展开 Wiki 补充语料。

工具执行函数解析参数、取得当前 Agent 的管理器，然后执行以下源码：

```ts
rawResults = await memory.manager.search(query, {
  maxResults,
  minScore,
  sessionKey: options.agentSessionKey,
  qmdSearchModeOverride,
  onDebug: (debug) => {
    runtimeDebug.push(debug);
  },
});
```

**工具层负责接参数与包装返回值；实际内置检索主线在 MemoryIndexManager.search。** 管理器取得失败或搜索发生错误时，工具会组织不可用信息，不能把它一概当成“用户从未说过”。

### 32.2 search 怎样预检和准备候选

进入 [manager.ts](/source/?file=f418791865e3d2784b.ts) 的 `search`。

首先检查是否有索引内容，空索引时尝试等待首次同步，源码摘录：

```ts
let hasIndexedContent = this.hasIndexedContent();
if (!hasIndexedContent) {
  try {
    // A fresh process can receive its first search before background watch/session
    // syncs have built the index. Force one synchronous bootstrap so the first
    // lookup after restart does not fail closed with empty results.
    await this.sync({ reason: "search", force: true });
  } catch (err) {
    log.warn(`memory sync failed (search-bootstrap): ${String(err)}`);
  }
  hasIndexedContent = this.hasIndexedContent();
}
```

之后规范化查询、检查可检索状态，按配置触发后台同步，并初始化需要的 Provider。

候选数的计算源码：

```ts
const candidates = Math.min(
  200,
  Math.max(1, Math.floor(maxResults * hybrid.candidateMultiplier)),
);
```

本例最终返回 3 项、候选倍数 4 时，每路候选额度为 12，再经过融合与筛选。**最终结果数与检索阶段的候选数不是同一个值。**

### 32.3 关键词路径怎样查询 chunks_fts

底层函数在 [manager-search.ts](/source/?file=1fb006b402c03a7668.ts) 的 `searchKeyword`。

它根据查询和 tokenizer 形成全文匹配计划。常规查询构造把多个词项用 AND 连接；特定 trigram 短中文路径还会使用补充的文字匹配条件。

下面是普通 FTS 路径的**教学简化 SQL**，将源码中的表名插值展开，并省略模型、来源等附加过滤：

```sql
SELECT id, path, source, start_line, end_line, text,
       bm25(chunks_fts) AS rank
FROM chunks_fts
WHERE chunks_fts MATCH ?
ORDER BY rank ASC
LIMIT ?;
```

两个 `?` 是按顺序绑定的参数占位符：`MATCH ?` 接收处理后的全文查询表达式，`LIMIT ?` 接收候选数。例如对这段简化 SQL 绑定 `"memory"` 和 `10`，就表示搜索匹配 `memory` 的记录，最多取 10 条候选。程序从命中记录直接取得路径、行号和正文片段，再把排名值转换为后续流程使用的文本分数。

例如第 15 节单独演示的查询“20”，可以匹配片段中的独立数字词项；较长中文查询是否命中，要看词项组合和实际 tokenizer，不能视为任意子串查找。

**关键词检索使用 chunks_fts 的文字索引，不比较 Hash，也不比较 Embedding。**

没有 Provider 时，`search` 会走单独的 FTS-only 分支；完整查询没有结果时，它还可能提取词项、扩大查询，再合并去重。这个分支应与有 Provider 的混合分支分别阅读。

### 32.4 语义路径怎样查询向量

有 Provider 时，`search` 中的核心源码是：

```ts
const queryVec = await this.embedQueryWithTimeout(cleaned);
const hasVector = queryVec.some((v) => v !== 0);
const vectorResults = hasVector
  ? await this.searchVector(queryVec, candidates).catch(() => [])
  : [];
```

**这里计算的是本次 query 的向量。片段向量已经在索引阶段准备，搜索不需要无条件为全部旧片段重新生成向量。**

继续看 `manager-search.ts` 的 `searchVector`：

```text
向量扩展准备成功
  → 在 chunks_vec 中查询邻近候选
  → 按 id 关联 chunks
  → 取得原文、来源和行号，并计算相应分数

向量扩展不可用
  → 从 chunks 读取当前模型和允许来源对应的片段向量
  → 程序计算查询向量与片段向量的余弦相似度
  → 排序，返回候选
```

扩展路径在源码中使用原生 KNN 取得候选，并用余弦距离参与评分。直接读取路径则解析 `chunks.embedding` 中的 JSON 数组，在程序里比较。

**“扩展不可用”和“没有 Embedding Provider”不同：前者仍可能计算语义相似度，后者走可用的关键词专用路径。**

### 32.5 两路结果怎样融合与返回

有 Provider 且混合搜索、FTS 可用时，管理器取得关键词和向量候选，再调用 [hybrid.ts](/source/?file=bb8cd17691799c117a.ts) 的 `mergeHybridResults`。

它按 Chunk ID 对齐，缺失一路的分数按 0 处理，核心源码：

```ts
const score = params.vectorWeight * entry.vectorScore + params.textWeight * entry.textScore;
```

随后应用启用的时间衰减、多样性重排等；管理器再做最低分数、数量限制和特定词法命中回退。禁用混合搜索或 FTS 不可用时，有 Provider 的路径可以只筛选向量结果。

工具层最后包装路径、行号、分数、snippet、Provider 和状态等信息，返回给 Agent。

**这时返回的是相关材料，不是最终用户答案。** 片段何时进入下一次模型请求，要看第 34 节的通用工具循环。

## 33. memory_get 怎样精确读取原文

### 33.1 搜索与读取的参数为什么不同

入口同样在 `tools.ts`，函数是 `createMemoryGetTool`。本例参数如下：

```json
{
  "path": "memory/2026-10-27.md",
  "from": 3,
  "lines": 4
}
```

**from 表示开始行，lines 表示读取行数。** 因此读取第 3、4、5、6 行，不是从第 3 行读到第 4 行。

内置后端分支的实际调用表达式：

```ts
await readAgentMemoryFile({
  cfg,
  agentId,
  relPath,
  from: from ?? undefined,
  lines: lines ?? undefined,
})
```

外层还会用 `executeMemoryReadResult` 处理返回值和异常。其他后端可能走自己的读取管理器；本讲不把这些分支混在一起。

### 33.2 为什么这里直接读文件

打开 [read-file.ts](/source/?file=96c8626a46ae90f2a7.ts)。

`readAgentMemoryFile` 解析当前 Agent 的配置、工作目录和读取额度，再调用 `readMemoryFile`。后者按下面的路径执行：

```text
规范化传入路径，解析为实际文件位置
  → 检查是否属于允许的记忆路径或配置的额外路径
  → 检查 Markdown 文件类型和文件状态
  → 读取当前磁盘上的原文件内容
  → 构造指定行范围的有界读取结果
```

**内置 memory_get 的这条路径读取原始 Markdown，不需要先查询 SQLite，更不需要生成查询向量。** 但是它仍受记忆配置、路径范围和上下文额度等限制，不是任意文件读取入口。

文件不存在时，可以返回空文本等结果；路径不允许或运行失败则有相应异常和工具错误包装。这些情况不能都解释为“已读到一条空记忆”。

### 33.3 行号和长度额度怎样生效

继续看 [read-file-shared.ts](/source/?file=616085843162d03fa0.ts) 的 `buildMemoryReadResult`。源码摘录：

```ts
const fileLines = params.content.split("\n");
const start = Math.max(1, params.from ?? 1);
const requestedCount = Math.max(
  1,
  params.lines ?? params.defaultLines ?? DEFAULT_MEMORY_READ_LINES,
);
const selectedLines = fileLines.slice(start - 1, start - 1 + requestedCount);
```

模型使用从 1 开始的行号；数组从 0 开始，所以内部用 `start - 1` 切片。本例相当于取下标 2、3、4、5，对应原文第 3～6 行。

默认行数常量为 120，默认字符额度为 12,000；实际 Agent 上下文配置可以提供覆盖值。后续结果构造还会检查字符上限和剩余原文。

**即使显式请求了若干行，也不是无界全文读取。** 结果可能带 `truncated`、`nextFrom` 和继续读取提示。本例只读取文件中部，后面还有第 7～9 行，也可能出现继续读取信息；前半讲为了聚焦事实只展示了原文部分。

返回的核心原文是：

```text
## 接待午饭
- 用户今天接待同事，午饭预算临时放宽到 40 元。
- 用户明确说明：这只是今天的例外，平时仍按 20 元以内。
- 口味仍然不辣；本次只给方案，不下单。
```

搜索使用索引版本，读取使用当前原文件。如果两次操作间文件被修改，旧行号可能变化，必须核对读取到的文字。

## 34. AgentSession 在哪里接入并执行记忆工具

### 34.1 OpenClaw 先把工具交给会话

先看 [openclaw-tools.ts](/source/?file=cb7d125c061753f2ae.ts)。`createOpenClawTools` 收集内置工具，再合并允许的插件工具。`memory-core` 注册的两个工具通过这条插件路径进入装配，之后还有 [pi-tools.ts](/source/?file=82b2fe241f7c60dcb0.ts) 的封装和策略筛选。

再看 [attempt.ts](/source/?file=4c2d09aeeb74b60140.ts)。它把有效工具转换成 SDK 工具，准备工具允许名单，并在创建会话时传入：

```ts
tools: sessionToolAllowlist,
customTools: allCustomTools,
```

这是创建参数中的两行源码，不是完整调用。外层通过 `createEmbeddedAgentSessionWithResourceLoader` 调用 `createAgentSession`，再应用构造好的系统提示，设置活动工具名称。

**注册成功、通过本次工具策略、进入会话工具集合，是连续但不同的检查点。**

Pi 课程快照中的 [agent-session.ts](/source/?file=24209413646c397dc9.ts) 使用 `_refreshToolRegistry` 合并工具定义和包装后的执行对象，并按允许名单、活动名称设置 Agent 可用工具。

本讲的 `pi-master` 是解释底层机制的源码快照；OpenClaw 的实际装配以它运行时安装的 Pi 依赖为准，不据此宣称两个仓库的版本完全相同。

### 34.2 AgentSession.prompt 没有直接调用 memory_search

`attempt.ts` 准备好当前输入后，实际进入会话的源码包括：

```ts
await abortable(activeSession.prompt(effectivePrompt));
```

Pi 的 `AgentSession.prompt` 处理扩展命令、输入展开、消息及前置事件等，随后进入：

```ts
await this.agent.prompt(messages);
```

**AgentSession.prompt 本身没有专门写一段“遇到午饭偏好就调用 memory_search”的业务代码。** 它把消息交给通用 Agent；模型结合 Memory Recall 提示和工具定义，决定发出记忆搜索调用。

### 34.3 真正调用工具 execute 的位置

继续跟 [agent-loop.ts](/source/?file=6adbf9ab77a3572a2f.ts)：

```text
模型输出 assistant 消息中的 toolCall
  → executeToolCalls
  → 按配置进入顺序或并发工具执行路径
  → 执行准备好的工具对象的 execute
```

`executePreparedToolCall` 中的关键调用表达式开头是：

```ts
const result = await prepared.tool.execute(
```

后面传入工具调用 ID、校验后的参数、取消信号和更新回调。这里按工具对象调用通用接口，不需要知道它内部使用 SQLite 还是直接读取文件。

因此两条分支自然接到前面的实现：

```text
memory_search 的 execute
  → tools.ts 的搜索执行函数
  → 当前 Agent 的 MemoryIndexManager.search
  → SQLite 全文和向量检索

memory_get 的 execute
  → tools.ts 的读取执行函数
  → readAgentMemoryFile
  → 原始 Markdown 文件的指定行
```

### 34.4 工具返回以后，哪里再把材料交给模型

同一个 AgentLoop 将执行结果包装成 `toolResult`。随后把结果追加到循环的上下文，源码摘录：

```ts
for (const result of toolResults) {
  currentContext.messages.push(result);
  newMessages.push(result);
}
```

循环继续，下一次模型请求就能看到这些工具消息。Session 订阅到消息结束事件后，也会把普通用户、助手和 `toolResult` 消息交给 `SessionManager.appendMessage` 保存。

**让模型使用检索材料的关键，是工具结果进入后续模型请求；把工具结果记入 Session 文件，则是另一条持久化动作。**

本例完整调用线是：

```text
OpenClaw 注册 memory-core
  → 装配并允许 memory_search、memory_get
  → 创建 AgentSession，提供 Memory Recall 和相关背景
  → activeSession.prompt
  → AgentSession.prompt → Agent.prompt → AgentLoop
  → 模型发出 memory_search
  → 工具 execute → MemoryIndexManager.search → 数据库检索
  → toolResult 加入循环上下文
  → 模型发出 memory_get
  → 工具 execute → readAgentMemoryFile → 原文件
  → 新 toolResult 加入循环上下文
  → 模型结合历史记录和今天 30 元的要求，形成回答
```

到这里只需要记住各层的职责：**memory-core 提供能力和工具，数据库维护与检索片段，memory_get 读取原文，AgentSession 和 AgentLoop 提供通用运行及工具调用机制。**
