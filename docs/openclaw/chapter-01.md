# 01 OpenClaw 介绍与整体架构

> 这一讲看三件事：OpenClaw 能帮我们做什么，图里的每一块负责什么，代码大概是怎么做出来的。
>
> 01～06 和 13 的主要做法在这一讲交代清楚；后面的源码讲解主要展开 07～12。

## 1. OpenClaw 是干什么的

**你在手机上发一句话，让电脑上的 AI 助手帮你干活，再把结果发回来。**

比如，你在 WeChat 里发：

> 帮我看看 todo.md 里还有哪些事没做，把最急的放前面。

助手去电脑上读这个文件，找出没完成的事项，排好顺序，再回到 WeChat 告诉你。

OpenClaw 就负责把这整件事接起来。

- 聊天软件负责让你发消息。
- 大模型负责看懂要求、判断怎么做、整理回答。
- 工具负责真的去读文件、运行命令。
- OpenClaw 负责把这些东西组织起来，让助手可以一直在线。

## 2. 为什么会有这个项目

项目最初的想法很直接：电脑上已经有能干活的 Agent，能不能从手机上给它发任务？

Peter Steinberger 从连接手机消息和电脑上的 Agent 做起，后来逐步加上更多渠道、工具和会话管理，发展成 OpenClaw。[项目介绍](https://openclaw.ai/blog/introducing-openclaw)

接上聊天软件以后，还得继续解决几件事：

- 这条消息是谁发的？
- 应该交给哪个助手？
- 上次聊到哪了？
- 助手能读哪些文件、用哪些工具？
- 做完以后，回到哪个聊天窗口？

这些事都需要程序来管。

## 3. 大模型、Agent、OpenClaw，各管哪一段

**大模型：看懂要求，想下一步，写回答。**

比如，模型判断：“要回答这个问题，我得先看看 todo.md。”

**Agent：把模型和工具接起来，让它能一步步做事。**

模型提出读文件，程序就调用读取工具；读完再把内容交给模型，让它继续处理。

**OpenClaw：把 Agent 放进一套随时能联系的助手系统里。**

它接消息、选助手、准备文件和工具，最后把结果送回来。

### 4.1 全程只用一个例子

假设 OpenClaw 已经在你的电脑上运行，也连好了 WeChat Bot。

助手的工作目录里放着 `todo.md`，也配好了读取文件的工具。

文件里写着：

```markdown
- [ ] 交课程作业（今晚截止）
- [x] 下载课件
- [ ] 整理课堂笔记（这周完成）
```

你发给助手一句话：

> 帮我看看 todo.md 里还有哪些事没做，把最急的放前面。

我们就跟着这句话，看图里的每一块做了什么。

### 4.2 先把总图读成四句话

**第一段：把你的消息接进来。**

**第二段：找到负责的助手，准备好这次要用的东西。**

**第三段：调用模型和工具，把事情做完。**

**第四段：把结果发回给你。**

图是为了说明分工。聊天消息、网页操作、定时任务，具体进入程序的走法会有区别。

下面每块都写明白两件事：**靠什么实现，以及拿一组具体输入走一遍会得到什么。** 例子中的代码和数据做了简化，用来讲思路；配置片段也只摘出本节需要的部分。

### 4.3 第一段：把消息接进来

![接入与控制](/resources/openclaw/assets/01-architecture-01-ingress.png)

| 图里这块负责干啥 | 这个例子里做了什么 |
| --- | --- |
| **01 WhatsApp / WeChat / Slack / Discord / WebChat / CLI**<br>这些是你联系助手的入口。聊天软件、网页、命令行都可以有自己的入口。 | 你打开 WeChat，把“帮我看看 todo.md”发给 Bot。 |
| **02 Channel ingress**<br>把聊天平台发来的消息整理一下，取出正文、谁发的、从哪儿发的。 | 取出你的要求，同时记下这是哪个 WeChat 聊天。 |
| **03 cron / heartbeat / webhook / internal trigger**<br>让助手在定好的时间，或者收到某个通知时开始干活。 | 这次是你主动发消息，用不到这一支。也可以另外配置成每天早上查看待办。 |
| **04 Gateway control plane**<br>这是一直开着的服务，负责管连接、接请求、协调运行和通知状态。 | 电脑上的服务收到这条消息，让后面的处理继续进行。 |

**Channel ingress 为什么要单独做？**

WeChat 和 Slack 发来的数据格式不一样。

先各自整理好，后面的代码就能用一套比较统一的信息处理消息。

**Gateway 图里的几个词，分别是什么意思？**

- **连接**：让客户端和助手服务保持联系。
- **认证**：检查连上来的客户端有没有相应凭据。
- **RPC**：客户端通过接口说“帮我做这件事”，服务再返回结果。
- **事件**：有了新状态，就通知关心这件事的客户端。

**不用你发消息，也能开始工作的几种方式：**

- **cron**：到点做事。比如每天早上 9 点检查待办。
- **heartbeat**：隔一段时间看看有没有需要处理或提醒的事。
- **webhook**：别的程序发来通知，助手按配置接着处理。
- **internal trigger**：程序内部发生了某件事，再带起后续处理。

这些方式需要提前配置。它们不一定都会调用模型，也不一定都会给你发消息。

#### 01 消息渠道与客户端：让你能联系到助手

**功能是什么：提供发任务、看回复的入口。你可以在 WeChat、网页或命令行里使用助手。**

**实现方式：普通的网络通信代码，收发消息这一步不需要大模型。**

以 WeChat 为例，先创建 Bot，把它的 Token 配到 OpenClaw 里。程序用这个 Token 调用 WeChat 的接口。

收消息有两种常见做法：

- **长轮询**：程序向 WeChat 请求新消息；暂时没有时，连接等一会儿再返回，然后继续请求。
- **Webhook**：程序提供一个 HTTP 地址，有新消息时由 WeChat 推送过来。

接到消息后，程序调用事先写好的处理函数。也就是“有消息来了，就执行这段代码”。

长轮询还会记下已经处理到哪条更新，后面继续往下取。网络断开时，也要处理重连和报错。

发消息则反过来：拿着 Bot 的账号信息、聊天编号和回复文字，调用平台的发送接口。

网页和命令行有自己的接法，可以通过 Gateway 的接口提交请求。它们不需要伪装成 WeChat 消息。

本例就是：**WeChat 把消息交给 Bot 的接收代码，接收代码再交给 OpenClaw。**

**拿一条消息走一遍：**

```text
WeChat 接口返回新消息：聊天编号 123，正文“帮我看看 todo.md”
    ↓
Bot 的消息处理函数收到这份数据
    ↓
调用后面的消息整理代码
```

这里是收到网络数据后执行函数，不需要模型先读一遍再决定“是不是来消息了”。

源码入口：[WeChat 接收方式的选择](/guide/unavailable#reference)。

#### 02 Channel ingress（消息接入）：把平台消息整理成后面能用的信息

**功能是什么：从平台消息中取出你说了什么、谁发的、来自哪个聊天等信息，让后面的代码能接着处理。**

**实现方式：普通代码读取字段、检查规则、转换格式，不需要大模型。**

WeChat 发来的东西里，有正文，也有发送者、聊天编号、消息编号等信息。

代码把后面需要的内容取出来，再装进自己的消息对象。Slack 等平台也做同样的整理。

可以把整理后的内容想成下面这样。字段名是讲义里的简写，不是源码接口原样：

```json
{
  "channel": "WeChat",
  "accountId": "日常助手的Bot账号",
  "senderId": "用户A",
  "chatId": "聊天123",
  "messageId": "消息456",
  "text": "帮我看看 todo.md 里还有哪些事没做，把最急的放前面。"
}
```

有附件就补上附件信息，有话题或线程就记下对应编号。还会按设置检查这个人或群能不能触发助手。

**正文给后面处理任务，来源信息留着找会话和发回复。** 所以不能只取一句文字，就把其他字段全丢掉。

这些是普通代码里的字段读取、判断和格式转换，不需要先问模型。

**具体的转换就像这样：**

```text
从 WeChat 数据里取 message.text       → 自己的数据里记成 text
从 WeChat 数据里取 message.chat.id    → 自己的数据里记成 chatId
从 WeChat 数据里取 message.from.id    → 自己的数据里记成 senderId
从 WeChat 数据里取 message.message_id → 自己的数据里记成 messageId
另外补上 channel = "WeChat" 和当前 Bot 的 accountId
```

这些字段的来源已经写在代码里，不用让模型猜哪一项是聊天编号。源码里的完整整理还会处理附件、线程、访问规则等情况。

源码入口：[WeChat 消息整理](/guide/unavailable#reference)。

#### 03 内部触发：让助手到点或收到通知后自动开始做事

**功能是什么：除了等你发消息，还能在约定时间、周期检查或收到其他程序通知时启动任务。比如每天早上自动整理待办。**

**实现方式：触发时机由定时器、HTTP 接口和普通代码决定；任务启动后，才可能需要模型处理内容。**

**cron 的做法，是保存一份任务安排，再算下一次什么时候执行。**

比如保存“每天早上 9 点检查 todo.md”，同时保存使用哪个助手、做什么、结果发到哪儿。

程序算出下次执行时间，用定时器等到相应时刻，再按配置发起任务或投递事件。执行后更新任务状态和下次时间。

任务安排会保存下来，程序重启后还能重新读取。

**heartbeat 的做法，是按配置隔一段时间发起一次检查。** 可以结合 `HEARTBEAT.md` 里的说明，看看现在有没有值得处理或提醒的事。
**例子：每隔 30 分钟，看看今天有没有快到期的作业。** 假设已经配置了这个检查间隔，并在 `HEARTBEAT.md` 里写好：“查看 todo.md，发现两小时内到期、还没完成的作业就提醒我；没有要提醒的就保持安静。”

```text
10:00，定时器触发检查 → 助手读取清单，发现没有快到期的作业 → 本次不发提醒
10:30，再次触发检查 → 发现有一项作业 12:00 截止、还没完成 → 提醒用户
```

这里“隔多久检查一次”由代码和配置控制；“查完有没有值得提醒的事”由助手按检查说明处理。要把提醒发给用户，还需配好发送目标；不是每次检查都发一条“我还活着”。

**Webhook 的做法，是写一个 HTTP 接口。** 别的程序向这个地址发请求，OpenClaw 检查凭据和内容，再按配置投递事件或启动任务。
**例子：项目的自动测试失败了，让助手看看原因。** 你先在测试流水线中配好：测试失败时，按 OpenClaw 任务 Webhook 接口要求的格式，带上凭据，发送项目名、错误摘要和可访问的日志位置；OpenClaw 也提前启用这个入口。

```text
测试流水线发现失败
    → 向 OpenClaw 的任务 Webhook 发 HTTP 请求：“项目 A 测试失败，日志在……”
    → OpenClaw 检查凭据和请求内容，按配置发起任务
    → 助手读取可访问的日志，分析报错，再把结果发到配置好的位置
```

**不是 OpenClaw 一直盯着测试平台，而是外部程序发现出事了，主动过来通知它**。日志访问和回复位置都要事先安排好。

这里的任务 Webhook，是“外部程序通知助手做事”；01 中 WeChat 的 Webhook，是“聊天平台推送新消息”。两者都用 HTTP 回调，但用途不同。

**其他内部触发的做法，是某段代码完成工作后，调用后续处理，或者放入一条待处理事件。**
**例子：助手刚才在后台跑的测试结束了，接着汇报结果。** 假设这次后台命令已经启用完成通知，并且产生了测试输出。

```text
助手启动后台测试 → 测试跑了几分钟，进程结束
    → OpenClaw 的进程管理代码记录退出状态和输出，放入完成事件并请求唤醒
    → 助手后续处理时接到完成信息，告诉用户“测试通过了”或分析失败原因
```

这里没有外部程序来发 HTTP 请求，也不用用户再问一句“跑完了吗”。是 OpenClaw 内部发现自己管理的任务结束，再触发后续处理。

**把这四种情况放在一起，就容易区分了：**

| 方式 | 谁来触发 | 这个例子在等什么 |
| --- | --- | --- |
| cron | 定时调度代码 | 到每天 9:00，固定执行一次待办整理 |
| heartbeat | 周期检查代码 | 又过了 30 分钟，检查有没有需要提醒的事 |
| Webhook | 外部程序发 HTTP 请求 | 测试平台发现失败，主动通知 OpenClaw |
| 其他内部触发 | OpenClaw 内部的处理代码 | 自己管理的后台测试结束，继续处理结果 |

所以，“谁来启动任务”有几种办法，后面仍然可以使用已有的助手执行代码。

**比如“每天早上 9 点整理待办”：**

| 到哪一步 | 谁来做，具体做什么 |
| --- | --- |
| 保存任务 | 程序记下时间规则，以及“读取 todo.md 并整理待办”这个任务 |
| 现在是 8:59 | 调度代码算出下一次是 9:00，安排定时唤醒 |
| 到了 9:00 | 调度代码发现该执行了，把任务交给助手 |
| 整理文件内容 | 助手运行时调用模型和读取工具，找出没完成的事 |

“现在到没到 9 点”由代码判断；“这些待办哪件更急”才交给模型结合内容判断。

如果任务最初是你用自然语言要求创建的，模型可以协助填好定时任务参数。任务保存后，每次按时触发由调度代码负责。

源码入口：[cron 定时处理](/source/?file=b936c2a2e80adbbdff.ts)、[heartbeat 周期检查](/source/?file=03ef7fa0ca8850d012.ts)、[任务 Webhook 处理](/source/?file=fa9f8e7e281e2a4034.ts)、[后台进程完成通知](/source/?file=713fefa022bb211246.ts)。

#### 04 Gateway control plane（控制面）：长期在线的后台服务，管接入、权限和运行

**功能是什么：把 OpenClaw 作为一个长期在线的服务运行起来。谁能连进来、连上后能做什么、请求交给哪段代码、任务状态怎样通知客户端，都是它要组织和管理的事。**

**实现方式：普通的服务器、认证和接口分发代码；Gateway 处理请求这一步不靠大模型选函数。**

**先把“Gateway”想成你电脑上一直开着的 OpenClaw 后台服务。** 你关掉控制网页，它仍然可以接收已经接好的渠道消息、启动任务、把结果发回去。前提是 Gateway 进程和相应渠道账户还在正常运行。

“控制面”这个名字可以先理解成：**给控制界面、CLI 等提供一套管理和操作助手的接口。** 同时，整个 Gateway 进程还会启动渠道插件、定时任务等配套服务。

| 它具体管什么 | 说得直白一点 | 例子 |
| --- | --- | --- |
| **让服务一直在线** | 启动网络入口，维护客户端连接和后台服务 | 你没打开网页，WeChat Bot 仍可以接消息 |
| **检查谁能连接** | 按配置验证 Token、密码等身份凭据；相关设备接入还可能涉及配对 | 一个控制客户端拿错 Token，连接认证不通过 |
| **检查能调用什么接口** | 根据连接的角色和已获准的权限范围，判断是否允许本次操作 | 只获准查看的客户端，不能提交新任务或改配置 |
| **把操作交给对应代码** | 看请求的 method，找到处理函数 | chat.history 查历史，chat.send 提交聊天请求 |
| **管理运行与通知状态** | 通过相关处理代码受理任务、提供取消入口，并把进度和结果事件送给相应客户端 | 网页显示“正在调用工具”，用户也可以请求停止 |
| **组织渠道和自动任务** | 启动并管理渠道账户任务、定时调度等服务 | WeChat 插件持续接消息，Cron 到点发起任务 |

**所以，权限控制确实是它的一项职责，但要分清控制的是哪一层。**

| 你问的是哪种“能不能” | 主要在哪里检查 |
| --- | --- |
| 这个网页、CLI 或设备能不能连接后台？ | Gateway 的连接认证，以及适用的设备配对等检查 |
| 连上以后，能不能查历史、发任务、改配置？ | Gateway 的角色和接口权限检查 |
| 这个 WeChat 或微信用户能不能让助手干活？ | 相应渠道的接入策略，例如配对、允许名单、群规则；插件由 Gateway 进程管理 |
| 助手接到任务后，能不能读某个文件、执行某条命令？ | 工具策略、沙箱与文件访问限制、命令执行审批等执行层机制，不能只看 Gateway 是否允许连接 |

**能连上后台，不等于能调用所有接口；能提交任务，也不等于助手能随意执行所有工具。** 这些检查在各自的处理位置落实。Gateway 也提供执行审批等管理接口，但具体工具仍要按执行层规则运行。

OpenClaw 启动 Gateway 后，服务监听网络请求，也管理已经连上的客户端。

控制界面等客户端可以通过 WebSocket 保持连接。这样客户端能发操作请求，服务也能主动推送运行状态。

程序先检查连接使用的凭据和允许的操作，再处理具体请求。不同入口的检查代码不完全一样。

客户端发来的操作请求，可以先记住三个信息：

- **id**：这次请求的编号，回消息时用它对上是哪一次请求。
- **method**：想做什么，比如提交聊天消息。
- **params**：做这件事需要哪些参数。

服务端根据 `method` 找到对应的处理函数，检查参数，再调用它。比如聊天请求会进入聊天处理代码。

源码把通信消息分成 `req`、`res`、`event` 三类：**发请求、回响应、推状态。**

一项任务可能要跑很久，所以接口回了“已接收”，和助手最后“已经做完”是两个时间点。运行中的变化可以继续用事件通知客户端。

Gateway 负责把服务和调用关系接起来；读取 todo.md 的动作还是交给后面的工具执行。

**拿“只允许查看的控制客户端”举个例子：** 假设它连接认证已通过，角色是 operator，获准的权限范围只有 `operator.read`。

```text
请求 chat.history：查看已有会话的历史
    → 接口权限检查允许，再由处理函数检查参数等条件并读取记录

请求 chat.send：提交一条新任务
    → 需要 operator.write，权限不够，返回 missing scope，不启动这次任务

请求 channels.start：启动渠道账户
    → 属于管理操作，需要 operator.admin，也不允许
```

这里的 `operator.read` 指“允许调用相应的查看接口”，不是“允许模型读取电脑上的所有文件”。这些权限要经过服务端认可，不是客户端自己声明一下就一定获得。

**比如网页想查看之前的聊天记录，发来一条请求：**

```json
{
  "type": "req",
  "id": "r1",
  "method": "chat.history",
  "params": {
    "sessionKey": "agent:daily:WeChat:direct:123"
  }
}
```

程序查到 `chat.history` 对应的处理函数，检查参数，读取会话记录，再用同一个 `id: "r1"` 返回响应。

这整个查询不用问模型。若收到的是提交新任务的请求，则进入对应处理代码，后面才可能开始模型调用。

源码入口：[Gateway 服务启动](/source/?file=7f336200ac1c1c8427.ts)、[连接认证](/source/?file=2073d9311e5f34b7ec.ts)、[接口分发与权限检查](/source/?file=8dc7ed3b0966626d10.ts)、[接口所需权限](/source/?file=57605cf6f5271be303.ts)、[三类通信消息的格式](/source/?file=be263054019f6bb2c6.ts)、[聊天请求的处理](/source/?file=0814e4cc709ffda64f.ts)。

### 4.4 第二段：找助手，排顺序，准备材料

![路由与准备](/resources/openclaw/assets/01-architecture-02-preparation.png)

| 图里这块负责干啥 | 这个例子里做了什么 |
| --- | --- |
| **05 Routing，路由**<br>按配置决定交给哪个助手、接上哪段聊天记录，同时保留回复位置。 | 假设配置让这个 WeChat 聊天使用你的日常助手，就交给它处理。 |
| **06 Queue / Session lane，排队和会话通道**<br>管任务的运行顺序，也管同时跑多少任务。 | 如果上一条任务还没处理完，就按当前设置安排这一条；这里先按排队理解。 |
| **07 Agent run preparation，运行前的准备**<br>把模型、聊天记录、工作目录、规则和工具准备好。 | 找到放着 todo.md 的工作目录，选好模型，准备读取文件的工具。 |

**Routing 图里的三个名字：**

- **agentId**：用哪个助手。
- **sessionKey**：接哪一段聊天记录。
- **delivery context**：最后往哪里回复。

一个助手可以有很多段聊天。聊天记录怎么分开，要看配置。

**排队也分两件事：**

- **Session lane**：管同一段聊天里的任务怎么接着做。
- **Global lane**：管这一类任务总共能同时跑多少个。

**07 这一大框，再逐个拆开看：**

- **History，聊天记录**：把之前聊过的内容接上，方便继续说。这次直接给了文件名，不靠历史也能理解。
- **Workspace，工作目录**：助手在哪个文件夹里干活。本例的 todo.md 就放在这里。
- **Bootstrap，启动准备**：开始前先准备工作目录里的说明，比如 AGENTS.md 写了哪些要求。
- **Skills，技能**：提供某类任务的做法。比如装一个整理周报的技能，遇到相关任务时可以读它的说明。本例读待办不一定需要技能。
- **Memory，长期记忆**：把值得长期保留的信息存下来，需要时再找出来。比如你长期的工作习惯；本例不用也能完成。
- **Policy，规则和限制**：决定能用什么工具、哪些操作受限制。本例要有读取这个文件的权限。
- **System Prompt，系统提示词**：把助手的身份、工作要求和工具用法等说明交给模型。
- **模型和工具**：选哪个模型来判断，准备哪些工具来实际做事。

这里说“准备好”，不等于把整个文件夹都塞给模型。

**todo.md 里究竟写了什么，后面还得调用工具去读。**

#### 05 Routing（路由）：决定消息交给哪个助手、接哪段聊天记录

**先看图：用“课程 Bot 收到实验群消息”这个例子，看看路由怎样选中 coding。**

![Routing 匹配过程：实验群消息命中具体聊天对象规则，交给 coding；未匹配时才继续看账号、渠道和默认助手](/resources/openclaw/assets/01-routing-process.png)

蓝色箭头表示这条消息实际走的路：**WeChat 的 class-bot 收到实验群 -10001 的消息 → 命中具体群绑定 → 交给 coding。** 到这里就选好了，不再往下找 teacher。

灰色箭头表示其他消息没匹配上时，怎样继续往下找。图中只画这份配置涉及的几层；它们的先后由代码规定，不是看谁写在配置数组的第一行。

**功能是什么：一个系统里可以有多个助手和多段聊天。路由根据消息来源和配置，选定负责的助手及会话；回复位置也会在入口处理中保留下来。**

**实现方式：直接按配置匹配。这里的入口路由不调用大模型，也不根据消息语义猜应该交给谁。**

先在配置里写好规则，比如“这个 WeChat 聊天交给日常助手”。代码收到消息后，拿渠道、账号、聊天对象等信息去匹配规则。

源码按规则的匹配层次查找。可以先理解为：优先找更具体的聊天对象规则，再看账号、渠道等规则；没有匹配时，使用默认助手。

选好助手后，再按会话设置生成 `sessionKey`。后面用这个键找到相应的会话记录。

**为什么这一步提前由人设置，而不是每次让大模型决定？**

因为这里要先确定：**这是谁的消息，应该接上哪套助手、哪段聊天记录和哪个工作环境。** 确定以后，才让选中的助手处理消息内容。

从这套实现看，这样分工有几个直接的好处：

| 为什么这样做 | 放到具体使用里看 |
| --- | --- |
| **使用安排由人决定** | 老师规定课程 Bot 用课程助手，个人 Bot 用日常助手。这是使用者的安排，仅凭一句“帮我看看”并不能推断出来。 |
| **连续聊天能稳定接上** | 你刚让日常助手看 todo.md，接着说“写个脚本帮我整理”。如果只按“脚本”这个词重新选助手，可能换到另一套会话和工作目录，接不上刚才的事。 |
| **先把模型要用的环境确定下来** | 要调用哪一个模型、带哪段历史、使用哪些工具，本来就要先确定。路由先按配置选好助手，后面才能准备这套材料。 |
| **这一步不用再增加一次模型请求** | 渠道、账号和聊天编号已经是明确的数据，代码比较一下就能匹配。每条消息先问一次模型，会多一次等待和调用开销。 |
| **结果容易解释，也容易查错** | 为什么这条消息进了 coding？查看它匹配了哪条绑定就知道。同样的入口信息和配置，可以复现同样的路由结果。 |

**比如，同一段聊天里连续说两句话：**

```text
第一句：“帮我看看 todo.md 里还有什么没做。”
第二句：“写个 Python 脚本，帮我把这些事项分组。”

配置匹配：两句都来自同一个私聊 → 仍交给 daily
接续记录：daily 看得到刚才整理的事项
模型处理：结合前面的内容，判断怎样编写脚本
```

“出现 Python 就换到 coding”需要另外设计按内容分类或转交任务的机制。它可能有用，但要同时考虑哪些上下文一起带过去、允许使用什么能力，以及分类不确定时怎么办。

因此，这里的分工是：**人提前决定助手和入口的对应关系，代码执行匹配，模型处理交给它的具体任务。**

配置选中了哪个助手，也会影响后面使用哪套工作环境。不过，路由本身不等于权限检查，文件和工具能不能访问，仍由对应的限制来落实。

人工设置也不代表必须逐字手写配置。可以让 AI 帮忙生成配置；保存后，消息仍按这些明确的规则分发，不是每次临时让模型重新决定。

**看一份具体配置。** 假设配置了两个助手：`daily` 管日常事务，`coding` 负责代码。私聊对端编号 `123`、`456` 是教学示例。

下面使用本课程版本的配置字段，只摘出助手、路由绑定和私聊划分这几项：

```json
{
  "agents": {
    "list": [
      { "id": "daily", "default": true },
      { "id": "coding" }
    ]
  },
  "bindings": [
    {
      "agentId": "daily",
      "match": {
        "channel": "WeChat",
        "peer": { "kind": "direct", "id": "123" }
      }
    },
    {
      "agentId": "coding",
      "match": {
        "channel": "WeChat",
        "peer": { "kind": "direct", "id": "456" }
      }
    }
  ],
  "session": {
    "dmScope": "per-channel-peer"
  }
}
```

**可以把它读成三句话：WeChat 私聊 `123` 交给 `daily`，私聊 `456` 交给 `coding`；没匹配上就用默认助手 `daily`。**

**现在拿几条消息去匹配：**

| 来的消息 | 配置匹配结果 |
| --- | --- |
| 私聊 `123`：“看看 todo.md” | 匹配第一条绑定，交给 `daily` |
| 私聊 `123`：“帮我写一个 Python 函数” | 仍匹配第一条绑定，还是交给 `daily`；正文变了，入口绑定没变 |
| 私聊 `456`：“看看 todo.md” | 匹配第二条绑定，交给 `coding` |
| 没有单独绑定的私聊 `789` | 使用默认助手 `daily` |

程序做的事情可以简化成：

```text
取出 channel 和 peer 等入口信息
    ↓
按匹配层次查 bindings，找到对应 agentId；没有就选默认助手
    ↓
按 agentId、渠道、对端和 session 设置生成 sessionKey
```

按上面的 `per-channel-peer` 设置，私聊 `123` 得到的会话键是 `agent:daily:WeChat:direct:123`。下一条同来源消息会再算出相同的键，用它接续对应记录。

想让不同用户分开聊，就配置相应的私聊隔离方式，让他们得到不同的会话键。

源码也支持把部分私聊接到同一段主会话，所以不能只凭“来了一个新用户”就认为它一定新建会话。

**这里主要靠配置匹配和生成标识。** 这条普通入口消息先交给哪个助手，不是临时让模型猜的。

如果想“看出是编程问题就转给编程助手”，还要另外设计内容分类或任务转交逻辑，不能仅凭这份绑定配置得到这种效果。

**再看一个稍复杂的例子：同一个人有两个 Bot，课程群还要单独处理。**

假设老师已经接好了两个 WeChat Bot 账号：

- `class-bot`：给课程使用，普通消息交给课程助手 `teacher`。
- `personal-bot`：个人使用，普通消息交给日常助手 `daily`。
- 课程 Bot 所在的实验群 `-10001`：单独交给编程助手 `coding`。

这里的 `accountId` 是 OpenClaw 里给 **Bot 账号**起的标识；`peer.id` 是对面的私聊或群编号，两者不要混在一起。

**这些分配规则由使用者或管理员提前写入配置。** 程序开发者则在源码里规定匹配层次，例如先看具体聊天对象，再看账号和渠道。规则保存后，收到消息就由普通代码匹配。

下面仍只摘相关配置，Bot 的 Token 和连接设置省略：

```json
{
  "agents": {
    "list": [
      { "id": "daily", "default": true },
      { "id": "teacher" },
      { "id": "coding" }
    ]
  },
  "bindings": [
    {
      "agentId": "teacher",
      "match": { "channel": "WeChat", "accountId": "class-bot" }
    },
    {
      "agentId": "coding",
      "match": {
        "channel": "WeChat",
        "accountId": "class-bot",
        "peer": { "kind": "group", "id": "-10001" }
      }
    },
    {
      "agentId": "daily",
      "match": { "channel": "WeChat", "accountId": "*" }
    }
  ],
  "session": {
    "dmScope": "per-account-channel-peer"
  }
}
```

这三条绑定读起来就是：课程 Bot 通常用 `teacher`；但它收到实验群的消息时用 `coding`；其他 WeChat 账号收到的消息用 `daily`。

| 消息从哪里来 | 会遇到哪些规则 | 最后交给谁 |
| --- | --- | --- |
| `class-bot`，实验群 `-10001`：“帮我看看代码” | 既符合课程账号规则，也符合具体群规则，还符合 WeChat 通用规则 | `coding`，具体群规则优先 |
| `class-bot`，实验群 `-10001`：“今天的待办有哪些” | 来源没有变，仍符合这几条规则 | 还是 `coding`，不会因为正文像日常问题就换助手 |
| `class-bot`，学生私聊 `123`：“这次作业什么时候交” | 没有匹配具体群，符合课程账号规则和 WeChat 通用规则 | `teacher`，账号规则优先 |
| `personal-bot`，同一位学生私聊 `123`：“整理 todo.md” | 不符合课程账号和实验群规则，只符合 WeChat 通用规则 | `daily` |
| `personal-bot`，也收到群 `-10001` 的消息 | 群编号虽然一样，但不符合实验群绑定里指定的 `class-bot` | `daily`，不能只比群编号就选 `coding` |
| 另一个已经接入的 Slack 渠道发来消息，且没有其他绑定 | 三条 WeChat 规则都不匹配 | 默认助手 `daily` |

**把第一行真的匹配一次：**

```text
入口信息：channel = WeChat，accountId = class-bot，peer = 群 -10001
    ↓
先检查具体聊天对象这一层
    ↓
找到第二条：渠道、Bot 账号、群类型和群编号都符合
    ↓
选中 coding，不再退到 teacher 的账号规则
```

虽然配置里把 `teacher` 的账号规则写在前面，这条具体群规则仍然先匹配。**程序先按规则层次查找，不是把整个数组从头扫到尾，碰到第一条就直接选。** 同一层里出现多条都符合的绑定时，再按该层的配置顺序取首个匹配项。

这段只展示具体群、账号、渠道和默认助手几种情况。源码还处理父会话、通配聊天对象、Discord 服务器与角色等匹配层次。

**选助手之后，还得分清聊天记录。** 上面的 `per-account-channel-peer` 表示私聊记录按 Bot 账号、渠道和对端划分：

```text
学生 123 找 class-bot：
agent:teacher:WeChat:class-bot:direct:123

学生 123 找 personal-bot：
agent:daily:WeChat:personal-bot:direct:123
```

这两段记录分开接续。即使以后两个 Bot 都绑定到同一个助手，这项私聊设置仍会把 Bot 账号放进会话键里。

源码入口：[路由选择](/source/?file=d458713855a0557332.ts)、[会话键的生成](/source/?file=35e532246be3d8273c.ts)。
**选好助手以后，也可以让它找其他助手一起做事。** 例如主助手把“查消息入口”和“查工具调用”分给两个子助手，最后自己汇总。这个过程放到[第 15 讲：多智能体系统原理](/openclaw/chapter-15)展开。

#### 06 Queue / Session lane（队列与会话通道）：先排自己的队，再等全局空位

**功能是什么：安排任务什么时候能开始。同一段会话按顺序处理，整个系统也不能一下子启动太多任务。**

**实现方式：普通的队列和计数代码，不需要大模型决定谁先运行。**

**这次用四个人，各有 2、3、3、2 条任务，全局同时最多运行 2 条。下面详细展示的前五轮，全局等待队列里一直有两个人。**

| 谁的会话 | 有几条任务 | 要按什么顺序做 |
| --- | --- | --- |
| 小林 | 2 条 | 林1：整理待办 → 林2：列出今天要做的事 |
| 小王 | 3 条 | 王1：读课堂笔记 → 王2：列出重点 → 王3：出几道练习题 |
| 小陈 | 3 条 | 陈1：总结文章 → 陈2：出几个问题 → 陈3：整理参考答案 |
| 小李 | 2 条 | 李1：检查作业清单 → 李2：整理缺交名单 |

**只有两条规则：**

- **每段会话一次只放行 1 条**：自己的前一条结束，才轮到下一条。已经在全局排队的那条也算放行了，后面的先别出来。
- **全局最多同时运行 2 条**：四个人共用两个运行位置，没有空位就进全局等待队列。

**“全局 2”限制的是正在运行的数量，不是最多只能有两个人排队。** 本例选四个人，是为了同时看到两个在运行、两个在全局等待；人更多，等待队列也可以更长。

这个运行上限可通过 `agents.defaults.maxConcurrent` 调整。个人有几条任务，不影响谁先得到空位。

假设十条消息都已分别形成任务，各人的第一条按林1、王1、陈1、李1的顺序送来。每一轮是某个任务完成、队列调整后的快照。

**图从左往右读：个人等待队列 → 全局等待队列 → 真正运行的位置。**

蓝色是还没轮到的个人任务，橙色是已经轮到、正在等全局空位的任务，绿色是运行中的任务，灰色是已完成任务。个人队列从左往右排，全局等待队列从上往下排。

##### 准备：四个人先各排自己的队

![准备：四个人的任务数分别为2、3、3、2，调度尚未开始](/resources/openclaw/assets/01-queue-two-waiters-00.png)

十条任务都还在各自的个人队列里，全局两个运行位置空着。

##### 第 1 轮：林1、王1运行，陈1、李1在全局等

![第1轮：林1王1运行，全局等待陈1和李1两个人](/resources/openclaw/assets/01-queue-two-waiters-01.png)

林1、王1先占两个运行位置。陈1、李1也都轮到了，但位置满了，只能排进全局等待队列。

**正在运行：林1、王1。全局等待：陈1 → 李1，共两个人。**

林2、王2等后续任务先留在个人队列里，不能越过自己前面的任务。

##### 第 2 轮：林1完成，陈1补位，林2排到队尾

![第2轮：陈1王1运行，全局等待李1和林2两个人](/resources/openclaw/assets/01-queue-two-waiters-02.png)

1. 林1完成，空出一个运行位置。
2. 全局队首是陈1，让陈1先进去运行。
3. 小林轮到林2，把林2排到全局队尾，排在李1后面。

**正在运行：陈1、王1。全局等待：李1 → 林2，仍是两个人。**

这次补进去一个陈1，又新来一个林2，所以全局等待人数还是 2。林1刚用过的位置，也不会直接留给林2。

##### 第 3 轮：王1完成，李1补位，王2排到队尾

![第3轮：陈1李1运行，全局等待林2和王2两个人](/resources/openclaw/assets/01-queue-two-waiters-03.png)

王1完成，队首李1先开始运行。小王的下一条王2再送出来，排到林2后面；王3继续留在小王的个人队列里。

**正在运行：陈1、李1。全局等待：林2 → 王2，还是两个人。**

##### 第 4 轮：陈1完成，林2补位，陈2排到队尾

![第4轮：林2李1运行，全局等待王2和陈2两个人](/resources/openclaw/assets/01-queue-two-waiters-04.png)

陈1完成，队首林2获得空位。小陈这时才放行陈2，把它排到王2后面；陈3还得继续等陈2完成。

**正在运行：林2、李1。全局等待：王2 → 陈2，还是两个人。**

##### 第 5 轮：李1完成，王2补位，李2排到队尾

![第5轮：林2王2运行，全局等待陈2和李2两个人](/resources/openclaw/assets/01-queue-two-waiters-05.png)

李1完成，队首王2开始运行。小李放行自己的李2，把它排到陈2后面。

**正在运行：林2、王2。全局等待：陈2 → 李2，还是两个人。**

这时王3、陈3还在个人队列里。它们和陈2、李2等的东西不同：**王3、陈3在等自己的前一条完成；陈2、李2已经轮到，只是在等全局空位。**

##### 后面照这个顺序处理，直到全部做完

从第 5 轮继续，假设剩下的任务按林2、王2、陈2、李2、王3、陈3的顺序完成。每完成一条，就让全局队首补位，再放行这个人自己的下一条。

后续任务越来越少，全局等待队列也会逐渐变短。下面直接跳到最终状态，省略中间几次补位。

![最终状态：十条任务全部完成，所有等待队列和运行位置都已清空](/resources/openclaw/assets/01-queue-two-waiters-06.png)

**每轮就看三件事：**

1. 谁完成了，哪个全局位置空出来？
2. 全局队首是谁，让它先补位。
3. 刚完成任务的那个人，还有下一条吗？有就放行下一条，再去排全局队尾。

代码用 `Map` 找到通道，用数组保存等待任务，并记录运行数量。**每个通道内部按入队顺序取任务，没有谁因为任务多就能插队。** 这里的入队顺序要分别看：王3虽然早就收到，也要先等王2完成，才能进入全局队列。

这里用人名表示个人队列，是因为每个人各用一段会话。源码实际按 **会话** 建通道；同一个人如果使用不同会话，也可以有不同的队列。

源码入口：[运行队列的实现](/source/?file=fe892bcf019302f8c2.ts)、[先会话通道、再全局通道](/source/?file=2404b063c2e804b099.ts)、[设置全局并发数量](/source/?file=b25cc42d767cc0bf37.ts)。

#### 07 Agent run preparation（运行准备）：把助手这次要用的东西备齐

**功能是什么：选好模型、工作目录和工具，准备需要的聊天记录与工作说明，让助手在合适的环境里开始做事。**

**实现方式：本节说的基础准备主要由代码读配置、读记录、筛选工具来完成。运行中的某些上下文压缩等功能还可能另行调用模型。**

代码先确定工作目录、模型和账号凭据，再读需要的聊天历史、工作区说明，准备这次可用的工具。

有些资料直接放进模型输入，有些只给出简介和位置，需要时再读。工具除了名称和参数说明，还要准备真正执行它的函数。

最后把这些东西交给 Pi 会话，再提交用户的任务。

本例就是：**模型选好了，工作目录确定了，读取工具装好了，再让 Pi 处理“看看 todo.md”。**

**把准备结果展开，就像这张清单：**

```text
从助手配置取到：daily 的工作目录和模型设置
从会话记录取到：这段聊天适用的历史
从工作区取到：需要的 AGENTS.md 等说明
从工具配置准备：read 工具的名称、参数说明和执行函数
本次用户输入：帮我看看 todo.md 里还有哪些事没做
```

代码把这些材料交给 Pi。`todo.md` 的当前内容还没读，不会因为准备好了工作目录就自动知道文件里写了什么。

后面重点看：材料怎么选、怎样组成上下文、技能和长期资料怎么用、输入太长时怎么处理。

源码入口：[一次运行前后的准备](/source/?file=4c2d09aeeb74b60140.ts)。

### 4.5 第三段：让模型和工具把事做完

![Pi 执行](/resources/openclaw/assets/01-architecture-03-execution.png)

| 图里这块负责干啥 | 这个例子里做了什么 |
| --- | --- |
| **08 Pi AgentSession**<br>管这次会话怎么运行，记下消息、状态和结果。OpenClaw 把它作为组件放在自己的程序里用。 | 接到“看看 todo.md”的任务，用前面准备好的模型和工具开始处理。 |
| **09 pi-agent-core Agent Loop**<br>先问模型；需要工具就调用工具；拿到结果再问模型，直到这轮处理结束。 | 先让模型判断怎么做，再把读到的文件内容交回模型。 |
| **10 pi-ai Model/API adapter**<br>负责和模型服务通信，把请求发过去，再把模型输出接回来。 | 第一次收到模型提出的读文件请求，后面再收到整理好的待办。 |
| **11 Tool execution**<br>真的执行工具。读文件、运行命令、访问服务，都由具体工具去做。 | 读取 todo.md，把文件中的三条事项交回来。 |

**这一段实际怎么走？一行一步：**

1. 先问模型：“用户要你整理 todo.md，接下来怎么做？”
2. 模型提出：“调用读取工具，读一下 todo.md。”
3. 程序真的去读文件，拿到上面那三条事项。
4. 把文件内容交回模型：“文件读到了，请继续。”
5. 模型看出“下载课件”已经完成，把“交作业”排在“整理笔记”前面。
6. 模型生成回答，这轮任务结束。

这是本例的一种简单走法。复杂任务可能要来回很多次。

**为什么要有 Agent Loop？**

第一次问模型时，它还没看到文件。

读完文件后，还要让它根据文件内容继续处理。

Agent Loop 就负责把这几步接起来。

**工具到底是谁调用的？**

模型提出“我要读这个文件”，程序调用工具去读，工具把结果返回。

**再看工具下面的几个词：**

- **Policy**：这次能用哪些工具。
- **Sandbox**：工具是否在隔离的环境里运行，能看到哪些文件。
- **Runtime permission**：这次具体操作能不能执行，是否需要审批。

本例假设读取工具能看到 todo.md，也允许读取它。

#### 08 Pi AgentSession（会话）：管一轮任务怎么运行、记录和继续

**功能是什么：把任务提交、运行状态、消息和记录组织在一个会话里。做完这一轮之后，下一轮还可以接着相应记录继续。**

**实现方式：普通的对象和会话管理代码。会话会启动模型调用，但“保存状态、提交任务、接续记录”这些管理动作由程序完成。**

OpenClaw 通过 Pi 的 `createAgentSession()` 创建会话，把模型、工具、记录管理等配置交进去，再通过 `prompt()` 提交任务。

会话对象持有运行需要的状态，并提供提交任务、监听事件和中止等操作。历史记录由相应的记录管理能力保存和接续。

本例中，用户的要求、工具读回的内容、助手的回答，会进入相应的消息和记录处理流程。

**比如一轮任务的记录会依次增加：**

```text
用户消息：帮我看看 todo.md
助手消息：提出读取 todo.md 的工具调用
工具结果：读到三条事项
助手消息：还有交作业、整理笔记两件事没做
```

记录管理代码保存这些内容。模型负责生成其中的助手输出，记录本身由程序维护。

后面重点看：`AgentSession` 怎样组织运行，聊天记录怎样保存，以及下一次怎样接着用。

#### 09 Agent Loop（Agent 循环）：让模型和工具来回配合，完成用户这一次请求
![Agent Loop 流程：用户只发一次请求，模型和工具在内部多轮往返，完成后返回回答](/resources/openclaw/assets/01-agent-loop-process.png)

**顺着回环箭头看：用户只提一次请求，中间却可以多次调用模型、多次执行工具。图中的次数只是例子，实际要来回几次，取决于任务需要。**

**功能是什么：用户只发出一个请求，助手为了把这件事做完，可能不止调用一次大模型，也不止调用一次工具。Agent Loop 就是把“调用模型 → 执行工具 → 把结果交回模型”这一轮一轮接起来，直到完成这次请求、给出回答。整个过程中，用户不需要每一步都再说一句“继续”。**

**实现方式：循环由普通代码控制；下一步要做什么，由模型结合当前输入给出文字或工具调用请求。**

**先说清它运行多久：一次运行可以调用模型很多次；没有后续工作时就结束。它不会一直停在里面，等用户下一次输入。**

最简单的思路就是：**请求模型 → 检查输出 → 执行工具 → 加入工具结果 → 再请求模型。**

代码保存本轮消息。模型输出里如果有工具调用，就找到相应工具执行，把结果作为一条工具结果消息加入。

下一次请求模型时，带上更新后的消息，让模型看到刚才的执行结果。

本例中，第一次模型提出读文件，下一次看到了文件内容，就可以整理待办。没有需要继续的动作时，这轮循环结束；报错和取消也有相应的退出处理。

**用一次循环分清两边的工作：**

| 模型输出了什么 | 运行代码接着做什么 |
| --- | --- |
| 工具调用：`read`，路径 `todo.md` | 根据调用类型找到工具，执行，再加入工具结果 |
| 读过文件后，输出排好的待办，本轮也没有其他继续条件 | 收好助手回答，结束这轮处理 |

代码会检查输出里的工具调用类型和参数，不是让另一个模型再猜“这段回答是不是想读文件”。

**“一次模型回答”“一次 Agent 运行”“一直能聊天的应用”，是三个不同的范围。**

| 说的是哪一层 | 什么时候结束 | 谁在等下一条用户消息 |
| --- | --- | --- |
| 一次模型请求 | 模型把这一次输出返回完，包括可能提出的工具调用 | 模型请求本身不会留着等你再说一句 |
| 一次 Agent Loop 运行 | 把本次工具往返和已取到的补充任务处理完，按结束条件退出 | Loop 不负责一直监听新的用户输入 |
| Pi 的交互界面，或 OpenClaw 的消息服务 | 应用可以继续保持运行，聊天记录也可以保留 | 外层界面或服务接收新消息，再交给会话和 Agent 处理 |

**例子一：读待办，一次运行里可以问模型两次。**

```text
用户发来：“看看 todo.md”
    ↓ 外层提交任务，开始第 1 次 Agent 运行
第 1 次模型请求：模型提出读取 todo.md
程序执行读取工具，把结果放回消息里
第 2 次模型请求：模型根据文件内容给出待办列表
没有新的工具调用，也没有排队的补充消息
    ↓
发出 agent_end，第 1 次运行结束

过一会儿，用户又发：“把第二项展开讲讲”
    ↓ 外层收到新消息，再次提交任务
开始第 2 次 Agent 运行，可以带上之前的聊天记录
```

所以，看起来是一段连续聊天，底下可以是多次先后启动、先后结束的运行；不需要让同一个 Loop 一直不退出。

**例子二：助手反问用户，也不代表 Loop 会在里面等答案。**

```text
用户：“帮我整理一下。”
模型：“你想整理哪个文件？”
没有工具调用，也没有排队的补充消息 → 这次运行结束

用户稍后：“todo.md。”
外层收到这条消息，连着已有记录再发起一次运行
模型这次才根据补充的信息继续处理
```

“等你回答”是聊天界面给人的交互感受。代码上通常是上一轮已经结束，收到答案后再开始下一轮。

**那源码里的两层 `while` 在循环什么？**

Pi 的 `agent-loop.ts` 里，主要处理逻辑在 `runLoop()` 中。下面摘出决定是否继续的关键位置，中间执行过程省略。

内层的条件是：

```ts
while (hasMoreToolCalls || pendingMessages.length > 0) {
  // 请求模型、执行工具、更新消息等过程省略
}
```

这层主要处理模型和工具的往返，以及已经取到的 steering 补充消息。

有正常需要继续处理的工具结果，就再次请求模型；没有工具需要继续，也没有待处理补充消息，就离开内层循环。取消、报错和工具要求提前终止等情况，还会走相应的结束处理。

外层在本来要结束的位置，再查一次 follow-up 队列：

```ts
const followUpMessages = (await config.getFollowUpMessages?.()) || [];
if (followUpMessages.length > 0) {
  pendingMessages = followUpMessages;
  continue;
}

break;
```

离开外层循环后，代码发出结束事件：

```ts
await emit({ type: "agent_end", messages: newMessages });
```

关键就是 **`break`**：没有取到后续消息，就退出，不是继续空转，也不是在这里等用户以后再输入。

`await` 只是等“读取队列”这个回调完成。Pi 的 Agent 给这里提供的是读取并取出已有排队消息的函数；队列为空就返回空数组，不会因此挂起等一个将来才到的用户回答。

**运行中恰好又来了消息，才有接着这次运行处理的可能。**

| 新消息什么时候到、怎样提交 | 接下来怎么处理 |
| --- | --- |
| 当前运行还在进行，外层通过 `steer()` 加入补充消息 | Loop 在相应处理节点取出消息，后续模型请求把它一起考虑 |
| 当前运行还在进行，外层通过 `followUp()` 排入后续消息 | 当前工作本来要结束时，取到这条后续消息，可以留在这次运行里继续处理 |
| 本次运行已经结束，用户才发来下一条 | 外层再次调用 `prompt()` 等入口，发起新运行，并接续适用的历史 |

这里是 Pi 底层 Agent 的队列机制。OpenClaw 自己怎样把平台上的新消息接入运行，还要经过前面 06 讲的消息模式和队列安排。

Pi 的 `Agent.prompt()` 会启动处理；交互界面的输入提交回调负责接用户输入，再交给会话。Loop 结束后，Agent 或会话对象仍可以保留，供下一次提交使用。

源码里还有 `agentLoopContinue()`，意思是从已有上下文发起一次继续处理，也使用同样的结束逻辑；这个名字不表示它会一直等待用户。

另外，在本地这份 Pi 实现中，`agent_end` 发出后还可能要等待事件监听函数收尾，之后 Agent 才真正空闲。这段等待是在等程序处理完成，不是在等用户说话。

源码入口：[Loop 的内外层循环与退出](/source/?file=6adbf9ab77a3572a2f.ts)、[Agent 的 prompt、消息队列与运行收尾](/source/?file=3688aa044ebb960834.ts#L332)、[交互界面接收用户提交](/source/?file=ee2e68c0d7b9d97a7f.ts)。

后面重点看：循环怎样推进，消息怎样变化，什么情况下继续、停止或报错。

#### 10 pi-ai Model/API adapter（模型适配）：把请求发给模型，再接回输出

**功能是什么：让上层能够使用不同的模型服务。它处理各家接口格式的区别，把模型返回的文字和工具调用交回运行层。**

**实现方式：适配层是普通的请求转换和网络通信代码；真正理解任务、生成回答的是所调用的模型。**

代码先根据配置选出模型对应的调用实现，把聊天消息、工具说明等内容转换成那家服务接受的请求。

请求发出后，再把返回的文字和工具调用整理成上层认识的形式。

如果服务逐段返回内容，代码就逐段读取和处理，上层不用等整段回答全生成完才知道有新内容。

本例中，模型提出的“读取 todo.md”会被整理成工具调用信息，交给运行层处理。

**比如模型服务返回了一次读文件的请求，适配层整理后可以读成这样：**

```json
{
  "type": "toolCall",
  "id": "call1",
  "name": "read",
  "arguments": { "path": "todo.md" }
}
```

这里的工具名和参数来自模型输出。适配代码负责把各家接口的返回格式整理成上层认识的表示，不需要再调用模型来做格式翻译。

后面重点看：共同的数据类型、不同 Provider 的请求转换，以及流式输出怎么读取。

#### 11 Tool execution（工具执行）：真正去读文件、运行命令或访问服务

**功能是什么：把模型提出的工具调用变成实际操作，再把成功结果或错误返回。比如真的打开 todo.md，取出里面的内容。**

**实现方式：工具执行是普通代码；本例读哪个文件的请求来自模型，真正打开文件的是读取函数。**

程序提前准备一组工具。每个工具都有名称、说明、参数要求，以及一个实际执行的函数。

模型说要调用读取工具时，运行层按名称找到工具，检查参数，再调用它的执行函数。

本例中，读取工具接到 `todo.md` 的路径，去相应工作目录读取文件，再把内容作为工具结果返回。

读不到文件时，也要把错误交回运行流程。代码还要按配置处理路径范围、沙箱和相应权限。

每次工具调用有自己的编号，工具结果带着对应编号返回，方便知道结果属于哪次调用。

**接着上面的 `call1`，实际处理过程是：**

```text
收到工具调用：name = "read"，path = "todo.md"，id = "call1"
    ↓
找到 read 工具，检查 path 参数及适用的访问限制
    ↓
调用工具的执行函数，用文件读取代码拿到 todo.md 内容
    ↓
把内容作为工具结果交回去，并关联 call1
```

本例的读文件动作不需要模型来执行。工具种类不同，实现也不同：查询服务的工具会发网络请求，有的工具内部也可能调用另一个模型。

后面重点看：工具怎么定义、怎么接入，参数怎么检查，以及结果怎么回到模型。

### 4.6 第四段：把结果发回给你

![事件与回复发送](/resources/openclaw/assets/01-architecture-04-delivery.png)

> 2. 整理课堂笔记——这周完成。

模型写好了回答以后，还要经过发送这一步，你才能在 WeChat 里看到它。

#### 12 Pi events / final assistant message（事件与最终消息）：报进度，给出回答

**功能是什么：把运行过程中发生的事告诉外面，比如工具开始了、工具结束了、又生成了文字；这一轮也会形成最终的助手消息。**

**实现方式：普通的事件对象和监听函数，不需要模型生成“开始了、结束了”这些程序状态。**

Pi 在文字更新、工具开始、工具结束等位置生成事件。事件里带着类型和相关数据。

外层先登记一个监听函数，有事件时就调用它。监听函数根据事件类型，更新状态、收集文字，或者继续通知其他代码。

源码中能看到 `message_update`、`tool_execution_start`、`tool_execution_end`、`agent_end` 等类型。

本例中，“读取工具开始了”和“读取工具返回了三条事项”，分别可以通过对应事件让外面知道。

**比如程序即将调用 read 工具时，发出一条这样的事件：**

```json
{
  "type": "tool_execution_start",
  "toolCallId": "call1",
  "toolName": "read",
  "args": { "path": "todo.md" }
}
```

工具开始运行这个事实，代码本来就知道，所以由代码填字段、发事件。监听函数收到后，就可以更新“正在读文件”的状态。

后面重点看：消息和事件有什么区别，事件怎样传递，以及异步执行时怎样接收和处理它们。

#### 13 OpenClaw event bridge + delivery（事件桥接与发送）：把运行输出接回来，发到用户的聊天里

**功能是什么：接住 Pi 的进度和回答，选出需要展示的内容，整理成渠道接受的格式，再发到正确的聊天或线程里。**

**实现方式：普通的事件处理、文本整理和平台接口调用。上面的模型已经写好待办，发送这一步不需要再问模型该往哪个聊天发。**

OpenClaw 先订阅 Pi 会话。Pi 有事件时，OpenClaw 的处理函数就能接到。

代码按事件类型分别处理：文字更新就收集文字，工具事件就更新状态，产生可回复的内容时再交给回复处理。

有些渠道和配置允许边生成边发，有些会先收集一段或等完整回答。不能来一个字符，就不加区分地调用一次发送接口。

发出去之前，还要做几件具体的事：

- **选内容**：哪些是给用户看的回答，哪些只是内部状态。
- **改格式**：把文字整理成 WeChat 等平台接受的格式。
- **拆长消息**：内容超过渠道限制时，按规则分成几段。
- **找发送位置**：从保存的来源信息里，拿到账号、聊天编号和需要的线程编号。
- **调用发送代码**：交给渠道插件，再由插件调用平台接口，处理返回结果和发送错误。

本例里，代码把两条未完成事项整理好，再用 WeChat Bot 的发送接口发到原聊天。

**把这一步的数据摊开看：**

```text
已生成的回答：“还有两件事没做：1. 交课程作业…… 2. 整理课堂笔记……”
保存的来源：WeChat，日常助手的 Bot 账号，聊天编号 123
    ↓
代码整理文字格式，必要时拆成几段
    ↓
用对应 Bot 账号的发送接口，把文字发给聊天 123
    ↓
检查平台返回的结果：发出去了，还是发送失败
```

聊天编号是前面接消息时保留下来的，不是模型读完回答后推测出来的。若带有话题或线程，还要把相应编号一起带上。

可以把它记成一条线：

```text
Pi 发出事件 → OpenClaw 接住 → 整理回复 → 找到原聊天 → 渠道插件发送
```

会话可能有跨渠道使用的情况，所以不能只随便取一个“最近聊天位置”就发。需要按本次请求保留的来源等信息选择目标。

**12 负责把运行变化报出来，13 负责把合适的内容变成用户实际收到的消息。**

源码入口：[订阅 Pi 事件](/source/?file=46e2683600cbd798f6.ts)、[按事件类型处理](/source/?file=ef0663fc89460d11fb.ts)、[选择回复目标](/source/?file=d49ae3a0102f379103.ts)、[WeChat 发送实现](/guide/unavailable#reference)。

### 4.7 多智能体协作：主助手找帮手，一起完成一个任务

**功能是什么：一个任务比较大时，主助手可以把它拆成几份，交给几个子助手分头做，再把结果整理成一份完整回答。** 用户仍然只需要提一个总任务，不用自己挨个找助手、再手动拼答案。

**实现方式：主助手通过 `sessions_spawn` 创建子会话、交代任务；每个子助手运行自己的 Agent Loop，调用模型和工具，做完把结果交回来。** 主助手拿到所需结果后，再检查、整理和汇总。

![多智能体协作：主助手拆任务，两个子助手分头查源码，结果回传后由主助手汇总](/resources/openclaw/assets/01-multi-agent-collaboration.png)

**举个例子：用户说“帮我分析 OpenClaw 的消息入口和工具调用，整理成一份说明”。**

| 谁来做 | 具体负责什么 | 最后交出什么 |
| --- | --- | --- |
| 主助手 | 先看任务能拆成哪几份，给子助手交代清楚范围和输出要求 | 分工安排；收齐结果后整理完整说明 |
| 子助手 A | 查消息怎么经过 Channel、Gateway、Routing | 消息进入系统的流程、相关源码路径 |
| 子助手 B | 查 Agent Loop 怎么调用工具、怎么接收工具结果 | 模型和工具来回配合的流程、相关源码路径 |

**把过程顺着走一遍：**

1. **先分工。** 主助手判断这两部分可以分开查，给 A、B 各写一份任务说明。用户也可以直接指定“请找两个子助手，一个查入口，一个查工具”。
2. **再启动。** 主助手调用两次 `sessions_spawn`。第一次被接受后，不必等 A 查完，就可以启动 B；有足够并发空位时，两边可以同时做。
3. **各自干活。** A、B 分别在自己的会话里读源码。每个子助手内部也可能多次调用模型、执行多次工具，靠前面 09 的 Agent Loop 完成自己的那份工作。
4. **结果回来。** 框架把完成状态和结果送回主助手。假如 A 先完成，主助手先记下 A 的结果，继续等 B；如果 B 失败，就根据任务需要补做或说明缺了哪部分。
5. **最后汇总。** 两份结果都拿到后，主助手检查有没有遗漏、两边说法能不能接上，再写成用户要的完整说明。

**这里哪些靠模型，哪些靠普通代码？**

| 要做的事 | 谁负责 |
| --- | --- |
| 把任务拆成几份、每份查什么 | 可以由主助手的模型决定，也可以按用户指定的分工来做 |
| 创建子会话、检查允许调用谁、安排排队和运行 | OpenClaw 的普通代码，根据配置执行 |
| 查源码、选择工具、理解结果 | 各个子助手的模型与工具配合完成 |
| 记录完成状态，把结果送回主助手 | OpenClaw 的运行管理和完成通知代码 |
| 把几份材料核对好，整理成完整回答 | 主助手的模型 |

这和 05 的路由发生在不同阶段：**路由先按配置决定“消息交给哪个助手”；选中的助手接到任务后，才可能再找子助手帮忙。** 配置了 daily 和 coding，并不等于它们每次都会一起处理消息。

子助手各有独立会话，但不一定各有隔离的文件目录。不写 `agentId` 时，可以沿用主助手所属的 Agent 配置来创建子会话；要找不同配置的助手，就指定 `agentId`，并配置允许调用的范围。子任务实际能同时跑几个，还受专门的 `subagent` 队列并发上限控制。

源码可以从[创建子助手的工具入口](/source/?file=31b532c623d68cd438.ts)、[启动与限制检查](/source/?file=ab9093a6fa6799a944.ts)、[完成后回传结果](/source/?file=840f0799aef42333e7.ts)这几处看。具体参数和执行流程放到[第 15 讲：多智能体系统原理](/openclaw/chapter-15)展开。

## 5. OpenClaw 和 Pi 各负责什么

**OpenClaw 管前后：接到谁的消息，用哪个助手，准备什么，最后发到哪儿。**

**Pi 管执行：把任务交给模型，需要工具就执行，拿到结果再继续。**

Pi 由 Mario Zechner 开发，既能作为编码助手直接使用，也把核心能力做成了可供其他程序使用的组件。OpenClaw 使用了这些组件。

Pi 里面三个常见的包，先这样记：

- **pi-coding-agent**：提供 AgentSession 等会话能力，也有编码工具和其他配套功能。
- **pi-agent-core**：管模型和工具怎么来回配合。
- **pi-ai**：管怎么调用不同的模型服务。

在本课程使用的 OpenClaw 版本里，Pi 直接放在 OpenClaw 程序内部运行。[本地集成说明](/source/?file=a645c5dd99be5a0dc7.md)
