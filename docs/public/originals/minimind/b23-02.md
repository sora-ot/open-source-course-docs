# 64 · MoE：负载均衡与稀疏计算

<!-- LECTURE-CONTENT-START -->
## 1. MoE 最大的问题：Expert 负载不均衡

假设有 8 个 Expert。

本来希望：

```text
不同 Token 分散到不同 Expert
```

但训练过程中 Router 可能发现：

```text
Expert 3 好像比较好用
```

于是大量 Token 都去：

```text
Expert 3
```

例如：

```text
Token 1 → E3
Token 2 → E3
Token 3 → E3
Token 4 → E3
...
```

最终：

```text
E3：非常拥挤

其他 Expert：几乎没人用
```

这叫：

\[
\boxed{\text{Load Imbalance}}
\]

即：

> 负载不均衡。

---

## 2. 为什么会出现 Expert Collapse？

假设训练早期：

```text
Expert 3 偶然表现稍好
```

于是 Router 更喜欢它：

```text
更多 Token → Expert 3
```

Expert 3 因为收到更多 Token：

```text
获得更多训练
```

于是变得更强。

Router 又会：

```text
更加喜欢 Expert 3
```

形成：

```text
稍微强
 ↓
收到更多 Token
 ↓
训练更多
 ↓
变得更强
 ↓
收到更多 Token
```

最终可能出现：

\[
\boxed{\text{Expert Collapse}}
\]

也就是：

> 大部分 Token 都集中到少数几个 Expert。

---

## 3. 为什么 Expert Collapse 很严重？

第一：

```text
很多 Expert 参数几乎没被使用
```

也就是：

> 参数浪费。

第二：

```text
某些 Expert 过载
```

如果 Expert 分布在不同 GPU：

```text
GPU0 很忙
GPU1 很闲
GPU2 很闲
GPU3 爆满
```

于是整个训练速度取决于最慢的那个 GPU。

所以：

> Expert Collapse 不只是模型问题，也是系统性能问题。

---

## 4. 解决办法：Auxiliary Loss

因此 MoE 通常会增加一个：

\[
\boxed{\text{Auxiliary Loss}}
\]

简称：

```text
Aux Loss
```

它不是用来预测下一个 Token 的。

它主要用来：

\[
\boxed{\text{鼓励 Expert 之间负载更加均衡}}
\]

总 Loss 可能是：

\[
L
=
L_{\text{LM}}
+
\lambda L_{\text{aux}}
\]

其中：

\[
L_{\text{LM}}
\]

是普通语言模型 Cross Entropy。

而：

\[
L_{\text{aux}}
\]

是 MoE 的负载均衡损失。

---

## 5. \(f_i\) 和 \(P_i\) 到底是什么？

一个经典形式是：

\[
\boxed{
L_{\text{aux}}
=
N
\sum_{i=1}^{N}
f_iP_i
}
\]

其中：

\[
N
\]

表示 Expert 数量。

两个最重要的量：

\[
\boxed{
f_i
=
\text{Expert i 实际接到了多少 Token}
}
\]

而：

\[
\boxed{
P_i
=
\text{Router 平均有多喜欢 Expert i}
}
\]

这两个很像，但完全不同。

---

## 6. 用完整数字例子理解 \(P_i\)

假设有 4 个 Expert：

```text
E0
E1
E2
E3
```

有 4 个 Token：

```text
T1
T2
T3
T4
```

Router Softmax 后得到：

\[
P=
\begin{bmatrix}
0.10 & 0.20 & 0.60 & 0.10\\
0.05 & 0.15 & 0.70 & 0.10\\
0.10 & 0.10 & 0.70 & 0.10\\
0.05 & 0.15 & 0.75 & 0.05
\end{bmatrix}
\]

每一行：

> 一个 Token 对四个 Expert 的概率。

例如第一行：

\[
[0.10,0.20,0.60,0.10]
\]

表示：

```text
T1 对 E0：0.10
T1 对 E1：0.20
T1 对 E2：0.60
T1 对 E3：0.10
```

---

## 7. \(P_i\)：看 Router 的平均偏好

例如 E2。

四个 Token 对 E2 的概率：

\[
0.60,\ 0.70,\ 0.70,\ 0.75
\]

所以：

\[
P_2
=
\frac{
0.60+0.70+0.70+0.75
}{4}
\]

得到：

\[
P_2=0.6875
\]

意思是：

> Router 对这批 Token 平均把 68.75% 的概率放到了 Expert 2 上。

其他 Expert：

\[
P_0
=
\frac{
0.10+0.05+0.10+0.05
}{4}
=
0.075
\]

\[
P_1
=
0.15
\]

\[
P_3
=
0.0875
\]

所以：

\[
\boxed{
P=
[
0.075,\,
0.15,\,
0.6875,\,
0.0875
]
}
\]

---

## 8. \(f_i\)：看真正的路由结果

现在假设：

\[
TopK=1
\]

每个 Token 只选概率最大的 Expert。

刚才：

```text
T1 → E2
T2 → E2
T3 → E2
T4 → E2
```

所以：

```text
E0：0 个 Token

E1：0 个 Token

E2：4 个 Token

E3：0 个 Token
```

总共有：

\[
4
\]

个 Token。

于是：

\[
f_0=0
\]

\[
f_1=0
\]

\[
f_2=1
\]

\[
f_3=0
\]

所以：

\[
\boxed{
f=
[
0,\,
0,\,
1,\,
0
]
}
\]

---

## 9. \(f_i\) 和 \(P_i\) 的区别

放在一起：

| Expert | \(f_i\) | \(P_i\) |
|---|---:|---:|
| E0 | 0 | 0.075 |
| E1 | 0 | 0.15 |
| E2 | 1 | 0.6875 |
| E3 | 0 | 0.0875 |

其中：

\[
f_2=1
\]

意思是：

> 实际上 100% 的 Token 都被送给 E2。

而：

\[
P_2=0.6875
\]

意思是：

> Router 平均给 E2 68.75% 的概率。

所以：

\[
\boxed{
f_i=\text{实际选择结果}
}
\]

而：

\[
\boxed{
P_i=\text{Router 的软概率偏好}
}
\]

---

## 10. 为什么要用 \(f_iP_i\)？

如果某个 Expert：

```text
实际接到了很多 Token
```

也就是：

\[
f_i
\]

很大。

同时 Router：

```text
还特别喜欢它
```

也就是：

\[
P_i
\]

也很大。

那么：

\[
f_iP_i
\]

就会很大。

所以：

\[
\boxed{
f_iP_i
}
\]

可以理解为：

> 某个 Expert 既真的很忙，又被 Router 特别偏爱的程度。

---

## 11. 计算刚才的 Aux Loss

前面：

\[
f=
[
0,0,1,0
]
\]

\[
P=
[
0.075,\,
0.15,\,
0.6875,\,
0.0875
]
\]

那么：

\[
f_0P_0=0
\]

\[
f_1P_1=0
\]

\[
f_2P_2
=
1\times0.6875
=
0.6875
\]

\[
f_3P_3=0
\]

所以：

\[
\sum_i f_iP_i
=
0.6875
\]

因为：

\[
N=4
\]

于是：

\[
L_{\text{aux}}
=
4\times0.6875
\]

得到：

\[
\boxed{
L_{\text{aux}}
=
2.75
}
\]

说明：

> Router 当前明显过度偏爱 E2。

### 11.1 Top-k MoE Auxiliary Loss：一般公式与数值例子

假设：

- 一共有 \(T\) 个 Token
- 一共有 \(E\) 个 Expert
- 每个 Token 选择 \(K\) 个 Expert

我们先定义两个量。

---

## 12. Router 对 Expert 的平均偏好：\(P_i\)

对于第 \(t\) 个 Token，Router 给 Expert \(i\) 的概率记为：

\[
p_{t,i}
\]

并且：

\[
\sum_{i=1}^{E} p_{t,i}=1
\]

那么 Expert \(i\) 的平均 Router 概率为：

\[
\boxed{
P_i
=
\frac{1}{T}
\sum_{t=1}^{T}
p_{t,i}
}
\]

它表示：

> Router 平均有多喜欢 Expert \(i\)。

---

## 13. Expert 的实际负载：\(f_i\)

对于 Top-\(K\) Routing，每个 Token 会实际选择 \(K\) 个 Expert。

因此一共会产生：

\[
T\times K
\]

次 Expert 选择。

定义：

\[
\boxed{
f_i
=
\frac{
\text{Expert }i\text{ 被选中的总次数}
}{
T\times K
}
}
\]

因此：

\[
\sum_{i=1}^{E}f_i=1
\]

它表示：

> 所有实际路由中，有多大比例最终去了 Expert \(i\)。

---

## 14. 最一般、最直观的 Auxiliary Loss

常见的负载均衡思想可以写成：

\[
\boxed{
L_{\text{aux}}
=
E
\sum_{i=1}^{E}
f_iP_i
}
\]

如果再乘一个辅助损失系数：

\[
\lambda
\]

那么：

\[
\boxed{
L_{\text{aux}}
=
\lambda E
\sum_{i=1}^{E}
f_iP_i
}
\]

这就是最值得记住的形式。

其中：

\[
\boxed{
f_i
=
\text{Expert }i\text{ 实际承担的路由比例}
}
\]

\[
\boxed{
P_i
=
\text{Router 平均给 Expert }i\text{ 的概率}
}
\]

所以：

\[
\boxed{
f_iP_i
}
\]

可以理解成：

> Expert \(i\) 实际已经很忙，并且 Router 还很偏爱它的程度。

---

## 15. 为什么这个公式能衡量负载不均衡？

如果某个 Expert：

\[
f_i
\]

很大，说明：

> 实际很多 Token 都去了它。

同时：

\[
P_i
\]

也很大，说明：

> Router 本身也一直偏爱它。

那么：

\[
f_iP_i
\]

就会很大。

因此：

\[
L_{\text{aux}}
\]

会增大。

训练为了降低这个 Loss，就会倾向于：

\[
P_i\downarrow
\]

也就是：

> Router 不要继续过度偏爱已经很忙的 Expert。

---

## 16. 完全均衡时是什么情况？

假设：

\[
E
\]

个 Expert 完全均衡。

那么：

\[
f_i=\frac1E
\]

同时：

\[
P_i=\frac1E
\]

于是：

\[
\sum_{i=1}^{E} f_iP_i
=
E\times
\frac1E
\times
\frac1E
\]

得到：

\[
\frac1E
\]

所以：

\[
L_{\text{aux}}
=
E\times\frac1E
=
1
\]

因此不考虑 \(\lambda\) 时：

\[
\boxed{
\text{理想均衡状态下 }L_{\text{aux}}=1
}
\]

如果带系数：

\[
\lambda
\]

则：

\[
\boxed{
L_{\text{aux}}=\lambda
}
\]

---

## 31. 为什么不直接只用 \(f_i\)？

这是很关键的一点。

有人可能会想：

> \(f_i\) 已经表示实际负载了，直接让所有 \(f_i\) 接近平均不就行了吗？

问题是：

\[
f_i
\]

通常来自：

```text
Top-k
argmax
```

也就是：

```text
选中 Expert 2
没选中 Expert 1
```

这是一个离散选择。

因此：

\[
f_i
\]

本身很难直接给 Router 提供平滑梯度。

---

## 32. 为什么需要 \(P_i\)？

因为：

\[
P_i
\]

来自：

\[
softmax(W_rx)
\]

它是连续的。

因此：

\[
\boxed{
P_i
\text{ 可以反向传播}
}
\]

所以：

```text
f_i
```

负责告诉模型：

> 实际负载是什么样。

而：

```text
P_i
```

负责：

> 给 Router 提供可微的调整方向。

因此：

\[
f_iP_i
\]

把：

```text
实际负载
```

和：

```text
可微 Router 概率
```

连接起来。

---

## 33. 一个更直观的理解

可以把：

\[
f_i
\]

理解成：

> 这个专家实际接到了多少活。

把：

\[
P_i
\]

理解成：

> 老板有多想继续把活交给这个专家。

比如：

```text
Expert 2 已经接了 70% 的工作
```

即：

\[
f_2=0.7
\]

而 Router 还给它：

\[
P_2=0.6
\]

那么：

\[
f_2P_2
=
0.42
\]

很大。

说明：

> 它已经很忙了，Router 还特别喜欢继续给它派活。

Aux Loss 就会惩罚这种行为。

---

## 34. 为什么 \(f_iP_i\) 可以推动 Router 改变？

假设：

\[
f_2=0.7
\]

那么：

\[
f_2P_2
=
0.7P_2
\]

这时：

\[
P_2
\]

稍微增加一点，Loss 就增加得比较明显。

于是梯度会推动：

\[
P_2\downarrow
\]

也就是：

> Router 不要继续那么偏爱 Expert 2。

其他负载较低的 Expert：

\[
f_i
\]

较小，因此对应惩罚较小。

最终 Router 会慢慢把更多概率分配给其他 Expert。

---

## 35. 一句话记住 \(f_i\) 和 \(P_i\)

可以概括为：

\[
\boxed{
f_i
=
\text{这个 Expert 实际接到了多少活}
}
\]

\[
\boxed{
P_i
=
\text{Router 平均有多想把活给它}
}
\]

而：

\[
\boxed{
f_iP_i
=
\text{它既已经很忙、Router 又继续偏爱它的程度}
}
\]

---

## 36. Capacity 是什么？

即使有 Aux Loss，某个 Batch 仍然可能瞬间有很多 Token 去同一个 Expert。

所以一些 MoE 会规定：

\[
\boxed{\text{Expert Capacity}}
\]

即：

> 一个 Expert 最多允许处理多少 Token。

例如：

```text
Expert Capacity = 1000
```

如果当前 Expert 收到：

```text
1200 Token
```

那么多出来：

```text
200 Token
```

可能会：

```text
丢弃
重新路由
或者特殊处理
```

具体看模型实现。

---

## 37. Capacity Factor

通常：

\[
Capacity
=
CapacityFactor
\times
\frac{
Tokens\times TopK
}{
N_{expert}
}
\]

例如：

\[
Tokens=1024
\]

\[
TopK=2
\]

\[
N_{expert}=8
\]

一共会产生：

\[
1024\times2
=
2048
\]

次 Expert 分配。

平均每个 Expert：

\[
2048/8
=
256
\]

如果：

\[
CapacityFactor=1.25
\]

那么：

\[
Capacity
=
256\times1.25
=
320
\]

所以一个 Expert 最多允许处理大约：

\[
320
\]

个 Token。

---

## 38. 为什么 MoE 参数很大，但计算量没有同比增长？

假设每个 FFN 参数量为：

\[
100M
\]

Dense：

```text
一个 FFN
```

总参数：

\[
100M
\]

每个 Token 计算：

\[
100M
\]

对应的 FFN 参数。

---

MoE：

```text
8 个 Expert
```

每个：

\[
100M
\]

所以总 Expert 参数：

\[
800M
\]

但是：

\[
TopK=2
\]

每个 Token 只经过两个 Expert。

因此每 Token 激活的 Expert 参数大约：

\[
200M
\]

所以：

```text
总参数：800M

单 Token 激活：200M
```

这就是：

\[
\boxed{
\text{Total Parameters}
\neq
\text{Activated Parameters}
}
\]

---

## 39. MoE 中哪些部分仍然是 Dense 的？

MoE 并不是整个 Transformer 都稀疏。

通常：

```text
Embedding
Attention
Norm
Router
```

依旧会被所有 Token 使用。

只有：

```text
Expert FFN
```

是稀疏激活。

因此：

```text
Token
 ↓
Attention        ← 每个 Token 都算
 ↓
Router           ← 每个 Token 都算
 ↓
Top-k Experts    ← 只算少数 Expert
 ↓
Output
```

---

## 40. Router 参数量大吗？

通常并不大。

例如：

\[
d=4096
\]

有：

\[
8
\]

个 Expert。

Router：

\[
W_r
\in
\mathbb R^{4096\times8}
\]

参数量：

\[
4096\times8
=
32768
\]

而一个 FFN 可能有数千万甚至上亿参数。

所以：

\[
\boxed{
Router 本身通常不是参数大户
}
\]

---

## 41. MoE 真正困难的地方：Token Dispatch

数学上：

\[
y=
\sum_i g_iE_i(x)
\]

其实并不复杂。

真正困难的是：

> Token 到底怎么快速送到正确的 Expert。

特别是在多个 GPU 上。

例如：

```text
GPU0：Expert 0,1
GPU1：Expert 2,3
GPU2：Expert 4,5
GPU3：Expert 6,7
```

现在 GPU0 上某个 Token：

```text
需要 Expert 6
```

那它的数据就需要送到：

```text
GPU3
```

另一个 Token：

```text
需要 Expert 2
```

则需要送到：

```text
GPU1
```

所以会产生大量 GPU 之间的数据交换。

---

## 42. All-to-All Communication

MoE 训练中经常需要：

\[
\boxed{\text{All-to-All Communication}}
\]

例如：

```text
GPU0 → GPU1
GPU0 → GPU3
GPU1 → GPU2
GPU2 → GPU0
GPU3 → GPU1
...
```

Token 先被发送到 Expert 所在 GPU。

Expert 计算完成之后：

```text
Expert Output
```

又要送回原来的位置。

所以：

> MoE 算法本身并不复杂，但大规模系统实现非常复杂。

---

## 43. Expert Parallelism

普通大模型常见：

```text
Data Parallel

Tensor Parallel

Pipeline Parallel
```

MoE 又多了一个非常重要的并行方式：

\[
\boxed{\text{Expert Parallelism}}
\]

例如：

```text
GPU0：
Expert 0
Expert 1

GPU1：
Expert 2
Expert 3

GPU2：
Expert 4
Expert 5

GPU3：
Expert 6
Expert 7
```

Router 计算完：

```text
Token → 对应 Expert 所在 GPU
```

计算完成：

```text
Expert Output → 返回
```

---

## 44. Router 是怎么训练的？

最终 MoE 输出：

\[
y=
g_1E_1(x)+g_3E_3(x)
\]

假设最终 Loss：

\[
L
\]

那么梯度可以通过：

\[
g_1
\]

和：

\[
g_3
\]

反向传播。

因为：

\[
g
=
softmax(W_rx)
\]

所以可以继续：

\[
\frac{\partial L}
{\partial W_r}
\]

于是 Router 参数：

\[
W_r
\]

也会被训练。

所以 Router 并不是人工规则，而是：

\[
\boxed{\text{可学习模块}}
\]

---

## 45. Top-k 明明是离散的，为什么还能训练？

Top-k 的：

```text
索引选择
```

本身确实是离散的。

例如：

```text
选 E1
选 E3
```

但被选中的 Expert 对应的 Gate Weight：

\[
g_1
\]

\[
g_3
\]

仍然来自可微的：

\[
softmax
\]

所以：

\[
y=
g_1E_1(x)
+
g_3E_3(x)
\]

仍然可以对：

\[
g_1,g_3
\]

求梯度。

再继续传播到 Router 参数。

所以可以简单理解：

> Expert 索引本身不是普通连续变量，但被选 Expert 的概率权重仍然可以参与梯度计算。

---

## 46. Expert 为什么会慢慢形成不同能力？

关键原因：

> 不同 Expert 收到的 Token 不一样。

例如训练一段时间后：

```text
E0 经常收到某类代码 Token

E1 经常收到某类语言结构

E2 经常收到某类数学结构

E3 经常收到另一类语义模式
```

那么：

\[
E_0
\]

收到的梯度数据和：

\[
E_1
\]

不一样。

所以它们的参数更新方向也会不同。

久而久之就产生：

\[
\boxed{\text{Expert Specialization}}
\]

---

## 47. 一个 Token 会更新所有 Expert 吗？

不会。

如果：

\[
TopK=2
\]

某个 Token 只经过：

```text
Expert 1
Expert 5
```

那么这个 Token 对 Expert 部分的梯度，主要只会更新：

```text
Expert 1

Expert 5
```

而：

```text
Expert 0
Expert 2
Expert 3
Expert 4
...
```

并不会因为这个 Token 直接得到同样的 Expert 梯度。

所以：

\[
\boxed{
\text{不同 Expert 收到不同训练数据}
}
\]

这正是它们形成不同能力的重要原因。

---

## 48. 同一个词是否永远去同一个 Expert？

不是。

Router 输入的是：

\[
\boxed{\text{当前层 hidden state}}
\]

不是单纯的：

```text
Token ID
```

例如：

```text
Apple released a new iPhone.
```

里面的：

```text
Apple
```

和：

```text
I ate an apple.
```

里面的：

```text
apple
```

虽然词面相似，但经过上下文 Attention 之后，hidden state 不一样。

因此：

\[
\boxed{
\text{完全可能走不同 Expert}
}
\]

所以 MoE Routing 是：

\[
\boxed{\text{Context-Aware}}
\]

的。

---

## 49. 同一个 Token 在不同层会选同一个 Expert 吗？

也不一定。

例如 Token：

```text
"model"
```

在第 5 层：

```text
Expert 1
Expert 3
```

到第 10 层：

```text
Expert 4
Expert 7
```

到第 20 层：

```text
Expert 2
Expert 6
```

因为每一层的 hidden state 已经不同。

而且不同层一般也有自己的 Router。

因此 Routing 还是：

\[
\boxed{\text{Layer-dependent}}
\]

的。

---

## 50. Shared Expert 是什么？

一些 MoE 架构还会加入：

\[
\boxed{\text{Shared Expert}}
\]

即：

> 不管 Router 选谁，每个 Token 都会经过这个共享 Expert。

结构类似：

```text
                 → Shared Expert

Token
                 → Router → Top-k Routed Experts
```

然后：

\[
y
=
E_{shared}(x)
+
\sum_{i\in TopK}
g_iE_i(x)
\]

---

## 51. Shared Expert 可以怎么理解？

可以直观理解为：

```text
Shared Expert
=
所有 Token 都需要的公共能力
```

而：

```text
Routed Experts
=
更加专门化的能力
```

例如可能把一些：

```text
通用语言能力
基础模式
公共表示
```

交给 Shared Expert。

而让 Routed Experts 专注于更有差异性的能力。

---

## 52. Gate 和 Router 是什么关系？

代码里面可能看到：

```python
self.gate
```

也可能看到：

```python
self.router
```

在很多 MoE 实现中，它们表达的核心作用基本一致：

\[
\boxed{
\text{根据 hidden state 计算各个 Expert 的分数}
}
\]

所以在很多代码里可以近似理解：

\[
\boxed{
Gate
\approx
Router
}
\]

只是名字不同。

---

## 53. MoE 常见代码结构

例如：

```python
class MOEFeedForward(nn.Module):
```

里面一般会有：

```python
self.gate

self.experts
```

例如：

```python
self.experts = nn.ModuleList(
    [
        FeedForward(config)
        for _ in range(
            config.n_routed_experts
        )
    ]
)
```

意思是：

> 创建多个独立的 FFN。

其中：

```python
experts[0]
experts[1]
experts[2]
...
```

每一个都有自己独立的参数。

---

## 54. Gate 的典型 shape

原始输入：

\[
x
\in
\mathbb R^{B\times T\times D}
\]

先变成：

\[
x
\in
\mathbb R^{BT\times D}
\]

例如：

```python
x = x.view(
    -1,
    hidden_size
)
```

然后：

```python
logits = self.gate(x)
```

得到：

\[
logits
\in
\mathbb R^{BT\times N_{expert}}
\]

即：

> 每个 Token 对所有 Expert 的 Router 分数。

---

## 55. Top-k 代码

常见：

```python
weight, ids = torch.topk(
    scores,
    k=top_k,
    dim=-1
)
```

例如：

```text
Token 0：

scores =
[0.1, 0.6, 0.2, 0.1]
```

如果：

\[
TopK=2
\]

得到：

```text
weight =
[0.6, 0.2]

ids =
[1, 2]
```

意思：

```text
选择 Expert 1

选择 Expert 2
```

## 56. 一个完整的 MoE 前向传播

假设：

```text
hidden_size = 4096

num_experts = 8

top_k = 2
```

输入：

\[
X
\in
\mathbb R^{B\times T\times4096}
\]

---

### 56.1 Step 1：展开 Token

\[
X
\rightarrow
X_f
\]

\[
X_f
\in
\mathbb R^{BT\times4096}
\]

---

### 56.2 Step 2：Router

\[
R=X_fW_r
\]

得到：

\[
R
\in
\mathbb R^{BT\times8}
\]

---

### 56.3 Step 3：Softmax

\[
P=softmax(R)
\]

得到：

> 每个 Token 对 8 个 Expert 的概率。

---

### 56.4 Step 4：Top-k

例如某个 Token：

```text
topk_idx =
[2,5]

topk_weight =
[0.71,0.29]
```

---

### 56.5 Step 5：按照 Expert 对 Token 分组

例如：

```text
Expert 2：
Token 0
Token 4
Token 8

Expert 5：
Token 0
Token 3
Token 7
```

---

### 56.6 Step 6：Expert Forward

分别计算：

\[
E_2(x)
\]

\[
E_5(x)
\]

---

### 56.7 Step 7：乘 Gate Weight

例如：

\[
0.71E_2(x)
\]

\[
0.29E_5(x)
\]

---

### 56.8 Step 8：通过 `index_add_` 加回原 Token

例如：

```python
output.index_add_(
    0,
    token_idx,
    expert_output * weight
)
```

本质上完成：

\[
y_t
=
\sum_{i\in TopK(t)}
g_{t,i}E_i(x_t)
\]

---

### 56.9 Step 9：恢复原 Shape

从：

\[
[BT,D]
\]

恢复：

\[
[B,T,D]
\]

然后继续进入 Transformer 下一部分。

---

## 57. MoE 和普通 Ensemble 不一样

Ensemble：

```text
Model A
Model B
Model C
```

通常是：

```text
完整模型分别进行推理
最后融合
```

而 MoE：

```text
一个模型内部
包含很多 Expert
```

并且：

```text
每个 Token 动态选择 Expert
```

所以：

\[
\boxed{
MoE
\neq
普通 Ensemble
}
\]

---

## 58. MoE 和 Multi-Head Attention 也不一样

MHA：

```text
Head 1
Head 2
Head 3
...
```

一般所有 Head 都会计算。

最终：

```text
Concat
→ W_O
```

MoE：

```text
Expert 0
Expert 1
Expert 2
...
```

通常只选择：

\[
TopK
\]

所以区别可以简单记：

```text
MHA：
所有 Head 基本都激活

MoE：
只有少数 Expert 激活
```

---

## 59. Expert 是越多越好吗？

不一定。

Expert 多：

优点：

```text
总参数容量大
可以产生更多 specialization
```

但是问题也更多：

```text
通信成本增加

负载均衡更困难

每个 Expert 收到的数据可能变少

显存占用增加

部署更复杂
```

所以 Expert 数量是一个 trade-off。

---

## 60. MoE 的主要优点

第一：

\[
\boxed{\text{参数容量大}}
\]

第二：

\[
\boxed{\text{每个 Token 激活参数少}}
\]

第三：

\[
\boxed{\text{不同 Expert 可以自动形成 specialization}}
\]

第四：

\[
\boxed{\text{可以在相近计算预算下增加模型总容量}}
\]

---

## 61. MoE 的主要缺点

第一：

> 全部 Expert 参数仍然要存储。

即使当前 Token 不计算某 Expert：

```text
这个 Expert 的参数依然存在
```

---

第二：

> GPU 之间通信成本很高。

特别是：

\[
All-to-All
\]

---

第三：

> 负载可能不均衡。

---

第四：

> 训练实现更加复杂。

需要考虑：

```text
Router

Top-k

Aux Loss

Capacity

Token Dispatch

Expert Parallelism
```

---

第五：

> 推理部署更复杂。

因为不同 Token：

```text
走不同路径
```

这会让：

```text
Batching

Memory

Kernel

Communication
```

都更加复杂。

## 63. 三个最重要的公式

### 63.1 Router

\[
\boxed{
g(x)
=
softmax(W_rx)
}
\]

---

### 63.2 Top-k Expert 融合

\[
\boxed{
y
=
\sum_{i\in TopK}
g_i(x)E_i(x)
}
\]

---

### 63.3 负载均衡 Aux Loss

\[
\boxed{
L_{\text{aux}}
=
N
\sum_i
f_iP_i
}
\]

其中：

\[
\boxed{
f_i
=
\text{Expert i 实际接收到的 Token 比例}
}
\]

\boxed{
P_i
=
\text{Router 对 Expert i 的平均概率}
}
\]

## 64. 最后总结

如果把整个 MoE 压缩成一条完整流程：

```text
Token Hidden State
        ↓
      Router
        ↓
  每个 Expert 的分数
        ↓
      Softmax
        ↓
      Top-k
        ↓
把 Token 分配到对应 Expert
        ↓
各个 Expert 批量做 FFN
        ↓
乘 Gate Weight
        ↓
index_add_
把多个 Expert 的结果
累加回原 Token 位置
        ↓
   得到 MoE 输出
```

训练时另外增加：

```text
f_i
=
Expert 实际接到多少 Token

P_i
=
Router 平均有多喜欢这个 Expert
```

构造：

\[
L_{\text{aux}}
=
N\sum_i f_iP_i
\]

避免：

```text
所有 Token 都跑去少数几个 Expert
```

## 65. 整节 MoE 最核心的一句话

\[
\boxed{
\text{MoE 就是把一个 FFN 变成很多个 FFN，
再通过 Router 为每个 Token 动态选择少数几个 FFN，
最后用 Gate Weight 加权，并通过类似 index\_add\_ 的操作，
把多个 Expert 的结果重新累加回对应 Token。}
}
\]

它最核心的价值是：

\[
\boxed{
\text{非常大的总参数容量}
+
\text{相对较少的每 Token 激活参数}
}
\]

最终可以概括成：

```text
多个 Expert
+
Router
+
Top-k
+
Sparse Activation
+
Expert Output 聚合
+
Load Balancing
=
MoE
```
