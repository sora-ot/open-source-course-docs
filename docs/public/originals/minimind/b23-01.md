# 63 · MoE：专家路由与 Token 分发

<!-- LECTURE-CONTENT-START -->

---

## 1. MoE 到底是什么？

MoE：

\[
\boxed{\text{Mixture of Experts}}
\]

中文通常叫：

> **混合专家模型**

它最核心的思想非常简单：

> 不再让所有 Token 都经过同一个 FFN，而是准备很多个不同的 FFN，再让模型自己决定：当前这个 Token 应该交给哪几个 FFN 处理。

这些不同的 FFN 就叫：

\[
\boxed{\text{Expert}}
\]

即：

> 专家。

因此最简单地说：

\[
\boxed{
\text{MoE}
=
\text{多个 FFN}
+
\text{一个负责选择 FFN 的 Router}
}
\]

---

## 2. 为什么会出现 MoE？

先回忆普通 Transformer。

一个 Transformer Block 大致可以写成：

```text
Hidden State
    ↓
Attention
    ↓
Residual
    ↓
FFN
    ↓
Residual
    ↓
下一层
```

其中 FFN 通常类似：

\[
x
\rightarrow
W_1
\rightarrow
\text{Activation}
\rightarrow
W_2
\]

例如：

\[
4096
\rightarrow
11008
\rightarrow
4096
\]

普通 Dense Transformer 中，每一个 Token 都经过：

\[
\boxed{\text{同一个 FFN}}
\]

例如：

```text
"I"      ──→ FFN
"love"   ──→ FFN
"AI"     ──→ FFN
```

也就是说：

> 所有 Token 共享这一套 FFN 参数。

---

## 3. Dense 模型的问题：参数量和计算量一起增加

如果希望模型能力更强，一种很直接的办法就是：

```text
把 FFN 做得越来越大
```

比如：

\[
4096
\rightarrow
11008
\rightarrow
4096
\]

改成更大的中间层。

这样当然可以增加参数量。

但是问题是：

\[
\boxed{
\text{参数量增加}
\Rightarrow
\text{每个 Token 的计算量也增加}
}
\]

因为每个 Token 都必须经过完整 FFN。

所以 Dense 模型往往存在：

\[
\boxed{
\text{模型越大}
\Rightarrow
\text{每个 Token 算得越多}
}
\]

---

## 4. MoE 的目标：参数很多，但每次只计算一小部分

MoE 的思想是：

> 我可以准备很多套 FFN，但不让每个 Token 都经过全部 FFN。

例如准备：

```text
Expert 0
Expert 1
Expert 2
Expert 3
Expert 4
Expert 5
Expert 6
Expert 7
```

一共：

\[
8
\]

个 Expert。

假设：

\[
TopK=2
\]

那么对于一个 Token，只选择其中两个 Expert。

例如：

```text
"AI"
 ↓
Router
 ↓
Expert 2
Expert 6
```

其他：

```text
Expert 0
Expert 1
Expert 3
Expert 4
Expert 5
Expert 7
```

这一轮都不计算。

因此：

\[
\boxed{
\text{总参数很多}
}
\]

但是：

\[
\boxed{
\text{单个 Token 只激活少量参数}
}
\]

这就是 MoE 最重要的思想：

\[
\boxed{\text{Sparse Activation}}
\]

即：

> 稀疏激活。

---

## 5. Dense 和 MoE 的直接对比

Dense：

```text
Token
 ↓
FFN
 ↓
Output
```

所有 Token：

```text
Token 1 ─→ FFN
Token 2 ─→ FFN
Token 3 ─→ FFN
Token 4 ─→ FFN
```

MoE：

```text
                  ┌→ Expert 0
                  ├→ Expert 1
Token → Router ───┼→ Expert 2
                  ├→ Expert 3
                  └→ ...
```

但是对于某个 Token：

```text
只选择 Top-k 个 Expert
```

例如：

```text
Token 1 → Expert 1 + Expert 4
Token 2 → Expert 0 + Expert 6
Token 3 → Expert 1 + Expert 5
```

因此 MoE 经常叫：

\[
\boxed{\text{Sparse MoE}}
\]

---

## 6. Expert 到底是什么？

这是学习 MoE 时首先要搞清楚的问题。

Expert 通常并不是：

```text
一个完整的大模型
```

而是：

\[
\boxed{\text{一个 FFN}}
\]

普通 Transformer：

```text
Attention
   ↓
FFN
```

MoE Transformer：

```text
Attention
   ↓
MoE
```

而这个 MoE 内部是：

```text
Router
+
Expert 0
+
Expert 1
+
Expert 2
+
...
```

其中每个 Expert 本身就是一个 FFN。

比如：

\[
Expert_i(x)
=
W_{2,i}
\sigma(W_{1,i}x)
\]

如果使用 LLaMA 常见的 SwiGLU，则类似：

\[
Expert_i(x)
=
W_{down,i}
\left[
\operatorname{SiLU}(W_{gate,i}x)
\odot
W_{up,i}x
\right]
\]

所以本质上：

\[
\boxed{
\text{MoE 就是把原来的一个 FFN 换成很多个 FFN}
}
\]

然后再增加一个 Router 来选择。

---

## 7. 为什么通常替换 FFN，而不是 Attention？

因为 FFN 本身就是 Transformer 中非常大的参数模块。

假设：

\[
d_{model}=4096
\]

FFN 为：

\[
4096
\rightarrow
11008
\rightarrow
4096
\]

仅仅两个主要矩阵：

\[
W_1\in\mathbb R^{4096\times11008}
\]

\[
W_2\in\mathbb R^{11008\times4096}
\]

参数量大约：

\[
2\times4096\times11008
\]

约为：

\[
90M
\]

所以如果把：

```text
1 个 FFN
```

变成：

```text
8 个 FFN
```

参数容量一下子就增加很多。

但如果每次只计算其中：

```text
2 个
```

那么计算量不会按照 8 倍一起增长。

因此 MoE 可以实现：

\[
\boxed{
\text{更大的参数容量}
+
\text{相对较低的激活计算量}
}
\]

---

## 8. MoE 最核心的组件：Router

假设某个 Token 当前的 hidden state 是：

\[
x\in\mathbb R^d
\]

例如：

\[
d=4096
\]

Router 的任务是：

> 判断当前 Token 应该送给哪些 Expert。

最简单的 Router 就是一个线性层：

\[
z=xW_r
\]

假设有：

\[
N=8
\]

个 Expert。

那么：

\[
W_r\in\mathbb R^{4096\times8}
\]

所以：

\[
x
\in
\mathbb R^{4096}
\]

经过 Router 后：

\[
z
\in
\mathbb R^8
\]

例如：

\[
z=
[
1.2,\,
-0.5,\,
2.0,\,
0.3,\,
-1.1,\,
1.5,\,
0.7,\,
2.4
]
\]

这 8 个数分别对应：

```text
Expert 0 的分数
Expert 1 的分数
Expert 2 的分数
...
Expert 7 的分数
```

---

## 9. Router 实际在学习什么？

Router 实际在学习：

\[
\boxed{
\text{什么样的 hidden state 应该交给哪个 Expert}
}
\]

训练之后，不同 Expert 可能形成不同的 specialization。

例如可能出现：

```text
某些 Expert 更擅长代码模式
某些 Expert 更擅长数学模式
某些 Expert 更擅长语言结构
某些 Expert 更偏向某些语义特征
```

但是要注意：

> 我们通常不会人为规定 Expert 0 就是数学专家，Expert 1 就是代码专家。

Expert 的分工通常是：

\[
\boxed{\text{训练过程中自动形成}}
\]

而且实际的分工往往比：

```text
数学专家
代码专家
英语专家
```

复杂得多。

---

## 10. Router 为什么还要经过 Softmax？

Router 首先输出 logits：

\[
z=xW_r
\]

例如：

\[
z=
[
1,\,
3,\,
2,\,
0
]
\]

再经过：

\[
p=\operatorname{softmax}(z)
\]

假设得到：

\[
p=
[
0.087,\,
0.644,\,
0.237,\,
0.032
]
\]

这表示：

```text
Expert 0 → 0.087
Expert 1 → 0.644
Expert 2 → 0.237
Expert 3 → 0.032
```

并且：

\[
\sum_i p_i=1
\]

这些概率经常叫：

\[
\boxed{\text{Routing Weight}}
\]

或者：

\[
\boxed{\text{Gate Weight}}
\]

---

## 11. Top-k Routing

假设：

\[
TopK=2
\]

对于：

\[
[
0.087,\,
0.644,\,
0.237,\,
0.032
]
\]

最大的两个是：

```text
Expert 1 → 0.644
Expert 2 → 0.237
```

所以当前 Token 只交给：

```text
Expert 1
Expert 2
```

其余 Expert 不执行。

这就是：

\[
\boxed{\text{Top-k Routing}}
\]

---

## 12. Top-1 和 Top-2

如果：

\[
TopK=1
\]

那么：

```text
Token
 ↓
Router
 ↓
Expert 3
```

每个 Token 只经过一个 Expert。

优点：

```text
计算量低
```

缺点：

```text
一次路由错误影响比较直接
表达能力可能相对弱一些
```

所以很多 MoE 会使用：

\[
TopK=2
\]

也就是：

> 一个 Token 同时经过两个 Expert。

---

## 13. Top-k 之后为什么有时还要重新归一化？

假设 Softmax 后：

\[
[
0.1,\,
0.6,\,
0.2,\,
0.1
]
\]

Top-2 选中：

\[
0.6,\ 0.2
\]

它们加起来：

\[
0.8
\]

如果希望最后两个 Expert 的权重之和仍然为：

\[
1
\]

那么重新归一化：

\[
g_1
=
\frac{0.6}{0.8}
=
0.75
\]

\[
g_2
=
\frac{0.2}{0.8}
=
0.25
\]

于是：

\[
g_1+g_2=1
\]

代码中可能会看到：

```python
weight = weight / weight.sum(
    dim=-1,
    keepdim=True
)
```

---

## 14. 多个 Expert 的输出怎么融合？

假设某个 Token 最终选择：

```text
Expert 1 → 0.7
Expert 5 → 0.3
```

分别执行：

\[
y_1=Expert_1(x)
\]

\[
y_5=Expert_5(x)
\]

最终输出不是简单相加，而是：

\[
y
=
0.7y_1
+
0.3y_5
\]

一般写成：

\[
\boxed{
y=
\sum_{i\in TopK}
g_iExpert_i(x)
}
\]

其中：

\[
g_i
\]

就是当前 Expert 的 Gate Weight。

## 15. 一个完整数字例子

假设有 4 个 Expert：

```text
E0
E1
E2
E3
```

某个 Token 的 hidden state：

\[
x
\]

经过 Router：

\[
z=
[
0.5,\,
2.0,\,
1.5,\,
-1.0
]
\]

Softmax 后假设：

\[
p=
[
0.12,\,
0.53,\,
0.32,\,
0.03
]
\]

Top-2：

```text
Expert 1
Expert 2
```

重新归一化：

\[
g_1
=
\frac{0.53}{0.53+0.32}
\approx0.624
\]

\[
g_2
=
\frac{0.32}{0.53+0.32}
\approx0.376
\]

然后：

\[
y_1=Expert_1(x)
\]

\[
y_2=Expert_2(x)
\]

最后：

\[
\boxed{
y=
0.624y_1
+
0.376y_2
}
\]

## 16. 可以把 MoE 理解成“医院分诊”

一个比较直观的类比：

```text
病人
 ↓
分诊台
 ↓
不同医生
```

其中：

```text
Router = 分诊台

Expert = 专科医生
```

比如：

```text
病人
 ↓
Router
 ↓
70% → 专家 A
30% → 专家 B
```

最后：

\[
y
=
0.7y_A
+
0.3y_B
\]

MoE 的逻辑基本就是这样。

## 17. 从 Batch 角度理解 MoE

真实训练不会只有一个 Token。

输入一般是：

\[
X\in\mathbb R^{B\times T\times D}
\]

例如：

\[
B=2
\]

\[
T=4
\]

\[
D=4096
\]

那么一共有：

\[
B\times T=8
\]

个 Token。

通常先 reshape：

\[
X
\rightarrow
X_f
\]

得到：

\[
X_f
\in
\mathbb R^{8\times4096}
\]

然后所有 Token 一起进入 Router：

\[
R=X_fW_r
\]

假设有 8 个 Expert：

\[
R
\in
\mathbb R^{8\times8}
\]

意思是：

> 8 个 Token，每个 Token 都有 8 个 Expert 分数。

---

## 18. 一个 Batch 的路由例子

假设有 5 个 Token：

```text
T0
T1
T2
T3
T4
```

有 4 个 Expert：

```text
E0
E1
E2
E3
```

Top-2 结果：

```text
T0 → E0, E2
T1 → E1, E2
T2 → E0, E3
T3 → E1, E2
T4 → E2, E3
```

真正运行的时候，一般不会写：

```text
先计算 T0
再计算 T1
再计算 T2
...
```

因为这样太慢。

通常会把属于同一个 Expert 的 Token 聚到一起。

所以重新整理成：

```text
E0：
T0
T2

E1：
T1
T3

E2：
T0
T1
T3
T4

E3：
T2
T4
```

然后一次性计算：

```text
E0(T0,T2)

E1(T1,T3)

E2(T0,T1,T3,T4)

E3(T2,T4)
```

这样就可以利用 GPU 的矩阵并行能力。

## 19. `one_hot` 在 MoE 中是做什么的？

真实代码中经常看到：

```python
expert_mask = F.one_hot(
    topk_idx,
    num_classes=num_experts
)
```

例如：

```text
Token 0 → Expert 1, Expert 3

Token 1 → Expert 0, Expert 2
```

假设一共有 4 个 Expert。

那么：

```text
Expert 0 → [1,0,0,0]
Expert 1 → [0,1,0,0]
Expert 2 → [0,0,1,0]
Expert 3 → [0,0,0,1]
```

通过 one-hot，就可以方便地回答：

> 哪些 Token 选择了 Expert 0？

> 哪些 Token 选择了 Expert 1？

> 哪些 Token 选择了 Expert 2？

这样程序就可以把属于同一个 Expert 的 Token 聚集起来。

## 20. 一个 Expert 如何批量处理属于自己的 Token？

假设：

```text
Expert 2
```

被以下 Token 选中：

```text
Token 1
Token 4
Token 7
Token 10
```

那么先根据索引取出：

```python
expert_input = x[token_indices]
```

例如得到：

\[
expert\_input
\in
\mathbb R^{4\times4096}
\]

然后一次执行：

```python
expert_output = expert_2(
    expert_input
)
```

得到：

\[
expert\_output
\in
\mathbb R^{4\times4096}
\]

这样 Expert 2 就一次性处理完自己的所有 Token。

## 21. `output.index_add_()` 到底是干什么的？

这是 MoE 实现里面非常关键的一个操作。

首先不要考虑 MoE。

先单独理解：

```python
output.index_add_(
    dim,
    index,
    source
)
```

它的核心意思是：

\[
\boxed{
\text{把 source 中的内容，根据 index 指定的位置，加到 output 上}
}
\]

注意关键词是：

\[
\boxed{\text{加}}
\]

而不是：

```text
覆盖
```

---

## 22. `index_add_` 最简单例子

假设：

```python
import torch

output = torch.tensor([
    10.,
    20.,
    30.,
    40.
])

index = torch.tensor([
    1,
    3
])

source = torch.tensor([
    5.,
    7.
])
```

现在执行：

```python
output.index_add_(
    0,
    index,
    source
)
```

什么意思？

`source[0] = 5`

对应：

```text
index[0] = 1
```

所以：

\[
output[1]
=
output[1]+5
\]

原来：

\[
output[1]=20
\]

变成：

\[
25
\]

---

`source[1] = 7`

对应：

```text
index[1] = 3
```

所以：

\[
output[3]
=
output[3]+7
\]

原来：

\[
40
\]

变成：

\[
47
\]

最终：

```python
tensor([
    10.,
    25.,
    30.,
    47.
])
```

所以：

\[
\boxed{
index\_add_
=
按照 index 指定的位置进行累加
}
\]

---

## 23. 为什么叫 `index_add_`？

拆开来看：

```text
index
+
add
+
_
```

`index`：

> 根据索引指定位置。

`add`：

> 执行加法。

最后的：

```text
_
```

表示：

\[
\boxed{\text{in-place}}
\]

即：

> 直接修改原来的 Tensor。

所以：

```python
output.index_add_(...)
```

会直接改变：

```python
output
```

本身。

---

## 24. 如果一个 index 重复出现会怎么样？

这正是 `index_add_` 特别适合 MoE 的原因。

例如：

```python
output = torch.tensor([
    0.,
    0.,
    0.
])

index = torch.tensor([
    1,
    1
])

source = torch.tensor([
    3.,
    5.
])
```

执行：

```python
output.index_add_(
    0,
    index,
    source
)
```

第一条：

```text
source[0] = 3
index[0] = 1
```

所以：

\[
output[1]+=3
\]

第二条：

```text
source[1] = 5
index[1] = 1
```

还是：

\[
output[1]+=5
\]

最后：

\[
output[1]=3+5=8
\]

所以结果：

```python
tensor([
    0.,
    8.,
    0.
])
```

也就是说：

> 多个 source 如果指向同一个 index，会自动累加到同一个位置。

这正好对应 MoE：

> 同一个 Token 可以被多个 Expert 选中，所以多个 Expert 的输出最终都要累加回这个 Token。

---

## 25. 二维 Tensor 中的 `index_add_`

MoE 里 `output` 一般不是一维，而是：

\[
[Token数,\ hidden\_size]
\]

比如：

```python
output = torch.zeros(
    3,
    2
)
```

得到：

\[
output=
\begin{bmatrix}
0&0\\
0&0\\
0&0
\end{bmatrix}
\]

假设：

```python
index = torch.tensor([
    0,
    2
])
```

然后：

```python
source = torch.tensor([
    [1., 2.],
    [3., 4.]
])
```

执行：

```python
output.index_add_(
    0,
    index,
    source
)
```

含义：

```text
source 第 0 行
加到 output 第 0 行

source 第 1 行
加到 output 第 2 行
```

所以：

\[
output=
\begin{bmatrix}
1&2\\
0&0\\
3&4
\end{bmatrix}
\]

---

## 26. `dim=0` 到底是什么意思？

这里：

```python
output.index_add_(
    0,
    index,
    source
)
```

第一个参数：

```python
0
```

表示：

> 沿着第 0 维，也就是“行”进行索引累加。

MoE 中：

\[
output.shape
=
[Token数,\ hidden\_size]
\]

第 0 维就是：

```text
Token 维
```

所以：

```python
dim=0
```

就是：

> 根据 Token 的编号，把 Expert 输出加回对应 Token 的位置。

## 27. 为什么 MoE 特别适合用 `index_add_`？

假设：

\[
TopK=2
\]

那么一个 Token 会被两个 Expert 处理。

例如：

```text
Token 3
 ↓
Expert 1
Expert 5
```

Expert 1 得到：

\[
E_1(x_3)
\]

Expert 5 得到：

\[
E_5(x_3)
\]

最终：

\[
output_3
=
g_1E_1(x_3)
+
g_5E_5(x_3)
\]

所以：

```text
Token 3 的 output
```

需要被写入两次。

但不是：

```text
第二次覆盖第一次
```

而是：

\[
\boxed{\text{累加}}
\]

因此 `index_add_` 就特别合适。

---

## 28. 一个真正对应 MoE 的 `index_add_` 数字例子

假设有 3 个 Token：

```text
T0
T1
T2
```

hidden size 为：

\[
2
\]

先初始化：

```python
output = torch.zeros(
    3,
    2
)
```

即：

\[
output=
\begin{bmatrix}
0&0\\
0&0\\
0&0
\end{bmatrix}
\]

现在 Expert 0 处理了：

```text
T0
T2
```

它得到加权之后的结果：

\[
source=
\begin{bmatrix}
1&2\\
3&4
\end{bmatrix}
\]

对应 Token 索引：

```python
token_idx = torch.tensor([
    0,
    2
])
```

执行：

```python
output.index_add_(
    0,
    token_idx,
    source
)
```

结果：

\[
output=
\begin{bmatrix}
1&2\\
0&0\\
3&4
\end{bmatrix}
\]

---

接下来 Expert 1 又处理了：

```text
T0
T1
```

得到：

\[
source=
\begin{bmatrix}
5&6\\
7&8
\end{bmatrix}
\]

对应：

```python
token_idx = torch.tensor([
    0,
    1
])
```

再次执行：

```python
output.index_add_(
    0,
    token_idx,
    source
)
```

那么：

```text
T0 已经有 Expert 0 的结果了

现在再把 Expert 1 的结果加进去
```

所以：

\[
T0:
[1,2]+[5,6]
=
[6,8]
\]

T1：

\[
[0,0]+[7,8]
=
[7,8]
\]

T2 不变：

\[
[3,4]
\]

最终：

\[
\boxed{
output=
\begin{bmatrix}
6&8\\
7&8\\
3&4
\end{bmatrix}
}
\]

这就是 MoE 中：

\[
\boxed{
\text{多个 Expert 的结果重新聚合回原 Token}
}
\]

的过程。

## 29. 把 Gate Weight 也放进来

真实 MoE 中不是直接：

\[
E_i(x)
\]

写回。

而是：

\[
g_iE_i(x)
\]

例如：

```text
Token 0
```

经过：

```text
Expert 0，权重 0.7
Expert 1，权重 0.3
```

Expert 0 输出：

\[
[2,4]
\]

加权后：

\[
0.7[2,4]
=
[1.4,2.8]
\]

Expert 1 输出：

\[
[10,20]
\]

加权后：

\[
0.3[10,20]
=
[3,6]
\]

那么：

```python
output.index_add_(...)
```

第一次写入：

\[
[1.4,2.8]
\]

第二次继续加：

\[
[3,6]
\]

最后：

\[
output_0
=
[1.4,2.8]+[3,6]
\]

得到：

\[
\boxed{
[4.4,8.8]
}
\]

这正好就是：

\[
0.7E_0(x)
+
0.3E_1(x)
\]

## 30. 对应到常见 MoE 代码

可能看到：

```python
output.index_add_(
    0,
    token_idx,
    expert_output * weight
)
```

逐项解释：

```python
output
```

表示：

> 所有 Token 最终的 MoE 输出。

shape 一般：

\[
[BT,D]
\]

---

```python
token_idx
```

表示：

> 当前这些 Expert 输出应该写回哪些 Token。

例如：

```text
[0, 3, 7, 10]
```

说明当前 Expert 处理的是：

```text
Token 0
Token 3
Token 7
Token 10
```

---

```python
expert_output
```

表示：

> 当前 Expert 对这些 Token 的计算结果。

---

```python
weight
```

表示：

> 每个 Token 对当前 Expert 的 Gate Weight。

---

所以：

```python
expert_output * weight
```

就是：

\[
g_iE_i(x)
\]

然后：

```python
output.index_add_(
    0,
    token_idx,
    ...
)
```

就是：

> 把这些加权 Expert 输出累加回原来的 Token 位置。

因此整行代码本质上就是在实现：

\[
\boxed{
y_t
=
\sum_{i\in TopK(t)}
g_{t,i}E_i(x_t)
}
\]

## 31. 为什么不能简单写 `output[token_idx] = expert_output`？

因为这样是：

\[
\boxed{\text{覆盖}}
\]

假设：

```text
Token 0
```

先经过：

```text
Expert 1
```

结果：

\[
[1,2]
\]

如果：

```python
output[0] = [1,2]
```

然后 Token 0 又经过：

```text
Expert 5
```

得到：

\[
[3,4]
\]

再执行：

```python
output[0] = [3,4]
```

那么：

```text
Expert 1 的结果没了
```

最后只剩：

\[
[3,4]
\]

这是错误的。

我们真正需要：

\[
[1,2]+[3,4]
=
[4,6]
\]

所以需要：

```python
index_add_
```

而不是简单赋值。

## 32. 一句话记住 `index_add_`

核心关系如下：

\[
\boxed{
\texttt{index\_add\_}
=
\text{根据索引，把结果“加回”原来的位置}
}
\]

在 MoE 中：

\[
\boxed{
\text{不同 Expert 的输出最终要加回对应 Token}
}
\]

所以它非常适合实现 Expert 输出聚合。
