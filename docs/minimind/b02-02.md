# 11 · Loss Scaling：梯度传播与数值保护

<a id="origin-2970"></a>
## 1. Loss Scaling 为什么只给 Loss 乘一个系数，就能保护整个 Backward？

理解 Loss Scaling，最关键的不是最终的 `parameter.grad`，而是：

> **Backward 过程中存在大量“中间梯度”，这些中间梯度可能以 FP16 参与计算，因此可能在到达 FP32 的 `.grad` 之前就已经下溢成 0。**

Loss Scaling 真正主要保护的，就是这些 **Backward 中间梯度**。

---

<a id="origin-2980"></a>
## 2. 先明确：FP16 在 Backward 阶段到底干什么？

混合精度训练中，FP16 并不是只用于 Forward。

Backward 本身也需要做大量矩阵运算。

例如一个最简单的线性层：

```math
Y=XW
```

Forward 要计算：

```math
Y=XW
```

Backward 时需要计算两个重要梯度：

```math
\frac{\partial L}{\partial X}
=
\frac{\partial L}{\partial Y}W^T
```

以及：

```math
\frac{\partial L}{\partial W}
=
X^T\frac{\partial L}{\partial Y}
```

这两个式子本质上也都是大型矩阵乘法。

所以：

```text
Forward
X @ W
    ↓
可以使用 FP16 / Tensor Core
    ↓
加速计算

Backward
dY @ Wᵀ
Xᵀ @ dY
    ↓
同样包含大量矩阵乘
    ↓
也可以使用低精度计算
```

因此 FP16 在 Backward 中的主要作用仍然是：

```text
更快
+
减少带宽和显存压力
+
利用 Tensor Core
```

但是随之而来的问题就是：

> **Backward 中的梯度通常非常小，FP16 表示范围有限，小梯度可能下溢。**

---

<a id="origin-3051"></a>
## 3. 最终 `.grad` 是 FP32，为什么还会有问题？

这是最容易困惑的地方。

假设模型参数：

```python
W.dtype == torch.float32
```

那么很多普通 AMP 训练场景下：

```python
W.grad.dtype == torch.float32
```

也就是说最终用于 optimizer 的参数梯度通常会累积在 FP32 中。

于是很容易产生一个想法：

> 最后都是 FP32 存梯度，那 FP16 下溢有什么关系？

问题是：

> **梯度在到达最终 FP32 `.grad` 之前，还需要经过一长串 Backward 中间计算。**

如果中途已经丢失，FP32 再精确也救不回来。

---

<a id="origin-3081"></a>
## 4. 什么叫 Backward 中间梯度？

假设网络结构：

```text
x
↓
Layer1
↓
h1
↓
Layer2
↓
h2
↓
Layer3
↓
y
↓
Loss
```

Backward 从 Loss 开始：

```text
Loss
 ↑
dL/dy
 ↑
Layer3
 ↑
dL/dh2
 ↑
Layer2
 ↑
dL/dh1
 ↑
Layer1
 ↑
dL/dx
```

其中：

```math
\frac{\partial L}{\partial y}
```

```math
\frac{\partial L}{\partial h_2}
```

```math
\frac{\partial L}{\partial h_1}
```

都属于：

> **中间梯度**

它们不是最终某个参数的 `.grad`，而是：

> 用来继续向前传播梯度的临时梯度信号。

---

<a id="origin-3147"></a>
## 5. 以一个线性层为例看得最清楚

假设：

```math
Y=XW
```

Backward 时，上游先传下来：

```math
G_Y
=
\frac{\partial L}{\partial Y}
```

然后这一层计算：

```math
G_X
=
\frac{\partial L}{\partial X}
=
G_YW^T
```

同时：

```math
G_W
=
\frac{\partial L}{\partial W}
=
X^TG_Y
```

整个流程：

```text
上游传来的梯度
G_Y = dL/dY
        │
        ├──────────────┐
        │              │
        ▼              ▼

G_Y @ Wᵀ           Xᵀ @ G_Y

        │              │
        ▼              ▼

G_X = dL/dX       G_W = dL/dW

        │              │
        ▼              ▼

继续向前传播      累积到 W.grad
                  通常最终是 FP32
```

这里真正危险的是左边：

```text
G_Y
↓
G_X
↓
下一层的中间梯度
↓
再下一层的中间梯度
```

这些中间梯度可能在低精度路径中参与计算。

---

<a id="origin-3223"></a>
## 6. FP16 下溢发生在哪里？

假设某个中间梯度：

```math
G_Y
=
3\times10^{-8}
```

这个数字非常小。

如果它在某个 FP16 运算路径中无法被正常表示，就可能：

```math
3\times10^{-8}
\rightarrow
0
```

于是后面：

```math
G_X
=
G_YW^T
```

就变成：

```math
G_X
=
0\times W^T
=
0
```

同样：

```math
G_W
=
X^TG_Y
```

也可能变成：

```math
G_W
=
X^T\times0
=
0
```

于是整个过程变成：

```text
真实中间梯度

3 × 10⁻⁸

    ↓

FP16 中间计算

    ↓

下溢成 0

    ↓

后面所有计算看到的都是 0

    ↓

最终存进 FP32 .grad

    ↓

仍然是 0
```

因此：

> **FP32 最终存储梯度，并不能挽救已经在 FP16 Backward 中间过程里丢失的梯度。**

---

<a id="origin-3313"></a>
## 7. 所以 Loss Scaling 真正要保护什么？

主要不是保护最终：

```python
W.grad
```

而是保护：

```text
Loss
↓
中间梯度
↓
中间梯度
↓
中间梯度
↓
……
↓
最终参数梯度
```

也就是：

> **从 Loss 一路反向传播到各个参数 `.grad` 之前的那些中间梯度。**

---

<a id="origin-3343"></a>
## 8. 那为什么只给一个 Loss 标量乘 1024 就够了？

假设原来的 Loss：

```math
L
```

我们不直接做：

```python
loss.backward()
```

而是：

```python
scaler.scale(loss).backward()
```

假设：

```math
S=1024
```

那么相当于构造：

```math
L'=SL
```

即：

```math
L'=1024L
```

关键来了。

假设我们要求：

```math
\frac{\partial L'}{\partial W}
```

那么：

```math
\frac{\partial L'}{\partial W}
=
\frac{\partial (SL)}{\partial W}
```

因为：

```math
S
```

是常数，所以：

```math
\frac{\partial L'}{\partial W}
=
S\frac{\partial L}{\partial W}
```

即：

```math
\boxed{
\frac{\partial L'}{\partial W}
=
S
\frac{\partial L}{\partial W}
}
```

所以只要：

```math
Loss\times1024
```

最终所有梯度都会自动：

```math
\times1024
```

---

<a id="origin-3436"></a>
## 9. 为什么“所有中间梯度”也会一起放大？

这里才是 Loss Scaling 最核心的地方。

假设计算图：

```text
W
↓
h1
↓
h2
↓
y
↓
L
```

正常 Backward：

```math
\frac{\partial L}{\partial W}
=
\frac{\partial L}{\partial y}
\frac{\partial y}{\partial h_2}
\frac{\partial h_2}{\partial h_1}
\frac{\partial h_1}{\partial W}
```

现在把：

```math
L
```

改成：

```math
L'=SL
```

首先：

```math
\frac{\partial L'}{\partial y}
=
\frac{\partial (SL)}{\partial y}
=
S\frac{\partial L}{\partial y}
```

所以第一个中间梯度直接被放大：

```math
\frac{\partial L'}{\partial y}
=
S
\frac{\partial L}{\partial y}
```

继续向前：

```math
\frac{\partial L'}{\partial h_2}
=
\frac{\partial L'}{\partial y}
\frac{\partial y}{\partial h_2}
```

代入：

```math
\frac{\partial L'}{\partial h_2}
=
S
\frac{\partial L}{\partial y}
\frac{\partial y}{\partial h_2}
```

所以：

```math
\frac{\partial L'}{\partial h_2}
=
S
\frac{\partial L}{\partial h_2}
```

继续：

```math
\frac{\partial L'}{\partial h_1}
=
S
\frac{\partial L}{\partial h_1}
```

最后：

```math
\frac{\partial L'}{\partial W}
=
S
\frac{\partial L}{\partial W}
```

因此：

```text
Loss × S

    ↓

dL/dy × S

    ↓

dL/dh2 × S

    ↓

dL/dh1 × S

    ↓

dL/dW × S
```

也就是说：

> **Scale 不是只影响最终梯度，而是会顺着链式法则，把整条 Backward 路径中的中间梯度一起放大。**

---

<a id="origin-3570"></a>
## 10. 可以把 Loss Scaling 理解成在 Backward 入口放一个总放大器

正常情况下：

```text
Loss
 │
 ▼
dL/dy
 │
 ▼
dL/dh2
 │
 ▼
dL/dh1
 │
 ▼
dL/dW
```

加入 Loss Scaling：

```text
Loss
 │
 │ × 1024
 ▼
Scaled Loss
 │
 ▼
1024 × dL/dy
 │
 ▼
1024 × dL/dh2
 │
 ▼
1024 × dL/dh1
 │
 ▼
1024 × dL/dW
```

所以完全没有必要手工写：

```text
每个梯度 × 1024
```

只需要在最顶端：

```math
L'=1024L
```

链式法则就自动帮你完成整条反向传播的缩放。

---

<a id="origin-3628"></a>
## 11. 一个具体数字例子

假设某个中间梯度本来是：

```math
\frac{\partial L}{\partial h}
=
3\times10^{-8}
```

如果直接用低精度 Backward：

```text
3 × 10⁻⁸
↓
FP16
↓
可能下溢
↓
0
```

现在使用：

```math
S=1024
```

那么：

```math
L'=1024L
```

所以：

```math
\frac{\partial L'}{\partial h}
=
1024
\times
3\times10^{-8}
```

得到：

```math
3.072\times10^{-5}
```

于是：

```text
原中间梯度：

3 × 10⁻⁸

    ↓ × 1024

3.072 × 10⁻⁵

    ↓

FP16 更容易表示

    ↓

Backward 继续正常传播
```

这就是 Loss Scaling 的核心。

<a id="origin-3702"></a>
## 12. 最终为什么还要 Unscale？

因为：

```math
L'=SL
```

之后得到的是放大的梯度：

```math
g'=Sg
```

比如真实梯度：

```math
g=0.002
```

Scale：

```math
S=1024
```

Backward 后：

```math
g'
=
2.048
```

但真正更新参数时显然不能用：

```math
2.048
```

因为我们真正想要的是：

```math
0.002
```

所以在参数更新之前：

```math
g
=
\frac{g'}{S}
```

即：

```math
g
=
\frac{2.048}{1024}
=
0.002
```

这就是：

```python
scaler.unscale_(optimizer)
```

做的事情。

---

<a id="origin-3776"></a>
## 13. 整个完整流程

假设真实中间梯度非常小：

```math
3\times10^{-8}
```

正常 FP16 Backward：

```text
Loss
 ↓
Backward
 ↓
中间梯度
3 × 10⁻⁸
 ↓
FP16 下溢
 ↓
0
 ↓
后面梯度信息全部丢失
```

Loss Scaling 后：

```text
Loss
 ↓
× 1024
 ↓
Scaled Loss
 ↓
Backward
 ↓
所有中间梯度自动 × 1024
 ↓
3.072 × 10⁻⁵
 ↓
避免过早下溢
 ↓
梯度正常传播
 ↓
最终参数梯度累积
 ↓
unscale
 ↓
÷ 1024
 ↓
恢复真实梯度
 ↓
optimizer.step()
```

<a id="origin-3831"></a>
## 14. 为什么没有 `clip_grad_norm_()` 可以不写 `unscale_()`，有了就要写？

核心原因只有一句话：

> `scaler.step(optimizer)` 在真正执行 `optimizer.step()` 之前，本来就会自动执行 `unscale`；但 `clip_grad_norm_()` 发生在 `scaler.step()` 之前，因此如果想让它裁剪“真实梯度”，就必须提前手动 `unscale_()`。

---

<a id="origin-3839"></a>
## 15. 先看 Loss Scaling 做了什么

假设真实的 loss 为：

```math
L
```

GradScaler 当前的缩放倍数为：

```math
S=1024
```

代码：

```python
scaler.scale(loss).backward()
```

实际上相当于先计算：

```math
L'=SL
```

然后对：

```math
L'
```

进行反向传播。

原本真实梯度为：

```math
g=\frac{\partial L}{\partial W}
```

放大 loss 之后得到：

```math
g'
=
\frac{\partial (SL)}{\partial W}
=
S\frac{\partial L}{\partial W}
=
Sg
```

也就是说：

```text
真实梯度 g
    ↓
乘以 Scale
    ↓
Scaled Gradient = Sg
```

例如：

```math
g=0.002
```

如果：

```math
S=1024
```

那么反向传播之后 `.grad` 里面保存的是：

```math
g'
=
1024\times0.002
=
2.048
```

因此此时：

```python
parameter.grad
```

里面看到的并不是：

```text
0.002
```

而是：

```text
2.048
```

---

<a id="origin-3943"></a>
## 16. 没有 `clip_grad_norm_()` 时为什么不用手动 `unscale_()`？

正常的 AMP 代码可以写成：

```python
scaler.scale(loss).backward()

scaler.step(optimizer)

scaler.update()
```

这里没有显式写：

```python
scaler.unscale_(optimizer)
```

但代码依然是正确的。

因为：

```python
scaler.step(optimizer)
```

内部会帮我们完成必要的 `unscale`。

可以近似理解为：

```python
def scaler_step(optimizer):

    if optimizer 还没有被 unscale:
        unscale_(optimizer)

    检查梯度中是否存在 inf / nan

    if 梯度正常:
        optimizer.step()
```

因此：

```python
scaler.step(optimizer)
```

并不是简单等价于：

```python
optimizer.step()
```

而更像是：

```text
恢复真实梯度
+
检查 Inf / NaN
+
optimizer.step()
```

---

<a id="origin-4009"></a>
## 17. `scaler.step()` 到底是怎么自动恢复梯度的？

假设：

```math
S=1024
```

真实梯度：

```math
g=0.002
```

反向传播后得到：

```math
g'=Sg
```

即：

```math
g'
=
1024\times0.002
=
2.048
```

此时：

```text
.grad = 2.048
```

GradScaler 自己知道当前：

```text
scale = 1024
```

所以 `scaler.step()` 内部可以执行：

```math
g
=
\frac{g'}{S}
```

即：

```math
g
=
\frac{2.048}{1024}
=
0.002
```

于是整个过程为：

```text
真实梯度
0.002

    ↓ × 1024

Scaled Gradient
2.048

    ↓ scaler.step()

内部执行：
2.048 / 1024

    ↓

真实梯度
0.002

    ↓

optimizer.step()
```

因此所谓：

> `scaler.step()` 自动恢复梯度

本质上没有什么神秘的。

就是：

> GradScaler 知道自己之前把 loss 放大了多少倍，因此在参数更新前，再把梯度除以相同的倍数。

---

<a id="origin-4107"></a>
## 18. 所以没有梯度裁剪时可以直接这样写

```python
scaler.scale(loss).backward()

scaler.step(optimizer)

scaler.update()
```

执行过程：

```text
loss
 │
 │ × Scale
 ▼
scaled_loss
 │
 │ backward()
 ▼
scaled gradient
 │
 │
 ▼
scaler.step(optimizer)
 │
 ├── 自动 unscale
 │
 ▼
真实 gradient
 │
 ├── 检查 Inf / NaN
 │
 ▼
optimizer.step()
```

这里没有任何代码需要在：

```python
backward()
```

和：

```python
scaler.step()
```

之间读取或者修改真实梯度。

所以：

> 没有必要提前手动 `unscale_()`。

## 19. 加入 `clip_grad_norm_()` 后，问题出现了

现在我们想限制梯度范数：

```python
torch.nn.utils.clip_grad_norm_(
    model.parameters(),
    max_norm=1.0
)
```

假设真实梯度仍然是：

```math
g=0.002
```

显然：

```math
0.002<1
```

这个梯度其实根本不应该被裁剪。

但是经过 Loss Scaling：

```math
S=1024
```

反向传播之后：

```math
g'
=
1024\times0.002
=
2.048
```

此时 `.grad` 里面是：

```text
2.048
```

<a id="origin-4214"></a>
## 20. 如果直接 Clip 会发生什么？

如果这样写：

```python
scaler.scale(loss).backward()

torch.nn.utils.clip_grad_norm_(
    model.parameters(),
    max_norm=1.0
)

scaler.step(optimizer)
scaler.update()
```

那么 `clip_grad_norm_()` 读取到的是：

```text
2.048
```

而不是：

```text
0.002
```

于是它看到：

```math
2.048>1
```

就会认为：

> 梯度太大了，需要裁剪。

但是实际上真实梯度：

```math
0.002
```

根本不大。

也就是说：

```text
真实梯度：

0.002
```

本来应该：

```text
不裁剪
```

但是因为 Loss Scaling：

```text
0.002
   ↓ ×1024
2.048
```

`clip_grad_norm_()` 错误地看到：

```text
2.048 > 1
```

于是进行了不该进行的裁剪。

---

<a id="origin-4292"></a>
## 21. 所以必须在 Clip 之前先恢复真实梯度

正确写法：

```python
scaler.scale(loss).backward()

scaler.unscale_(optimizer)

torch.nn.utils.clip_grad_norm_(
    model.parameters(),
    max_norm=1.0
)

scaler.step(optimizer)

scaler.update()
```

执行过程：

```text
真实梯度
0.002

    ↓ Loss Scaling

Scaled Gradient
2.048

    ↓ scaler.unscale_(optimizer)

真实梯度
0.002

    ↓ clip_grad_norm_()

按照真实梯度判断是否需要裁剪

    ↓

scaler.step(optimizer)

    ↓

optimizer.step()
```

<a id="origin-4342"></a>
## 22. `unscale_()` 的真正目的是什么？

这里非常容易产生一个误解：

> 是不是因为 `optimizer.step()` 必须使用真实梯度，所以必须手动 `unscale_()`？

并不是。

因为：

```python
scaler.step(optimizer)
```

本身就会自动完成 `unscale`。

真正的问题是：

```python
clip_grad_norm_()
```

发生在：

```python
scaler.step()
```

之前。

因此：

> 如果想在 `scaler.step()` 之前对梯度进行任何依赖真实数值的操作，就需要提前把梯度恢复回来。

所以真正的逻辑是：

```text
不是 optimizer.step() 需要手动 unscale

而是 clip_grad_norm_() 需要看到真实梯度
```

---

<a id="origin-4386"></a>
## 23. 为什么 `clip_grad_norm_()` 自己不能自动 `unscale`？

因为：

```python
torch.nn.utils.clip_grad_norm_()
```

本身完全不知道 GradScaler 的存在。

它接收到的只有：

```python
model.parameters()
```

以及：

```python
max_norm
```

例如：

```python
torch.nn.utils.clip_grad_norm_(
    model.parameters(),
    1.0
)
```

它做的事情非常简单：

```text
读取 parameter.grad
        ↓
计算 Gradient Norm
        ↓
判断是否超过 max_norm
        ↓
如果超过，就缩小梯度
```

它并不知道：

```text
你有没有用 AMP

你有没有使用 GradScaler

scale 是多少

当前 gradient 有没有被 scale

应该除以多少
```

例如它根本不知道当前：

```text
scale = 1024
```

还是：

```text
scale = 65536
```

因此：

> `clip_grad_norm_()` 没有能力自动执行 `unscale`。

---

<a id="origin-4461"></a>
## 24. 那手动 `unscale_()` 后，`scaler.step()` 不会又除一次吗？

不会。

例如我们写：

```python
scaler.scale(loss).backward()

scaler.unscale_(optimizer)

torch.nn.utils.clip_grad_norm_(
    model.parameters(),
    1.0
)

scaler.step(optimizer)
```

可能会担心：

```text
第一次：

2.048 / 1024
=
0.002
```

然后 `scaler.step()` 再执行一次：

```text
0.002 / 1024
```

这样梯度岂不是又变小了？

实际上不会。

<a id="origin-4502"></a>
## 25. GradScaler 会记录当前 optimizer 是否已经 unscale

当你执行：

```python
scaler.unscale_(optimizer)
```

之后，GradScaler 会记录：

```text
这个 optimizer 的梯度已经 unscale 过了
```

因此后面执行：

```python
scaler.step(optimizer)
```

时，可以近似理解为：

```python
if optimizer 没有执行过 unscale:
    scaler.unscale_(optimizer)

optimizer.step()
```

如果之前已经：

```python
scaler.unscale_(optimizer)
```

那么就：

```text
跳过第二次 unscale
```

因此不存在重复除法。


更准确的理解应该是：

```text
只要你需要在 scaler.step() 之前

```

```python
clip_grad_norm_()
```

<a id="origin-4733"></a>
## 29. 最终总结

正常情况下：

```python
scaler.scale(loss).backward()
scaler.step(optimizer)
```

完全可以，因为：

```text
scaler.step()
=
自动 unscale
+
Inf / NaN 检查
+
optimizer.step()
```

但是如果中间需要：

```python
clip_grad_norm_()
```

就必须变成：

```python
scaler.scale(loss).backward()

scaler.unscale_(optimizer)

clip_grad_norm_()

scaler.step(optimizer)
```

原因是：

> `clip_grad_norm_()` 必须根据真实梯度进行裁剪，而不能根据 Loss Scaling 之后被人为放大的梯度进行裁剪。

所以最终可以记成：

```text
没有 Clip：

backward
    ↓
scaled gradient
    ↓
scaler.step
    ↓
自动 unscale
    ↓
optimizer.step
```

而有 Clip：

```text
backward
    ↓
scaled gradient
    ↓
手动 unscale
    ↓
真实 gradient
    ↓
clip
    ↓
scaler.step
    ↓
optimizer.step
```

最核心的一句话：

> **`unscale_()` 不是为了帮助 `optimizer.step()`，而是为了让发生在 `scaler.step()` 之前的梯度操作能够看到真实梯度。**


<a id="origin-4815"></a>
## 30. Loss Scaling 为什么只给 Loss 乘一个系数，就能保护整个 Backward？

理解 Loss Scaling，最关键的不是最终的 `parameter.grad`，而是：

> **Backward 过程中存在大量“中间梯度”，这些中间梯度可能以 FP16 参与计算，因此可能在到达 FP32 的 `.grad` 之前就已经下溢成 0。**

Loss Scaling 真正主要保护的，就是这些 **Backward 中间梯度**。

---

<a id="origin-4825"></a>
## 31. 先明确：FP16 在 Backward 阶段到底干什么？

混合精度训练中，FP16 并不是只用于 Forward。

Backward 本身也需要做大量矩阵运算。

例如一个最简单的线性层：

```math
Y=XW
```

Forward 要计算：

```math
Y=XW
```

Backward 时需要计算两个重要梯度：

```math
\frac{\partial L}{\partial X}
=
\frac{\partial L}{\partial Y}W^T
```

以及：

```math
\frac{\partial L}{\partial W}
=
X^T\frac{\partial L}{\partial Y}
```

这两个式子本质上也都是大型矩阵乘法。

所以：

```text
Forward
X @ W
    ↓
可以使用 FP16 / Tensor Core
    ↓
加速计算

Backward
dY @ Wᵀ
Xᵀ @ dY
    ↓
同样包含大量矩阵乘
    ↓
也可以使用低精度计算
```

因此 FP16 在 Backward 中的主要作用仍然是：

```text
更快
+
减少带宽和显存压力
+
利用 Tensor Core
```

但是随之而来的问题就是：

> **Backward 中的梯度通常非常小，FP16 表示范围有限，小梯度可能下溢。**

---

<a id="origin-4896"></a>
## 32. 最终 `.grad` 是 FP32，为什么还会有问题？

这是最容易困惑的地方。

假设模型参数：

```python
W.dtype == torch.float32
```

那么很多普通 AMP 训练场景下：

```python
W.grad.dtype == torch.float32
```

也就是说最终用于 optimizer 的参数梯度通常会累积在 FP32 中。

于是很容易产生一个想法：

> 最后都是 FP32 存梯度，那 FP16 下溢有什么关系？

问题是：

> **梯度在到达最终 FP32 `.grad` 之前，还需要经过一长串 Backward 中间计算。**

如果中途已经丢失，FP32 再精确也救不回来。

---

<a id="origin-4926"></a>
## 33. 什么叫 Backward 中间梯度？

假设网络结构：

```text
x
↓
Layer1
↓
h1
↓
Layer2
↓
h2
↓
Layer3
↓
y
↓
Loss
```

Backward 从 Loss 开始：

```text
Loss
 ↑
dL/dy
 ↑
Layer3
 ↑
dL/dh2
 ↑
Layer2
 ↑
dL/dh1
 ↑
Layer1
 ↑
dL/dx
```

其中：

```math
\frac{\partial L}{\partial y}
```

```math
\frac{\partial L}{\partial h_2}
```

```math
\frac{\partial L}{\partial h_1}
```

都属于：

> **中间梯度**

它们不是最终某个参数的 `.grad`，而是：

> 用来继续向前传播梯度的临时梯度信号。

---

<a id="origin-4992"></a>
## 34. 以一个线性层为例看得最清楚

假设：

```math
Y=XW
```

Backward 时，上游先传下来：

```math
G_Y
=
\frac{\partial L}{\partial Y}
```

然后这一层计算：

```math
G_X
=
\frac{\partial L}{\partial X}
=
G_YW^T
```

同时：

```math
G_W
=
\frac{\partial L}{\partial W}
=
X^TG_Y
```

整个流程：

```text
上游传来的梯度
G_Y = dL/dY
        │
        ├──────────────┐
        │              │
        ▼              ▼

G_Y @ Wᵀ           Xᵀ @ G_Y

        │              │
        ▼              ▼

G_X = dL/dX       G_W = dL/dW

        │              │
        ▼              ▼

继续向前传播      累积到 W.grad
                  通常最终是 FP32
```

这里真正危险的是左边：

```text
G_Y
↓
G_X
↓
下一层的中间梯度
↓
再下一层的中间梯度
```

这些中间梯度可能在低精度路径中参与计算。

---

<a id="origin-5068"></a>
## 35. FP16 下溢发生在哪里？

假设某个中间梯度：

```math
G_Y
=
3\times10^{-8}
```

这个数字非常小。

如果它在某个 FP16 运算路径中无法被正常表示，就可能：

```math
3\times10^{-8}
\rightarrow
0
```

于是后面：

```math
G_X
=
G_YW^T
```

就变成：

```math
G_X
=
0\times W^T
=
0
```

同样：

```math
G_W
=
X^TG_Y
```

也可能变成：

```math
G_W
=
X^T\times0
=
0
```

于是整个过程变成：

```text
真实中间梯度

3 × 10⁻⁸

    ↓

FP16 中间计算

    ↓

下溢成 0

    ↓

后面所有计算看到的都是 0

    ↓

最终存进 FP32 .grad

    ↓

仍然是 0
```

因此：

> **FP32 最终存储梯度，并不能挽救已经在 FP16 Backward 中间过程里丢失的梯度。**

---

<a id="origin-5158"></a>
## 36. 所以 Loss Scaling 真正要保护什么？

主要不是保护最终：

```python
W.grad
```

而是保护：

```text
Loss
↓
中间梯度
↓
中间梯度
↓
中间梯度
↓
……
↓
最终参数梯度
```

也就是：

> **从 Loss 一路反向传播到各个参数 `.grad` 之前的那些中间梯度。**

<a id="origin-5188"></a>
## 37. 那为什么只给一个 Loss 标量乘 1024 就够了？

假设原来的 Loss：

```math
L
```

我们不直接做：

```python
loss.backward()
```

而是：

```python
scaler.scale(loss).backward()
```

假设：

```math
S=1024
```

那么相当于构造：

```math
L'=SL
```

即：

```math
L'=1024L
```

关键来了。

假设我们要求：

```math
\frac{\partial L'}{\partial W}
```

那么：

```math
\frac{\partial L'}{\partial W}
=
\frac{\partial (SL)}{\partial W}
```

因为：

```math
S
```

是常数，所以：

```math
\frac{\partial L'}{\partial W}
=
S\frac{\partial L}{\partial W}
```

即：

```math
\boxed{
\frac{\partial L'}{\partial W}
=
S
\frac{\partial L}{\partial W}
}
```

所以只要：

```math
Loss\times1024
```

最终所有梯度都会自动：

```math
\times1024
```

<a id="origin-5281"></a>
## 38. 为什么“所有中间梯度”也会一起放大？

这里才是 Loss Scaling 最核心的地方。

假设计算图：

```text
W
↓
h1
↓
h2
↓
y
↓
L
```

正常 Backward：

```math
\frac{\partial L}{\partial W}
=
\frac{\partial L}{\partial y}
\frac{\partial y}{\partial h_2}
\frac{\partial h_2}{\partial h_1}
\frac{\partial h_1}{\partial W}
```

现在把：

```math
L
```

改成：

```math
L'=SL
```

首先：

```math
\frac{\partial L'}{\partial y}
=
\frac{\partial (SL)}{\partial y}
=
S\frac{\partial L}{\partial y}
```

所以第一个中间梯度直接被放大：

```math
\frac{\partial L'}{\partial y}
=
S
\frac{\partial L}{\partial y}
```

继续向前：

```math
\frac{\partial L'}{\partial h_2}
=
\frac{\partial L'}{\partial y}
\frac{\partial y}{\partial h_2}
```

代入：

```math
\frac{\partial L'}{\partial h_2}
=
S
\frac{\partial L}{\partial y}
\frac{\partial y}{\partial h_2}
```

所以：

```math
\frac{\partial L'}{\partial h_2}
=
S
\frac{\partial L}{\partial h_2}
```

继续：

```math
\frac{\partial L'}{\partial h_1}
=
S
\frac{\partial L}{\partial h_1}
```

最后：

```math
\frac{\partial L'}{\partial W}
=
S
\frac{\partial L}{\partial W}
```

因此：

```text
Loss × S

    ↓

dL/dy × S

    ↓

dL/dh2 × S

    ↓

dL/dh1 × S

    ↓

dL/dW × S
```

也就是说：

> **Scale 不是只影响最终梯度，而是会顺着链式法则，把整条 Backward 路径中的中间梯度一起放大。**

## 39. 可以把 Loss Scaling 理解成在 Backward 入口放一个总放大器

正常情况下：

```text

 │
 ▼
dL/dy
 │
 ▼
dL/dh2
 │
 ▼
dL/dh1
 │
 ▼
dL/dW
```

加入 Loss Scaling：

```text
 │
 ▼
1024 × dL/dh1

 ▼
```

所以完全没有必要手工写：



链式法则就自动帮你完成整条反向传播的缩放。

## 43. 和 FP32 `.grad` 的关系

可以把混合精度 Backward 粗略分成三类数据：

| 数据                     | 常见情况             | 作用               |
| ---------------------- | ---------------- | ---------------- |
| Forward 保存的 Activation | FP16/BF16 或 FP32 | Backward 时重新计算梯度 |
| Backward 中间梯度          | 可能参与低精度计算        | 将梯度继续向前传播        |
| 参数 `.grad`             | FP32 参数时通常为 FP32 | 最终用于 Optimizer   |

因此：

```text
FP16 / 低精度最危险的地方
        ↓
不是只有最终 .grad
        ↓
而是整个 Backward 中间梯度传播过程
```

## 45. 为什么最后 FP32 保存还不够？

因为如果中间已经：

```text
3 × 10⁻⁸
↓
FP16
↓
0
```

那么后面：

```text
0
↓
转换为 FP32
↓
0.000000
```

FP32 并不会神奇地恢复成：

```text
3 × 10⁻⁸
```

所以：

> **FP32 只能准确保存“已经算出来的梯度”，不能恢复“已经在 FP16 中丢失的梯度”。**

## 46. Loss Scaling 真正解决的问题

因此不要把 Loss Scaling 简单理解成：

> 把最终梯度放大。

更准确的理解是：

> **Loss Scaling 在 Backward 开始之前，把整个梯度信号整体抬高，从而让 Backward 中那些需要参与低精度计算的中间梯度，不那么容易在传播过程中下溢成 0。**

<a id="origin-5817"></a>
## 47. 为什么只乘 Loss 一个标量就足够？

因为整个神经网络训练最终只有一个标量目标：

```math
L
```

所有梯度：

```math
\frac{\partial L}{\partial W_1}
```

```math
\frac{\partial L}{\partial W_2}
```

```math
\frac{\partial L}{\partial h_1}
```

```math
\frac{\partial L}{\partial h_2}
```

本质上全部是：

> “这个变量发生一点变化，会对最终 Loss 产生多大影响？”

因此只要把：

```math
L
```

变成：

```math
SL
```

那么所有：

```math
\frac{\partial L}{\partial(\cdot)}
```

自然都会变成：

```math
S
\frac{\partial L}{\partial(\cdot)}
```

即：

```math
\boxed{
L'=SL
}
```

直接导致：

```math
\boxed{
\frac{\partial L'}{\partial z}
=
S
\frac{\partial L}{\partial z}
}
```

这里的：

```math
z
```

可以是：

```text
参数 W
Activation h
中间输出 y
任何计算图中的变量
```

## 48. 最终一句话总结

Loss Scaling 不是主要为了：

```text
把最终 FP32 .grad 放大
```

而是为了：

```text
Loss × Scale
        ↓
整条 Backward 的梯度信号一起被放大
        ↓
中间梯度不容易在 FP16 计算阶段下溢
        ↓
梯度成功传播到各层
        ↓
最终累积到 FP32 .grad
        ↓
unscale
        ↓
恢复真实梯度
```

最值得记住的两个公式：

```math
\boxed{L'=SL}
```

以及：

```math
\boxed{
\frac{\partial L'}{\partial z}
=
S
\frac{\partial L}{\partial z}
}
```

所以：

> **只需要给 Loss 这个标量乘一个 Scale，就能够通过链式法则自动把整个 Backward 中所有中间梯度一起放大，这正是 Loss Scaling 能够缓解 FP16 Backward 中间梯度下溢问题的根本原因。**
