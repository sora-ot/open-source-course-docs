# 41 · 推理：KV Cache 调用链与流式输出

<a id="origin-2785"></a>
## 1. MiniMind 中 KV Cache 的完整原理与代码流程

<a id="origin-2787"></a>
## 2. 先给出最重要的结论

在这份 MiniMind 代码中，KV Cache 的核心不是改变 Attention 的公式，而是：

> **历史 token 不再重复送进 Transformer 计算，而是直接复用它们之前已经计算好的 K 和 V。**

Attention 公式始终还是：

```math
\operatorname{Attention}(Q,K,V)
=
\operatorname{softmax}
\left(
\frac{QK^T}{\sqrt{d}}
\right)V
```

真正发生变化的是参与计算的矩阵尺寸。

不使用 KV Cache 时，假设当前上下文长度为 $T$：

```text
Q: T × d
K: T × d
V: T × d
```

需要计算：

```math
QK^T
```

其大小为：

```text
T × T
```

而使用 KV Cache 后，在自回归 Decode 阶段，每次只输入一个新 token：

```text
Q_new: 1 × d
K_all: T × d
V_all: T × d
```

因此只需要计算：

```math
Q_{\text{new}}K_{\text{all}}^T
```

大小变成：

```text
1 × T
```

也就是说：

> **以前需要重新计算完整 Attention Score 矩阵，现在只需要计算新增的最后一行。**

---

<a id="origin-2852"></a>
## 3. MiniMind 中 KV Cache 涉及的完整调用链

代码中的调用关系是：

```text
generate()
    ↓
MiniMindForCausalLM.forward()
    ↓
MiniMindModel.forward()
    ↓
MiniMindBlock.forward()
    ↓
Attention.forward()
```

KV Cache 会沿着这条路径不断向下传递，然后再返回：

```text
generate
    │
    │ past_key_values
    ↓
MiniMindForCausalLM
    ↓
MiniMindModel
    ↓
每一个 Transformer Block
    ↓
Attention
    ↓
计算新的 K、V
    ↓
present_key_value
    ↓
presents
    ↓
outputs.past_key_values
    ↓
重新回到 generate
```

因此 KV Cache 本质上是一个循环：

```text
旧 KV Cache
    ↓
当前新 token
    ↓
Attention
    ↓
追加新的 K、V
    ↓
得到新的 KV Cache
    ↓
下一轮继续使用
```

---

<a id="origin-2912"></a>
## 4. 最关键的代码其实在 generate() 中

MiniMind 的生成代码中有：

```python
past_len = past_key_values[0][0].shape[1] if past_key_values else 0

outputs = self.forward(
    input_ids[:, past_len:],
    attention_mask,
    past_key_values,
    use_cache=use_cache,
    **kwargs
)
```

这里最重要的是：

```python
input_ids[:, past_len:]
```

它的含义是：

> **把已经通过 Transformer 计算过的历史 token 从本轮输入中切掉，只留下还没有计算过的新 token。**

这才是 KV Cache 能够避免重复计算的真正入口。

## 8. 第一轮没有历史 KV

代码：

```python
if past_key_value is not None:
    xk = torch.cat([past_key_value[0], xk], dim=1)
    xv = torch.cat([past_key_value[1], xv], dim=1)
```

第一次：

```text
past_key_value = None
```

所以这一段不会执行。

此时：

```text
K =
[K_BOS, K_I, K_love, K_AI]

V =
[V_BOS, V_I, V_love, V_AI]
```

<a id="origin-3106"></a>
## 9. 第一轮建立 KV Cache

代码：

```python
past_kv = (xk, xv) if use_cache else None
```

如果：

```python
use_cache=True
```

那么得到：

```text
past_kv =

(
    [K_BOS, K_I, K_love, K_AI],
    [V_BOS, V_I, V_love, V_AI]
)
```

也就是说：

> **第一次 Prefill 会把整个 Prompt 在当前 Transformer Layer 中产生的 K 和 V 保存下来。**

---

<a id="origin-3137"></a>
## 10. KV Cache 是每一层都有一份

这一点非常重要。

MiniMind 中：

```python
presents = []

for layer, past_key_value in zip(self.layers, past_key_values):
    hidden_states, present = layer(...)
    presents.append(present)
```

说明不是整个模型只有一个 KV Cache，而是：

```text
Layer 0:
K Cache
V Cache

Layer 1:
K Cache
V Cache

Layer 2:
K Cache
V Cache

...

Layer 7:
K Cache
V Cache
```

原因是不同层的 hidden state 不同，因此每一层产生的 K、V 也不同。

例如：

```math
K_i^{(1)} = H_i^{(0)}W_K^{(1)}
```

而第二层：

```math
K_i^{(2)} = H_i^{(1)}W_K^{(2)}
```

显然：

```math
K_i^{(1)} \neq K_i^{(2)}
```

所以每一层都必须单独缓存自己的 K 和 V。

<a id="origin-3197"></a>
## 11. 第一轮 Attention 是完整矩阵

第一次：

```text
Q 长度 = 4
K 长度 = 4
```

所以：

```math
QK^T
```

是：

```text
4 × 4
```

即：

```math
\begin{bmatrix}
Q_{BOS}\\
Q_I\\
Q_{love}\\
Q_{AI}
\end{bmatrix}
\begin{bmatrix}
K_{BOS}^T &
K_I^T &
K_{love}^T &
K_{AI}^T
\end{bmatrix}
```

得到：

```text
            BOS      I      love      AI

BOS          ✓
I            ✓       ✓
love         ✓       ✓       ✓
AI           ✓       ✓       ✓       ✓
```

通过 Causal Mask 保证每个位置只能看自己和之前的 token。

<a id="origin-3250"></a>
## 12. 第一轮最终只使用最后一个位置预测下一个 token

虽然第一次计算了所有位置：

```text
BOS
I
love
AI
```

但是 generate 中：

```python
logits = outputs.logits[:, -1, :]
```

只取最后一个位置：

```text
AI
```

对应的 logits。

也就是根据：

```text
BOS I love AI
```

预测下一个 token。

假设预测得到：

```text
is
```

那么：

```python
input_ids = torch.cat([input_ids, next_token], dim=-1)
```

于是完整 token 序列变成：

```text
[BOS, I, love, AI, is]
```

<a id="origin-3303"></a>
## 13. 注意：input_ids 仍然保存完整历史

这是很容易混淆的地方。

此时：

```text
input_ids =
[BOS, I, love, AI, is]
```

完整历史并没有被删除。

原因是完整 `input_ids` 还要用于：

- 最终返回完整生成结果；
- repetition penalty；
- tokenizer decode；
- streamer 输出；
- 保存完整上下文。

但是：

> **完整 input_ids 不代表下一轮会把全部 token 重新送进 Transformer。**

真正送入 Transformer 的内容由：

```python
input_ids[:, past_len:]
```

决定。

## 15. 第二轮只计算新 token 的 Q、K、V

第二轮：

```text

[B, 1, 768]
```

所以：

```python

xk = self.k_proj(x)
xv = self.v_proj(x)
```

只会计算：

```text
Q_is
K_is
V_is
```

不会重新计算：

```text

Q_I
Q_love

```

也不会重新计算：

```text

K_I
K_love
```

```text
V_love
V_AI
```

<a id="origin-3459"></a>
## 16. 历史 K、V 从 Cache 中取回来

Attention 中：

```python
if past_key_value is not None:
    xk = torch.cat([past_key_value[0], xk], dim=1)
    xv = torch.cat([past_key_value[1], xv], dim=1)
```

历史：

```text
past K =
[K_BOS, K_I, K_love, K_AI]

past V =
[V_BOS, V_I, V_love, V_AI]
```

当前新算：

```text
K_is
V_is
```

拼接以后：

```text
K =
[K_BOS, K_I, K_love, K_AI, K_is]

V =
[V_BOS, V_I, V_love, V_AI, V_is]
```

---

<a id="origin-3498"></a>
## 17. 为什么没有缓存 Q？

注意代码只有：

```python
xk = torch.cat(...)
xv = torch.cat(...)
```

没有：

```python
xq = torch.cat(...)
```

所以第二轮：

```text
Q =
[Q_is]

K =
[K_BOS, K_I, K_love, K_AI, K_is]

V =
[V_BOS, V_I, V_love, V_AI, V_is]
```

这是因为历史 Q 已经没有用了。

历史 Q 的作用，是在过去那一轮计算：

```text
“历史 token 自己应该关注谁？”
```

这些输出已经计算完成，没有必要再次计算。

当前真正需要解决的问题只有：

```text
“当前新 token is 应该关注历史中的谁？”
```

所以只需要：

```text
Q_is
```

但它需要和所有历史 K 做匹配，因此历史 K 必须保存。

Softmax 之后还要读取历史信息，因此历史 V 也必须保存。

所以：

> **KV Cache 缓存 K 和 V，而不是 Q。**

---

<a id="origin-3558"></a>
## 18. 第二轮 Attention Score 已经从矩阵变成“一行”

不用 KV Cache 时，第二轮如果重新输入：

```text
BOS I love AI is
```

则：

```text
Q:
5 × d

K:
5 × d
```

需要：

```math
QK^T
```

得到：

```text
5 × 5
```

而使用 KV Cache 后：

```text
Q:
1 × d

K:
5 × d
```

所以：

```math
Q_{is}K^T
```

得到：

```text
1 × 5
```

即：

```text
             BOS       I       love      AI       is

Q_is        score     score    score     score    score
```

所以 KV Cache 可以理解为：

> **原来整个 Attention Score 矩阵都重新计算，现在只计算新增的最后一行。**

---

<a id="origin-3624"></a>
## 19. Softmax 之后如何利用 V

得到：

```text
Q_is
```

与所有 K 的 Attention Score 后，经过 Softmax：

```math
[
\alpha_{BOS},
\alpha_I,
\alpha_{love},
\alpha_{AI},
\alpha_{is}
]
```

然后：

```math
O_{is}
=
\alpha_{BOS}V_{BOS}
+
\alpha_IV_I
+
\alpha_{love}V_{love}
+
\alpha_{AI}V_{AI}
+
\alpha_{is}V_{is}
```

因此：

> 虽然历史 token 没有重新输入模型，但当前 token 仍然能够通过历史 K/V 读取完整上下文信息。

## 21. 整个推理流程总结

MiniMind 的生成可以整理成：

```text
初始 Prompt：

[BOS, I, love, AI]

        ↓

========================
Prefill
========================

整个 Prompt 一次送入

Q: 4 个
K: 4 个
V: 4 个

Attention:
4 × 4

建立 KV Cache：

K_BOS K_I K_love K_AI
V_BOS V_I V_love V_AI

        ↓

预测 is

        ↓

========================
Decode 第 1 轮
========================

完整 input_ids：

[BOS, I, love, AI, is]

但是：

past_len = 4

所以真正输入：

[is]

只计算：

Q_is
K_is
V_is

Attention：

Q_is
×
[K_BOS K_I K_love K_AI K_is]^T

得到：

1 × 5

        ↓

预测 very

        ↓

========================
Decode 第 2 轮
========================

完整 input_ids：

[BOS, I, love, AI, is, very]

past_len = 5

真正输入：

[very]

Attention：

1 × 6
```

因此：

```math
\boxed{
\text{大模型推理}
=
\text{Prefill}
+
\text{逐 Token Decode}
}
```

## 22. Prefill 和 Decode 的区别

<a id="origin-3847"></a>
### 22.1 Prefill

Prompt 一次输入：

```text
[BOS, I, love, AI]
```

特点：

```text
seq_len > 1
```

Attention：

```text
T × T
```

主要任务：

```text
理解整个 Prompt
+
建立所有 Layer 的 KV Cache
```

---

<a id="origin-3877"></a>
### 22.2 Decode

之后每次：

```text
只输入一个新 token
```

例如：

```text
is
```

特点：

```text
seq_len = 1
```

Attention：

```text
1 × 当前总长度
```

主要任务：

```text
使用历史 KV Cache
+
计算当前新 token
+
生成下一个 token
```

## 23. RoPE 如何知道新 token 的真实位置？

第二轮虽然只输入：

```text
is
```

但它不能被当成 position 0。

MiniMind 中：

```python
start_pos = past_key_values[0][0].shape[1] if past_key_values[0] is not None else 0
```

第一轮缓存长度为：

```text
4
```

所以：

```text
start_pos = 4
```

然后：

```python
position_embeddings = (
    self.freqs_cos[start_pos:start_pos + seq_length],
    self.freqs_sin[start_pos:start_pos + seq_length]
)
```

第二轮：

```text
seq_length = 1
```

于是使用：

```text
position 4
```

所以实际位置仍然是：

```text
BOS   → 0
I     → 1
love  → 2
AI    → 3
is    → 4
very  → 5
```

虽然 Decode 每次只输入一个 token，但位置不会重新从 0 开始。

<a id="origin-3979"></a>
## 24. GQA 和 KV Cache 的关系

MiniMind 配置中：

```python
num_attention_heads = 8
num_key_value_heads = 4
```

所以：

```python
self.n_rep = 8 // 4
```

得到：

```text
n_rep = 2
```

说明：

```text
8 个 Query Head
共享
4 个 KV Head
```

也就是每一个 KV Head 被两个 Query Head 使用。

代码：

```python
repeat_kv(xk, self.n_rep)
repeat_kv(xv, self.n_rep)
```

会在 Attention 计算前把：

```text
4 个 KV Head
```

逻辑展开成：

```text
8 个 KV Head
```

但是注意：

```python
past_kv = (xk, xv)
```

发生在 `repeat_kv()` 之前。

因此真正存在 KV Cache 中的仍然只有：

```text
4 个 KV Head
```

而不是：

```text
8 个
```

这正是 GQA 能够降低 KV Cache 显存占用的重要原因之一。

<a id="origin-4053"></a>
## 25. presents 为什么叫 presents？

MiniMindModel 中：

```python
presents = []
```

然后：

```python
hidden_states, present = layer(...)
presents.append(present)
```

这里：

```text
past_key_values
```

表示：

> 进入当前 forward 之前已有的 KV Cache。

而：

```text
present_key_value
```

表示：

> 当前 forward 执行完成以后，更新后的完整 KV Cache。

例如：

```text
输入：

past KV =
K1 K2 K3 K4

当前新 token：

K5
```

执行后：

```text
present KV =
K1 K2 K3 K4 K5
```

然后：

```text
present
```

到了下一轮，又变成：

```text
past
```

所以：

```text
past
  ↓
当前 forward
  ↓
present
  ↓
下一轮
  ↓
past
```

因此 `present` 这个命名本身是合理的。

## 26. 训练阶段 KV Cache 基本没有用

这里一定要区分：

> **K、V 有用。**

和：

> **KV Cache 有用。**

这是两回事。

训练时 Attention 当然仍然必须计算：

```text
Q
K
V
```

但是通常：

```text
不需要缓存 K、V 给下一次 forward
```

<a id="origin-4166"></a>
## 27. 为什么训练不需要 KV Cache？

假设训练样本：

```text
[BOS, I, love, AI, very, much]
```

训练时通常一次全部输入：

```text
seq_len = 6
```

直接计算：

```text
Q1 ... Q6
K1 ... K6
V1 ... V6
```

然后通过 Causal Mask：

```text
BOS        ✓
I          ✓ ✓
love       ✓ ✓ ✓
AI         ✓ ✓ ✓ ✓
very       ✓ ✓ ✓ ✓ ✓
much       ✓ ✓ ✓ ✓ ✓ ✓
```

一次 forward 就可以同时训练：

```text
BOS                     → I
BOS I                   → love
BOS I love              → AI
BOS I love AI           → very
BOS I love AI very      → much
```

所以根本没有必要：

```text
先输入 BOS
↓
保存 KV

再输入 I
↓
保存 KV

再输入 love
↓
保存 KV
```

这种串行训练方式反而会失去 GPU 并行计算的优势。

---

<a id="origin-4229"></a>
## 28. MiniMind 训练时一般 use_cache=False

Attention 中：

```python
past_kv = (xk, xv) if use_cache else None
```

训练时通常：

```python
use_cache=False
```

于是：

```text
past_kv = None
```

虽然当前 forward 中仍然计算了：

```text
K
V
```

但不会把它们保存下来给下一轮使用。

所以最准确的说法是：

> **训练不是不计算 K、V，而是不需要 KV Cache。**

---

<a id="origin-4264"></a>
## 29. 为什么训练阶段缓存 K/V 反而不自然？

训练阶段需要反向传播。

例如：

```math
K=XW_K
```

```math
V=XW_V
```

Loss 最终还要沿着计算图反向传播：

```text
Loss
 ↓
Attention
 ↓
K / V
 ↓
W_K / W_V
```

也就是说：

```math
\frac{\partial L}{\partial W_K}
```

和：

```math
\frac{\partial L}{\partial W_V}
```

都需要正常计算。

而推理时：

```python
@torch.inference_mode()
```

不需要梯度：

```text
参数不会更新
```

所以历史 K/V 一旦计算完成，就可以直接保存并重复使用。

因此：

```math
\boxed{
\text{KV Cache 主要是一种推理优化，而不是训练优化}
}
```

---

<a id="origin-4328"></a>
## 30. 训练、Prefill、Decode 的完整对比

| 阶段 | 本轮输入 | Q 数量 | K/V 数量 | Attention Score | 是否使用 KV Cache |
|---|---:|---:|---:|---:|---|
| 训练 | 整个训练序列 | T | T | T×T | 通常否 |
| 推理 Prefill | 整个 Prompt | T | T | T×T | 建立 Cache |
| Decode 第 1 步 | 1 个新 token | 1 | T+1 | 1×(T+1) | 是 |
| Decode 第 2 步 | 1 个新 token | 1 | T+2 | 1×(T+2) | 是 |
| Decode 第 3 步 | 1 个新 token | 1 | T+3 | 1×(T+3) | 是 |

<a id="origin-4340"></a>
## 31. 完整 input_ids 和计算历史不是同一个东西

MiniMind 中实际上同时维护了两种历史。

<a id="origin-4344"></a>
### 31.1 第一种：完整 token 历史

```python
input_ids
```

例如：

```text
[BOS, I, love, AI, is, very]
```

它主要用于：

```text
最终输出
repetition penalty
token decode
streamer
```

---

<a id="origin-4367"></a>
### 31.2 第二种：计算历史

```python
past_key_values
```

里面保存的是：

```text
每一层历史 token 的 K/V
```

它主要用于：

```text
避免历史 token 再次经过 Transformer
```

因此可以记成：

```text
逻辑历史：
input_ids

计算历史：
past_key_values
```

<a id="origin-4397"></a>
## 32. 把 generate() 简化以后，KV Cache 就非常清楚

去掉 top-k、top-p、temperature 等采样逻辑后，核心可以理解成：

```python
input_ids = prompt
past_key_values = None

for _ in range(max_new_tokens):

    # 已经计算过多少 token
    past_len = (
        past_key_values[0][0].shape[1]
        if past_key_values
        else 0
    )

    # 只拿没有计算过的新 token
    new_input = input_ids[:, past_len:]

    outputs = self.forward(
        new_input,
        past_key_values=past_key_values,
        use_cache=True
    )

    # 根据最后一个位置预测下一个 token
    next_token = sample(outputs.logits[:, -1, :])

    # 完整 token 历史继续保存
    input_ids = torch.cat(
        [input_ids, next_token],
        dim=-1
    )

    # 保存新的 KV Cache
    past_key_values = outputs.past_key_values
```

KV Cache 的两个核心操作就在这里：

```text
input_ids[:, past_len:]
```

负责：

```text
切掉已经计算过的历史 token
```

而 Attention 中：

```python
xk = torch.cat([past_key_value[0], xk], dim=1)
xv = torch.cat([past_key_value[1], xv], dim=1)
```

负责：

```text
把历史 token 留下来的 K/V 接回来
```

可以总结成：

> **上面切掉，下面接回来。**

---

<a id="origin-4467"></a>
## 33. 把 Attention 简化以后更容易看懂

KV Cache 相关逻辑本质上就是：

```python
def attention(x, past_kv=None):

    # 当前新输入
    q = Wq(x)
    k = Wk(x)
    v = Wv(x)

    # 拼接历史 KV
    if past_kv is not None:
        old_k, old_v = past_kv

        k = cat(old_k, k)
        v = cat(old_v, v)

    # 更新 Cache
    new_cache = (k, v)

    # q 只有当前新 token
    output = softmax(q @ k.T) @ v

    return output, new_cache
```

图示：

```text
当前新 token
     │
     ├──→ Q_new
     │
     ├──→ K_new ─────┐
     │                │
     └──→ V_new ──┐   │
                  │   │
历史 K ───────────┼───┘
                  ↓
               K_all

历史 V ───────────┼────┐
                  │    │
V_new ────────────┘    ↓
                    V_all


Q_new × K_all^T
       ↓
    Softmax
       ↓
     × V_all
       ↓
      O_new
```

---

<a id="origin-4527"></a>
## 34. 最终总结

KV Cache 并没有修改 Attention 的数学公式：

```math
\operatorname{Attention}(Q,K,V)
=
\operatorname{softmax}
\left(
\frac{QK^T}{\sqrt d}
\right)V
```

它修改的是：

> **下一轮到底还需要重新计算哪些 token。**

不使用 KV Cache：

```text
每生成一个新 token

都重新输入：

全部历史 token + 新 token

然后重新计算：

全部 Q
全部 K
全部 V
全部 Attention Score
```

使用 KV Cache：

```text
第一次：

整个 Prompt 一次 Prefill
↓
保存每一层全部历史 K/V

之后：

每轮只输入一个新 token
↓
只计算新的 Q/K/V
↓
新 K/V 追加到历史 Cache
↓
当前 Q 和所有历史 K 做 Attention
```

所以：

```math
T\times T
```

的大矩阵重复计算，变成：

```math
1\times T
```

的新增一行计算。

---

<a id="origin-4597"></a>
## 35. 推理要点

<a id="origin-4599"></a>
### 35.1 第一句

> **KV Cache 缓存的是每一层历史 token 的 K 和 V，而不是原始 token，也不是 Q。**

<a id="origin-4603"></a>
#### 35.1.1 第二句

> **Prefill 一次处理整个 Prompt，Decode 才是一个 token 一个 token 地生成。**

<a id="origin-4607"></a>
#### 35.1.2 第三句

> **KV Cache 不改变 Attention 公式，只减少重复计算。**

<a id="origin-4611"></a>
#### 35.1.3 第四句

> **不用 Cache 时重新算整个 $T\times T$ Attention；使用 Cache 后，Decode 每轮只算新增的 $1\times T$ 那一行。**

<a id="origin-4615"></a>
#### 35.1.4 第五句

> **训练不是不需要 K、V，而是不需要缓存 K、V。**

<a id="origin-4619"></a>
#### 35.1.5 第六句

> **KV Cache 主要是推理优化，而不是训练优化。**

<a id="origin-4623"></a>
#### 35.1.6 第七句

MiniMind 中最核心的两部分代码是：

```python
# generate 中：
input_ids[:, past_len:]
```

负责：

```text
把历史 token 从本轮模型输入中切掉
```

以及：

```python
# Attention 中：
xk = torch.cat([past_key_value[0], xk], dim=1)
xv = torch.cat([past_key_value[1], xv], dim=1)
```

负责：

```text
把历史 K/V 从 Cache 中重新接回来
```

因此可以用一句话概括：

<a id="origin-4654"></a>
## 36. 上面切掉历史输入，下面接回历史 K/V。

这就是 MiniMind 中 KV Cache 的完整工作原理。

<a id="origin-4660"></a>
## 37. Transformers 中 Streamer 的基本用法

<a id="origin-4662"></a>
## 38. Streamer 是干什么的？

正常情况下：

```python
outputs = model.generate(...)
```

模型会：

```text
token1
↓
token2
↓
token3
↓
...
↓
EOS
↓
全部生成结束
↓
一次性把结果返回
```

所以用户可能要等整个回答全部生成完，才能看到文字。

而 `streamer` 的作用就是：

> **模型每生成一部分 token，就立即把已经可以显示的文本输出出去。**

效果类似 ChatGPT：

```text
浙
浙江
浙江大学
浙江大学位于
浙江大学位于宁波
...
```

而不是等全部生成完以后才一次性显示：

```text
浙江大学位于宁波。
```

---

<a id="origin-4713"></a>
## 39. 最简单的 `TextStreamer`

Transformers 提供：

```python
from transformers import TextStreamer
```

最基本的写法：

```python
from transformers import AutoTokenizer, AutoModelForCausalLM, TextStreamer

tokenizer = AutoTokenizer.from_pretrained("模型路径")
model = AutoModelForCausalLM.from_pretrained("模型路径")

prompt = "浙江大学软件学院位于哪里？"

inputs = tokenizer(
    prompt,
    return_tensors="pt"
)

streamer = TextStreamer(
    tokenizer,
    skip_prompt=True,
    skip_special_tokens=True
)

model.generate(
    **inputs,
    max_new_tokens=100,
    streamer=streamer
)
```

运行时就会在终端中逐渐输出：

```text
浙江大学软件学院位于浙江省宁波市。
```

而不是等到 `generate()` 完全执行结束以后再统一打印。

---

<a id="origin-4759"></a>
## 40. 最关键的其实只有两步

第一步：

```python
streamer = TextStreamer(tokenizer)
```

创建一个 Streamer。

第二步：

```python
model.generate(
    ...,
    streamer=streamer
)
```

把它交给 `generate()`。

所以可以把整个流程理解成：

```text
model.generate()
      │
      │ 生成 token
      ▼
   token_id
      │
      ▼
   streamer
      │
      │ tokenizer.decode()
      ▼
     文本
      │
      ▼
   立即显示
```

---

<a id="origin-4802"></a>
## 41. `TextStreamer(tokenizer)` 为什么必须传 tokenizer？

因为大模型真正生成的是：

```text
Token ID
```

例如：

```text
[3241, 982, 7312]
```

而不是直接生成：

```text
浙江大学
```

所以 Streamer 收到 token 后，需要：

```python
tokenizer.decode(...)
```

把 Token ID 转回人能看到的文本。

整个过程：

```text
模型
↓
token_id
↓
Streamer
↓
Tokenizer.decode()
↓
字符串
↓
显示
```

---

<a id="origin-4848"></a>
## 42. `skip_prompt=True`

例如输入：

```text
用户：浙江大学在哪里？
```

模型回答：

```text
浙江大学位于浙江省杭州市。
```

如果：

```python
skip_prompt=False
```

Streamer 可能连输入 Prompt 一起显示：

```text
用户：浙江大学在哪里？浙江大学位于浙江省杭州市。
```

如果：

```python
skip_prompt=True
```

则跳过输入 Prompt，只显示新生成的部分：

```text
浙江大学位于浙江省杭州市。
```

所以聊天机器人通常会使用：

```python
streamer = TextStreamer(
    tokenizer,
    skip_prompt=True
)
```

---

<a id="origin-4897"></a>
## 43. `skip_special_tokens=True`

模型输出中可能包含：

```text
<bos>
<eos>
<|im_start|>
<|im_end|>
```

这类特殊 token。

如果：

```python
skip_special_tokens=True
```

解码时就不会把这些特殊 token 显示给用户。

因此经常写：

```python
streamer = TextStreamer(
    tokenizer,
    skip_prompt=True,
    skip_special_tokens=True
)
```

<a id="origin-4930"></a>
## 44. Streamer 并不是负责生成 token 的

这一点非常重要。

很多人看到：

```python
streamer=streamer
```

容易误以为：

> Streamer 参与了模型采样。

实际上不是。

真正负责生成的仍然是：

```python
model.generate()
```

内部仍然执行：

```text
模型 forward
↓
得到 logits
↓
temperature / top-k / top-p
↓
选择 next_token
↓
把 next_token 加入输入
↓
继续 forward
```

Streamer 只是旁边接收生成结果：

```text
                ┌──────────────→ Streamer → 显示
                │
model.generate()
      │
      ▼
生成 next_token
      │
      ▼
继续下一轮生成
```

所以：

> **Streamer 负责“怎么把生成过程展示出来”，而不是“怎么生成”。**

---

<a id="origin-4988"></a>
## 45. `TextStreamer` 内部可以简单理解成什么？

可以把它极度简化成：

```python
class SimpleStreamer:

    def __init__(self, tokenizer):
        self.tokenizer = tokenizer

    def put(self, token_ids):
        text = self.tokenizer.decode(token_ids)
        print(text, end="", flush=True)

    def end(self):
        print()
```

真正的 `TextStreamer` 要复杂一些，因为它不会机械地每得到一个 token 就一定立即打印，而是会处理：

- token 解码；
- 单词边界；
- 文本缓存；
- Prompt 跳过；
- 最后的缓存刷新。

可以先理解为：

```text
put(token)
    ↓
收到新 token
    ↓
decode
    ↓
打印

end()
    ↓
生成结束
    ↓
把剩余缓存输出
```

---

<a id="origin-5034"></a>
## 46. `generate()` 和 Streamer 是怎么连接起来的？

可以把内部过程简化理解为：

```python
while not finished:

    outputs = model(input_ids)

    next_token = sample(outputs.logits)

    # 告诉 streamer：
    # 我刚刚生成了这个 token
    streamer.put(next_token)

    input_ids = append(
        input_ids,
        next_token
    )

streamer.end()
```

于是：

```text
生成 token1
↓
streamer.put(token1)
↓
生成 token2
↓
streamer.put(token2)
↓
生成 token3
↓
streamer.put(token3)
↓
...
↓
EOS
↓
streamer.end()
```

这就是 Streaming Generation 最核心的原理。


而是希望：

## 48. `TextIteratorStreamer`

基本导入：

```python
from transformers import TextIteratorStreamer
```

基本写法：

```python
from transformers import (
    AutoTokenizer,
    AutoModelForCausalLM,
    TextIteratorStreamer
)

from threading import Thread

tokenizer = AutoTokenizer.from_pretrained("模型路径")
model = AutoModelForCausalLM.from_pretrained("模型路径")

prompt = "介绍一下 Transformer。"

inputs = tokenizer(
    prompt,
    return_tensors="pt"
)

streamer = TextIteratorStreamer(
    tokenizer,
    skip_prompt=True,
    skip_special_tokens=True
)

generation_kwargs = {
    **inputs,
    "max_new_tokens": 200,
    "streamer": streamer
}

thread = Thread(
    target=model.generate,
    kwargs=generation_kwargs
)

thread.start()

for new_text in streamer:
    print(new_text, end="", flush=True)
```

<a id="origin-5195"></a>
## 49. 为什么 `TextIteratorStreamer` 经常要配 `Thread`？

如果直接写：

```python
model.generate(...)
```

程序会一直卡在这里：

```text
开始 generate
↓
生成 token
↓
生成 token
↓
生成 token
↓
...
↓
全部生成结束
↓
generate 返回
↓
程序才继续执行
```

那么你就没办法同时：

```python
for text in streamer:
```

读取 Streamer。

因此通常把生成放到另外一个线程：

```text
主线程                     生成线程

for text in streamer       model.generate()
       ▲                         │
       │                         │
       └────── Streamer ◄────────┘
```

生成线程：

```text
不断产生 token
```

主线程：

```text
不断从 streamer 读取文本
```

于是就实现了：

> **一边生成，一边显示。**

## 53. 一句话总结

`streamer` 并不改变 Transformer 的生成算法。

它只是把原来的：

```text
全部生成完成
↓
一次性返回
```

变成：

```text
生成一点
↓
交给 Streamer

再生成一点
↓
再交给 Streamer

再生成一点
↓
再交给 Streamer
```

因此：

$$
\boxed{
Streamer
=
模型生成过程与实时显示过程之间的接口
}
$$

最简单的：

