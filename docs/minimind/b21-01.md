# 57 · PPO 代码：模型角色与 PyTorch 基础


> 目标：不是只会“跑 PPO”，而是看懂这份代码为什么这样写、每一个关键 API 在做什么、每一个张量是什么形状，以及一条 Prompt 到底怎样一步一步变成一次 PPO 参数更新。
>
> 源文件：`train_ppo.py`，共 532 行。
>
> 记号：
>
> - `B`：一个 rollout batch 中的 Prompt 数量
> - `P`：Prompt token 长度
> - `R`：Response token 长度
> - `T=P+R`：完整序列长度
> - `H`：hidden size
> - `V`：词表大小
> - `old`：采样这批回答时的策略
> - `new/current`：正在被 PPO 更新的 Actor
> - `ref`：冻结的参考策略，通常是 SFT 模型

---

<a id="origin-21"></a>
## 1. 先用一句话说清楚这份程序在干什么

这份代码实现的是一个典型的 **LLM PPO 在线强化学习循环**：

```text
Prompt
  ↓
Actor 生成回答
  ↓
保存“采样时 Actor”对每个回答 token 的 old_log_prob
  ↓
Reward Model + 规则奖励 → 整条回答 reward
  ↓
Critic 对每个回答位置估计 Value
  ↓
把最终 reward 放到最后一个回答 token
  ↓
GAE 从后往前传播奖励
  ↓
得到每个 token 的 Advantage 和 Return
  ↓
对同一批 rollout 做若干轮 PPO 更新
  ├── 更新 Actor
  └── 更新 Critic
  ↓
必要时把新 Actor 同步给 rollout engine
  ↓
保存权重
```

最重要的是：

> **PPO 不是“生成一个回答，然后直接让 reward 对语言模型反向传播”。**

Reward Model 给出来的只是一个分数，它本身通常没有连接到 Actor 的计算图。

真正让 Actor 更新的是：

$$
\text{Reward}
\rightarrow
\text{GAE}
\rightarrow
A_t
\rightarrow
\text{PPO Policy Loss}
\rightarrow
\nabla_\theta
$$

## 2. 先分清四个模型/角色

这份代码至少要同时理解四个角色。

<a id="origin-77"></a>
### 2.1 Actor：当前正在训练的语言模型

代码：

```python
actor_model, tokenizer = init_model(...)
```

Actor 做两件事：

1. 根据 Prompt 生成 Response；
2. PPO 更新时重新计算 Response token 的概率。

记为：

$$
\pi_\theta(a_t|s_t)
$$

其中：

- $s_t$：当前上下文；
- $a_t$：当前生成的 token；
- $\theta$：Actor 参数。

---

<a id="origin-104"></a>
### 2.2 Old Policy：采样这批数据时的 Actor

代码中没有单独创建一个 `old_model`。

而是 rollout 时直接保存：

```python
old_resp_logp = rollout_result.per_token_logps
```

所以“旧策略”被压缩成了：

> **这批动作当初被采样出来时的 log probability。**

例如：

```text
token:       A       B       C
old_logp:   -0.7    -1.1    -0.3
```

后面 Actor 更新后，再算：

```text
new_logp
```

于是：

$$
r_t(\theta)
=
\frac{\pi_\theta(a_t|s_t)}
{\pi_{\text{old}}(a_t|s_t)}
=
\exp(
\log\pi_\theta
-
\log\pi_{\text{old}}
)
$$

这就是 PPO 的概率比值。

<a id="origin-148"></a>
#### 2.2.1 为什么不一定要真的保存一整份 old model？

因为 PPO 对这批已经采样好的 token，只需要知道：

$$
\pi_{\text{old}}(a_t|s_t)
$$

也就是说，只要保存这些被选中 token 的 old log probability 就够了。

---

<a id="origin-160"></a>
### 2.3 Reference Model：永远冻结的参考模型

代码：

```python
ref_model, _ = init_model(...)
ref_model = ref_model.eval().requires_grad_(False)
```

它与 old policy 的作用完全不同。

<a id="origin-171"></a>
#### 2.3.1 old policy 的作用

回答：

> “这批 token 当初是以多大概率被采样出来的？”

用于 PPO ratio：

$$
\frac{\pi_{\text{new}}}{\pi_{\text{old}}}
$$

<a id="origin-183"></a>
#### 2.3.2 reference model 的作用

回答：

> “当前 Actor 是否已经偏离原始 SFT 模型太远？”

用于 reference KL 约束。

所以：

```text
Old Policy
    ↓
控制“一次 PPO 更新别跨太大步”

Reference Model
    ↓
控制“长期训练别离原始模型太远”
```

---

<a id="origin-205"></a>
### 2.4 Critic：估计每个 token 状态有多“值钱”

代码：

```python
class CriticModel(MiniMindForCausalLM):
    def __init__(self, params):
        super().__init__(params)
        self.value_head = nn.Linear(params.hidden_size, 1)
```

普通语言模型：

$$
[B,T,H]
\rightarrow
[B,T,V]
$$

Critic：

$$
[B,T,H]
\rightarrow
[B,T,1]
\rightarrow
[B,T]
$$

它不预测“下一个 token 是什么”，而是预测：

$$
V(s_t)
$$

即：

> 从当前状态继续往后走，预计最终能得到多少回报？

#### 3.8.6 `torch.stack(list, dim=...)`（重点）

把若干形状相同的 Tensor 沿新维度堆起来。

<a id="origin-719"></a>
#### 3.8.7 `torch.stack(list, dim=...)`：为什么 GAE 最后要这样写？

`torch.stack()` 的作用是：

> 把多个**形状相同的 Tensor**，沿着一个新的维度堆起来。

在 PPO 的 GAE 中：

```python
advs_rev.append(lastgaelam)
```

每一次循环得到的是：

> 当前时间步、整个 Batch 的 Advantage。

---

<a id="origin-737"></a>
##### 3.8.7.1 假设 Batch 中有 2 条回答

即：

$$
B=2
$$

每条回答有 3 个 token：

$$
R=3
$$

例如：

```text
样本1：A1 A2 A3
样本2：B1 B2 B3
```

我们最终希望得到的 Advantage 矩阵是：

$$
[B,R]=[2,3]
$$

也就是：

```text
          token1   token2   token3
样本1      A1       A2       A3
样本2      B1       B2       B3
```

---

<a id="origin-774"></a>
##### 3.8.7.2 GAE 是从后往前计算的

代码：

```python
for t in reversed(range(gen_len)):
```

如果：

```text
gen_len = 3
```

那么实际计算顺序是：

```text
t = 2
t = 1
t = 0
```

也就是：

```text
token3
↓
token2
↓
token1
```

---

<a id="origin-808"></a>
##### 3.8.7.3 第一次循环：计算最后一个 token

假设两个样本最后一个 token 的 Advantage 分别是：

```python
lastgaelam = tensor([1.2, 0.8])
```

这里：

```text

0.8 → 样本2的 token3
```

$$
[B]=[2]
$$

然后：

```python

```

于是：

```python

]
```

<a id="origin-845"></a>
##### 3.8.7.4 第二次循环：计算 token2

```python
lastgaelam = tensor([1.5, 1.1])
```

```text
1.5 → 样本1的 token2
```

<a id="origin-877"></a>

```text
token1
```

```text
token3
```

<a id="origin-949"></a>


```python
tensor([1.8, 1.4])   # token1
tensor([1.5, 1.1])   # token2
tensor([1.2, 0.8])   # token3
```

每一个 Tensor 的形状都是：

[B]=[2]
$$

可以把它们想象成：

```text

[1.8,
 1.4]

[1.5,
```

现在沿：

```python
advantages = tensor([
    [1.8, 1.5, 1.2],
```

$$

$$

$$

<a id="origin-1031"></a>
##### 3.8.7.8 为什么是 `dim=1`？

因为我们希望：

```text

第 1 维：Response Token
```

即：

```text
advantages[样本编号][token编号]
```

例如：

```python

```

得到：

```text
[1.8, 1.5, 1.2]
```

表示：

> 第 1 条回答三个 token 的 Advantage。

而：

```python
advantages[1]
```

得到：

```text
[1.4, 1.1, 0.8]
```

表示：

> 第 2 条回答三个 token 的 Advantage。

---

<a id="origin-1080"></a>

```python

```

```python
    [1.8, 1.4],   # token1
    [1.5, 1.1],   # token2
    [1.2, 0.8]    # token3

```


但后面的 PPO 代码通常希望数据格式是：

$$

$$

也就是：


所以源码使用：

```python

```

##### 3.8.7.11 一句话记忆

```python
torch.stack(advs_rev[::-1], dim=1)
```

可以拆成两件事：

```text
[::-1]
    ↓
因为 GAE 是倒着算的，
先把 token 顺序恢复成 token1 → token2 → token3

torch.stack(..., dim=1)
    ↓
把每个时间步得到的 [B] Advantage
沿 token 维拼起来

最终：
[B] × R
→
[B,R]
```

所以最终矩阵的含义就是：

```text
行 = 不同样本
列 = 不同 response token
值 = 每个 token 对应的 Advantage
```

### 3.15 `.gather(...)`：本文件最重要的 Tensor API 之一（重点）

先理解一个例子。

假设 logits：

$$
[B,T,V]
$$

其中最后一维是词表。

某个位置模型对词表给出：

```text
token 0 → -4.0
token 1 → -1.2
token 2 → -0.7
...
```

但真实生成 token 是：

```text
token 2
```

我们只想拿：

```text
-0.7
```

这时用：

```python
.gather(dim=2, index=token_ids)
```

就是：

> 沿词表维度，按照真实 token id 把对应 log probability 拿出来。

代码：

```python
F.log_softmax(logits, dim=-1)
    .gather(2, labels.unsqueeze(-1))
    .squeeze(-1)
```

实现：

$$
[B,T,V]
\rightarrow
[B,T,1]
\rightarrow
[B,T]
$$

然后又：

```python
.gather(1, logp_pos)
```

表示：

> 从完整序列位置中，只拿回答 token 对应的位置。

最终：

$$
[B,R]
$$

<a id="origin-1813"></a>
#### 3.15.1 `torch.gather()` 最简单理解

<a id="origin-1815"></a>
##### 3.15.1.1 `gather` 是干什么的？

一句话：

> **按照给定索引，从指定维度里取值。**

---

<a id="origin-1823"></a>
##### 3.15.1.2 最简单的二维例子

假设有一个 Tensor：

```python
x = torch.tensor([
    [10, 20, 30],
    [40, 50, 60]
])
```

它长这样：

```text
[
    [10, 20, 30],
    [40, 50, 60]
]
```

形状：

$$
[2,3]
$$

现在我们想：

```text
第 0 行取下标 2
第 1 行取下标 0
```

也就是想拿：

```text
30
40
```

索引写成：

```python
index = torch.tensor([
    [2],
    [0]
])
```

然后：

```python
y = torch.gather(
    x,
    dim=1,
    index=index
)
```

得到：

```text
[
    [30],
    [40]
]
```

形状：

$$
[2,1]
$$

所以：

```python
torch.gather(x, dim=1, index=index)
```

可以理解成：

> 对每一行，按照 `index` 指定的列号去取值。

---

<a id="origin-1909"></a>
##### 3.15.1.3 再看一个更直观的表格

原来的：

```text
       col0   col1   col2

row0    10     20     30
row1    40     50     60
```

索引：

```text
row0 → 取 col2
row1 → 取 col0
```

所以：

```text
row0 → 30
row1 → 40
```

最终：

```text
[
    [30],
    [40]
]
```

---

<a id="origin-1945"></a>
##### 3.15.1.4 `dim=1` 是什么意思？

原 Tensor：

$$
[2,3]
$$

可以理解成：

```text
dim=0 → 行
dim=1 → 列
```

所以：

```python
gather(dim=1)
```

就是：

> **沿列这个维度，根据索引去取值。**

---

<a id="origin-1972"></a>
##### 3.15.1.5 PPO 里为什么用 `gather`？

语言模型输出的是：

```text
每个位置
对整个词表所有 token 的概率
```

例如某一个位置：

```text
token0 → -4.0
token1 → -1.2
token2 → -0.7
token3 → -2.5
```

但这一位置真实生成的是：

```text
token2
```

所以 PPO 并不需要：

```text
[-4.0, -1.2, -0.7, -2.5]
```

全部概率。

它只需要：

```text
token2 对应的 -0.7
```

于是就可以用：

```python
.gather(...)
```

把真实 token 对应的 log probability 取出来。

---

<a id="origin-2020"></a>
###### 3.15.1.5.1 假设 `log_softmax` 后得到下面这个矩阵

对这一条样本：

```text
                 词表 token

位置          0       1       2       3       4
-------------------------------------------------
t=0         -2.0    -0.5    -3.0    -1.2    -4.0

t=1         -1.5    -2.1    -0.3    -3.5    -2.8

t=2         -4.0    -1.0    -2.0    -0.2    -3.1

t=3         -0.7    -2.5    -1.8    -3.0    -2.2
```

这个矩阵的形状就是：

$$
[T,V]=[4,5]
$$

完整 batch 形状：

$$
[B,T,V]=[1,4,5]
$$

---

<a id="origin-2052"></a>
###### 3.15.1.5.2 这个矩阵到底是什么意思？

例如：

```text
t = 0
```

这一行：

```text
token0 → -2.0
token1 → -0.5
token2 → -3.0
token3 → -1.2
token4 → -4.0
```

表示：

> 在第 0 个预测位置，模型认为下一个 token 属于整个词表中每个 token 的 log probability。

例如：

$$
\log P(token1)=-0.5
$$

而：

$$
\log P(token4)=-4.0
$$

所以模型明显更倾向：

```text
token1
```

---

<a id="origin-2094"></a>
###### 3.15.1.5.3 现在真实 token 是什么？

假设真正的 labels 是：

```text
位置0 → token1
位置1 → token2
位置2 → token3
位置3 → token0
```

所以：

```python
labels = tensor([
    [1, 2, 3, 0]
])
```

形状：

$$
[B,T]=[1,4]
$$

---

<a id="origin-2121"></a>
###### 3.15.1.5.4 我们真正想要的是什么？

虽然每个位置都有：

```text
5 个词表 token 的概率
```

但 PPO 不关心其他 token。

它只关心：

> **这个位置真正生成出来的 token，当时概率是多少？**

所以我们想从上面矩阵中取：

```text
t=0：
真实 token = 1
→ 取 -0.5

t=1：
真实 token = 2
→ 取 -0.3

t=2：
真实 token = 3
→ 取 -0.2

t=3：
真实 token = 0
→ 取 -0.7
```

最终想得到：

```text
[-0.5, -0.3, -0.2, -0.7]
```

---

<a id="origin-2163"></a>
###### 3.15.1.5.5 这就是第一次 `gather`

代码：

```python
F.log_softmax(logits, dim=-1)
    .gather(
        2,
        labels.unsqueeze(-1)
    )
```

先看：

```python
labels
```

原来：

```text
[[1, 2, 3, 0]]
```

形状：

$$
[1,4]
$$

但是 logits 是：

$$
[1,4,5]
$$

`gather(dim=2)` 要沿第 2 维，也就是词表维取值。

所以 index 也要带一个词表索引维。

于是：

```python
labels.unsqueeze(-1)
```

变成：

```text
[
    [
        [1],
        [2],
        [3],
        [0]
    ]
]
```

形状：

$$
[B,T,1]
=
[1,4,1]
$$

---

<a id="origin-2232"></a>
###### 3.15.1.5.6 `gather(dim=2)` 是怎么取的？

因为：

```python
dim=2
```

表示：

> 沿着最后一维，也就是词表 V 维取。

所以：

```text
位置 t=0：
index = 1
→ 在第0行词表中拿 token1

位置 t=1：
index = 2
→ 在第1行词表中拿 token2

位置 t=2：
index = 3
→ 在第2行词表中拿 token3

位置 t=3：
index = 0
→ 在第3行词表中拿 token0
```

所以：

```text
原矩阵：

t=0   [-2.0, -0.5, -3.0, -1.2, -4.0]
              ↑
            取这里


t=1   [-1.5, -2.1, -0.3, -3.5, -2.8]
                     ↑
                   取这里


t=2   [-4.0, -1.0, -2.0, -0.2, -3.1]
                            ↑
                          取这里


t=3   [-0.7, -2.5, -1.8, -3.0, -2.2]
         ↑
       取这里
```

得到：

```text
[
    [
        [-0.5],
        [-0.3],
        [-0.2],
        [-0.7]
    ]
]
```

形状：

$$
[B,T,1]
$$

---

<a id="origin-2310"></a>
###### 3.15.1.5.7 为什么还要 `.squeeze(-1)`？

现在最后一维只是：

```text
1
```

没有实际意义。

所以：

```python
.squeeze(-1)
```

把：

$$
[B,T,1]
$$

变成：

$$
[B,T]
$$

结果：

```text
[
    [-0.5, -0.3, -0.2, -0.7]
]
```

这时候已经完成：

> **每个序列位置，只保留真实 token 的 log probability。**

---

<a id="origin-2352"></a>
###### 3.15.1.5.8 一句话总结

`gather` 最简单的理解就是：

> **我告诉你“沿哪个维度”，再告诉你“每个位置要取哪个下标”，你就把对应值拿出来。**

在 PPO 中：

```text
第一次 gather
→ 从整个词表中取真实生成 token 的 log probability

第二次 gather
→ 从整个序列中只保留 Response 部分
```

最终得到：

$$
\boxed{
[B,R]
}
$$

也就是：

> **每条回答每个 token 对应的 log probability。**

允许某些 GPU 运算自动使用：

- FP16；
- BF16；

从而：

- 降低显存；
- 加速 Tensor Core 运算。

注意：

> autocast 不等于“整个模型永久转换成 FP16”。

它主要影响上下文中具体运算使用的计算精度。

判断 CUDA GPU 是否可用。

```python
"cuda:0" if torch.cuda.is_available() else "cpu"
```

### 3.27 模型状态 API

<a id="origin-2662"></a>
#### 3.27.1 `model.train()`

进入训练模式。

主要影响：

- Dropout；
- BatchNorm 等。

---

<a id="origin-2673"></a>
#### 3.27.2 `model.eval()`

进入推理模式。

注意：

> `eval()` 不会自动关闭梯度。

所以 Reference Model 又调用：

```python
.requires_grad_(False)
```

---

<a id="origin-2689"></a>
#### 3.27.3 `.requires_grad_(False)`

把模型参数设置成：

```text
不需要梯度
```

Reference Model 因此不会被训练。

---

<a id="origin-2701"></a>
#### 3.27.4 `.parameters()`

返回模型中可训练参数的迭代器。

给：

- optimizer；
- grad clipping；

使用。

---

<a id="origin-2714"></a>
#### 3.27.5 `.state_dict()`

得到模型参数和 buffer 的字典。

类似：

```python
{
    "model.layers.0....weight": tensor(...),
    ...
}
```

---

<a id="origin-2729"></a>
#### 3.27.6 `.load_state_dict(...)`

把保存的参数装回模型。

这里：

```python
critic_model.load_state_dict(
    state_dict,
    strict=False
)
```

因为 Critic 比 Actor 多了：

```text
value_head
```

`strict=False` 允许：

- checkpoint 没有 value_head；
- 模型存在额外参数。

但是要注意：

> `strict=False` 并不代表所有形状错误都会被忽略；同名参数尺寸不匹配通常仍会报错。

```python
state_dict = torch.load(...)
```

<a id="origin-2769"></a>
### 3.29 `torch.save`

保存 Python / Tensor 对象。

代码保存：

```python
{
    parameter_name: fp16_cpu_tensor
}
```

注意：

> 保存 `state_dict` 不等于把整个 Python 模型结构一起保存；加载时还要先构建匹配的模型。

<a id="origin-2787"></a>
### 3.30 `torch.compile`

PyTorch 2.x 的图编译优化。

```python
actor_model = torch.compile(actor_model)
```

它尝试把可编译的计算图优化成更高效执行版本。

代价：

- 第一次运行有编译成本；
- 动态 Python 控制流可能造成 graph break。
