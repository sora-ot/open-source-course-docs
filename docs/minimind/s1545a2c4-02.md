# 08 · 预训练源码：训练循环、评估与工程细节

## 1. MiniMind 的训练主程序

`train_pretrain.py` 可以分为 9 个阶段：

```text
1. 初始化环境和随机种子
2. 创建模型配置 / 检查断点
3. 配置混合精度
4. 配置实验日志
5. 创建模型 / Dataset / Optimizer
6. 恢复 checkpoint
7. torch.compile / DDP
8. epoch 训练循环
9. 清理分布式进程
```

## 3. Epoch

```python
--epochs 2
```

一个 epoch：

> 整个训练数据集大致被访问一遍。

2 epochs：

> 数据集训练两轮。

注意大模型预训练通常更习惯用：

```text
tokens
steps
FLOPs
```

衡量训练规模，而不只用 epoch。

因为大规模语料可能一轮就已经非常巨大。

<a id="origin-2506"></a>
## 5. 梯度累积

MiniMind：

```python
--accumulation_steps 8
```

每 8 个 batch 才：

```python
optimizer.step()
```

因此单卡时名义有效 batch size：

$$
32\times8
=
\boxed{256}
$$

如果使用：

$$
N
$$

张 GPU DDP，则全局 batch size 约：

$$
\boxed{
32\times8\times N
}
$$

例如 4 GPU：

$$
32\times8\times4=1024
$$

条序列 / optimizer update。

<a id="origin-2552"></a>
## 6. 梯度累积为什么先除以 accumulation_steps？

源码：

```python
loss = loss / args.accumulation_steps
```

然后：

```python
loss.backward()
```

假设 8 个 micro-batch：

$$
g_i=\nabla L_i
$$

如果不除 8：

$$
g=
\sum_{i=1}^8 g_i
$$

梯度规模会放大约 8 倍。

除以 8：

$$
g=
\frac18
\sum_{i=1}^8 g_i
$$

相当于大 batch 平均梯度。

<a id="origin-2612"></a>
## 8. 学习率调度

MiniMind：

```python
lr = get_lr(
    epoch * iters + step,
    args.epochs * iters,
    args.learning_rate
)
```

`get_lr`：

```python
return lr * (
    0.1
    + 0.45 * (
        1 + cos(pi * current_step / total_steps)
    )
)
```

数学形式：

$$
\boxed{
\eta_t
=
\eta_0
\left[
0.1+
0.45
\left(
1+\cos\frac{\pi t}{T}
\right)
\right]
}
$$

---

<a id="origin-2654"></a>
## 9. 这个 cosine schedule 从多少降到多少？

当：

$$
t=0
$$

时：

$$
\cos0=1
$$

所以：

$$
0.1+0.45(2)=1
$$

$$
\eta_0=5\times10^{-4}
$$

训练末尾：

$$
t=T
$$

$$
\cos\pi=-1
$$

所以：

$$
0.1+0=0.1
$$

最终学习率：

$$
0.1\eta_0
=
5\times10^{-5}
$$

所以 MiniMind 当前实现是：

> **无 warmup 的 cosine decay，从初始 LR 平滑衰减到初始值的 10%。**

这是源码事实。

需要注意：

> 大型正式预训练通常经常还会加入 warmup；MiniMind 为了保持训练代码极简，这里没有实现 warmup。

<a id="origin-2714"></a>
## 10. Forward + Loss

核心：

```python
with autocast_ctx:
    res = model(input_ids, labels=labels)
    loss = res.loss + res.aux_loss
    loss = loss / args.accumulation_steps
```

Dense 模型时：

```text
aux_loss = 0
```

所以：

$$
loss
=
LM\ Loss
$$

MoE 时：

$$
loss
=
LM\ Loss
+
Router\ Auxiliary\ Loss
$$

<a id="origin-2751"></a>
## 11. `res.loss` 在哪里计算？

不是 `train_pretrain.py` 计算。

而是在：

```text
model/model_minimind.py
MiniMindForCausalLM.forward()
```

内部：

```python
if labels is not None:
    x = logits[..., :-1, :]
    y = labels[..., 1:]
    loss = F.cross_entropy(...)
```

这是理解项目结构的重要一点：

```text
Trainer
  负责优化流程

Model
  负责 forward 和语言模型 loss

Dataset
  负责把原始数据做成 input_ids / labels
```

<a id="origin-2786"></a>
## 12. 反向传播

MiniMind：

```python
scaler.scale(loss).backward()
```

从 CrossEntropy 开始，梯度一路反传：

```text
CrossEntropy
      ↓
LM Head
      ↓
第8层 Transformer
      ↓
……
      ↓
第1层 Transformer
      ↓
Embedding
```

用链式法则：

$$
\frac{\partial L}{\partial W}
=
\frac{\partial L}{\partial z}
\frac{\partial z}{\partial h}
\frac{\partial h}{\partial W}
$$

最终每个可训练参数都获得梯度。

---

<a id="origin-2824"></a>
## 13. Softmax + Cross Entropy 的梯度为什么漂亮？

设 logits：

$$
z_i
$$

softmax：

$$
p_i
$$

真实标签 one-hot：

$$
y_i
$$

Cross Entropy 对 logits 的梯度：

$$
\boxed{
\frac{\partial L}{\partial z_i}
=
p_i-y_i
}
$$

如果正确 token 是第 3 类：

```text
y = [0,0,1,0]
```

模型：

```text
p = [0.1,0.1,0.7,0.1]
```

梯度：

```text
[+0.1, +0.1, -0.3, +0.1]
```

含义：

- 错误 token 的 logits 往下压
- 正确 token 的 logits 往上推

模型就这样一步一步变得更准确。

<a id="origin-2881"></a>
## 14. AdamW

MiniMind：

```python
optimizer = optim.AdamW(
    model.parameters(),
    lr=args.learning_rate
)
```

Adam 的核心是维护：

一阶动量：

$$
m_t
=
\beta_1m_{t-1}
+
(1-\beta_1)g_t
$$

二阶动量：

$$
v_t
=
\beta_2v_{t-1}
+
(1-\beta_2)g_t^2
$$

参数更新大致：

$$
\theta_{t+1}
=
\theta_t
-
\eta
\frac{\hat m_t}
{\sqrt{\hat v_t}+\epsilon}
$$

AdamW 将 weight decay 与梯度更新解耦。

MiniMind 没有显式填写 betas / weight_decay，所以使用 PyTorch `AdamW` 默认值。

<a id="origin-2932"></a>
## 15. 梯度裁剪

MiniMind：

```python
torch.nn.utils.clip_grad_norm_(
    model.parameters(),
    args.grad_clip
)
```

默认：

```text
grad_clip = 1.0
```

如果整体梯度范数：

$$
\|g\|_2>1
$$

就按比例缩小。

例如：

$$
\|g\|=5
$$

大约乘：

$$
\frac15
$$

使 norm 变为 1。

目的：

> 防止偶发的大梯度让参数更新爆炸。

---

<a id="origin-2977"></a>
## 16. 为什么先 `scaler.unscale_` 再梯度裁剪？

float16 混合精度训练时，GradScaler 会把 loss 放大。

如果直接 clip：

> clip 的其实是被放大的梯度。

所以 MiniMind：

```python
scaler.unscale_(optimizer)
torch.nn.utils.clip_grad_norm_(...)
```

先恢复真实梯度尺度，再 clip。

这是正确顺序。

<a id="origin-3024"></a>
## 18. FP16 与 BF16

FP16：

```text
1 sign
5 exponent
10 mantissa
```

BF16：

```text
1 sign
8 exponent
7 mantissa
```

BF16 和 FP32 都有 8 位 exponent，因此数值范围很大，更不容易 overflow。

所以现代大模型训练如果硬件支持，通常更偏向 BF16。

MiniMind 默认：

```text
bfloat16
```

---

<a id="origin-3054"></a>
## 19. 为什么 BF16 时不启用 GradScaler？

MiniMind：

```python
scaler = torch.cuda.amp.GradScaler(
    enabled=(args.dtype == 'float16')
)
```

也就是说：

```text
FP16 → GradScaler 开启
BF16 → GradScaler 关闭
```

原因是 FP16 的指数范围更小，容易下溢。

BF16 范围更接近 FP32，一般不需要 loss scaling。

<a id="origin-3077"></a>
## 20. Optimizer Step

只有：

```python
if step % accumulation_steps == 0:
```

才执行：

```python
scaler.step(optimizer)
scaler.update()
optimizer.zero_grad(set_to_none=True)
```

所以流程：

```text
micro batch 1 → backward
micro batch 2 → backward
...
micro batch 8 → backward
                 ↓
              clip grad
                 ↓
           optimizer.step
                 ↓
             zero_grad
```

---

<a id="origin-3110"></a>
## 21. `zero_grad(set_to_none=True)` 为什么不是清零？

普通：

```python
grad.zero_()
```

会保留 gradient tensor，只把值改为 0。

`set_to_none=True`：

```python
param.grad = None
```

通常更省内存 / 更高效。

下一次 backward 再创建 gradient。

---

<a id="origin-3132"></a>
## 22. 一个 optimizer step 到底用了多少 token？

默认单 GPU：

```text
batch_size = 32
seq_len = 340
accumulation = 8
```

最大输入 token：

$$
32\times340\times8
=
\boxed{87040}
$$

token / optimizer update。

严格说：

- PAD 不产生有效语言模型 loss
- shift 后每条序列最多是 339 个预测 target

最大有效预测位置接近：

$$
32\times339\times8
=
86784
$$

如果全都没有 padding。

## 23. DDP 多 GPU

MiniMind：

```python
local_rank = init_distributed_mode()
```

如果环境变量有 RANK：

```python
dist.init_process_group(
    backend="nccl"
)
```

然后：

```python
model = DistributedDataParallel(
    model,
    device_ids=[local_rank]
)
```

DDP 基本思想：

```text
GPU 0：一部分 batch
GPU 1：一部分 batch
GPU 2：一部分 batch
GPU 3：一部分 batch
       ↓
各自 forward/backward
       ↓
梯度 All-Reduce
       ↓
每张卡得到相同平均梯度
       ↓
各自 optimizer.step()
       ↓
参数继续保持一致
```

MiniMind：

```python
train_sampler = DistributedSampler(train_ds)
```

作用：

## 27. 断点续训

MiniMind 有两类文件：

```text
普通模型权重：
pretrain_768.pth

恢复训练 checkpoint：
pretrain_768_resume.pth
```

恢复 checkpoint 包括：

```python
{
    'model': ...,
    'optimizer': ...,
    'epoch': ...,
    'step': ...,
    'world_size': ...,
    'wandb_id': ...
}
```

训练恢复时不仅恢复模型：

```python
model.load_state_dict(...)
```

也恢复：

```python
optimizer.load_state_dict(...)
scaler.load_state_dict(...)
```

为什么必须恢复 optimizer？

因为 AdamW 不是只有模型参数。

它还有：

```text
一阶动量 m
二阶动量 v
```

如果只恢复模型权重、不恢复 optimizer：

> 虽然看似“继续训练”，实际上 Adam 的历史状态丢了。


<a id="origin-3392"></a>
## 30. 为什么保存成 half + CPU？

MiniMind：

```python
{k: v.half().cpu() for k, v in state_dict.items()}
```

含义：

```text
GPU Tensor
  ↓
FP16
  ↓
CPU
  ↓
torch.save
```

优点：

- 权重文件更小
- 保存时不把 CUDA tensor 状态直接写进去
- 后续更方便加载

例如 64M 参数：

FP32 大约：

$$
64M\times4 Byte
\approx256MB
$$

FP16：

$$
64M\times2 Byte
\approx128MB
$$

忽略序列化开销时约减半。

默认：

```python
--use_moe 0
```

不使用 MoE。

如果：

```python
--use_moe 1
```

每层 FFN 换成：

```python
MOEFeedForward
```

router：

```python
scores = F.softmax(
    self.gate(x_flat),
    dim=-1
)
```

选择 Top-K expert：

```python
topk_weight, topk_idx = torch.topk(...)
```

默认：

```text
num_experts = 4
num_experts_per_tok = 1
```

因此每个 token 只路由到一个 expert。

<a id="origin-3517"></a>
## 33. MoE Auxiliary Loss

MoE 如果不加约束，router 可能：

```text
所有 token 都选 expert 0
```

其他 expert 闲置。

MiniMind 添加负载平衡 auxiliary loss：

```python
load = F.one_hot(
    topk_idx,
    num_experts
).float().mean(0)

aux_loss = (
    load * scores.mean(0)
).sum() * num_experts * coef
```

训练：

$$
\boxed{
L_{total}
=
L_{LM}
+
L_{aux}
}
$$

源码：

```python
loss = res.loss + res.aux_loss
```

默认 Dense：

$$
L_{aux}=0
$$

<a id="origin-3566"></a>
## 34. Pretrain 和 SFT 的核心区别：Loss Mask


<a id="origin-3570"></a>
### 34.1 Pretrain

MiniMind：

```python
labels = input_ids.clone()
labels[PAD] = -100
```

除了 padding：

> **几乎每个 token 都需要预测。**

例如：

```text
Transformer 是一种神经网络
```

所有正文 token 都训练。

---

<a id="origin-3593"></a>
### 34.2 SFT

SFTDataset 的 `generate_labels()` 会先：

```python
labels = [-100] * len(input_ids)
```

只把：

```text
assistant 回答部分
```

改回真实 token id。

也就是说 SFT 通常不要求模型学习：

```text
user 问题本身应该如何生成
```

主要要求模型学习：

```text
给定 system + user
→ assistant 应该回答什么
```

---

<a id="origin-3624"></a>
## 35. 一个最直观的 Pretrain vs SFT 对比

<a id="origin-3626"></a>
### 35.1 Pretrain

文本：

```text
北京是中国的首都
```

loss：

```text
BOS → 北京
北京 → 是
是 → 中国
中国 → 的
的 → 首都
首都 → EOS
```

几乎全算。

<a id="origin-3647"></a>
### 35.2 SFT

```text
user: 中国的首都是哪里？
assistant: 北京。
```

loss 常见做法：

```text
system/user 部分 → mask
assistant 的“北京。” → 计算 loss
```

所以：

> Pretrain 学“语言和知识分布”。

> SFT 学“按照指令回答”。

---

<a id="origin-3669"></a>
## 36. 为什么 Pretrain 后模型还不一定会聊天？

因为预训练目标只是：

> 预测互联网文本接下来是什么。

它可能看到：

```text
问：1+1等于多少？
答：2
```

也可能看到：

```text
有人问“1+1等于多少？”
这个问题很简单……
```

也可能看到文章、小说、网页、代码。

所以 Base Model 学的是：

$$
P(\text{text})
$$

而不是明确学：

$$
P(\text{helpful answer}\mid \text{user instruction})
$$

SFT 才把行为分布拉向：

```text
User → Assistant
```

## 38. 用伪代码把 MiniMind Pretrain 缩到 20 行

```python
tokenizer = load_tokenizer()
model = MiniMindForCausalLM(config)
optimizer = AdamW(model.parameters())

for text in corpus:

    ids = tokenizer(text)

    ids = [BOS] + ids + [EOS]
    ids = pad(ids)

    labels = ids.copy()
    labels[PAD] = -100

    logits = model(ids)

    pred = logits[:-1]
    target = labels[1:]

    loss = cross_entropy(
        pred,
        target,
        ignore_index=-100
    )

    loss.backward()
    optimizer.step()
    optimizer.zero_grad()
```

这 20 行代码体现了：

> 就已经理解了 Decoder-only LLM 预训练最核心的机制。

- 更现代的 Transformer 结构

- 混合精度
- 梯度累积
- 多 GPU
- 日志
- 保存
- 恢复
- MoE

等工程问题。

## 39. 从概率角度再看一次源码

源码：

```python
logits = self.lm_head(hidden_states)
```

代表模型参数化：

$$
P_\theta(x_{t+1}\mid x_{\le t})
$$

源码：

```python
x = logits[..., :-1, :]
y = labels[..., 1:]
```

代表：

$$
(x_{\le t}, x_{t+1})
$$

监督对。

源码：

```python
F.cross_entropy(x, y)
```

代表：

$$
-\log
P_\theta(x_{t+1}\mid x_{\le t})
$$

全数据训练就是：

$$
\boxed{
\min_\theta
-\sum_{\text{documents}}
\sum_t
\log
P_\theta(
x_{t+1}
\mid
x_{\le t}
)
}
$$

整个 Pretraining 最终就是这一个式子。

<a id="origin-3886"></a>
## 40. 从“信息压缩”的角度理解语言模型

一个好语言模型能给真实文本更高概率。

例如：

```text
中国的首都是北京
```

好模型可能：

```text
P(北京 | 中国的首都是) = 0.8
```

差模型：

```text
P(北京 | 中国的首都是) = 0.0001
```

Negative log probability：

好模型：

$$
-\log0.8
$$

很小。

差模型：

$$
-\log0.0001
$$

很大。

因此最小化 cross entropy，也可以理解成：

> 让模型越来越能够“压缩”真实语言。

越可预测，编码真实文本所需的信息量越低。

<a id="origin-3934"></a>
## 41. Perplexity（PPL）

如果平均 token loss：

$$
L
$$

定义：

$$
\boxed{
PPL=e^L
}
$$

例如：

$$
L=2
$$

则：

$$
PPL=e^2\approx7.39
$$

直观上可粗略理解成：

> 模型平均每一步像在约 7.39 个等可能候选中犹豫。

PPL 越低通常表示语言建模能力越好。

但注意：

> 不同 tokenizer 下 PPL 不宜简单横向比较。

MiniMind README 也专门指出 tokenizer 会影响按 token 统计的 PPL，跨 tokenizer 时 BPB 往往更公平。

## 42. 为什么 MiniMind 词表只有 6400？

对于小模型：

Embedding / LM Head 参数：

$$
V\times H
$$

如果词表从：

$$
6400
$$

扩大到：

$$
128000
$$

hidden=768 时：

$$
128000\times768
=
98.3M
$$

光 embedding 就比整个 MiniMind 还大。

所以小模型必须认真权衡：

```text
更大词表
↔
更短 token 序列
↔
更大的 embedding 参数
```

MiniMind 选择 6400 是一种小模型体积优先设计。

## 43. 小词表的代价

词表小意味着：

> 一个中文词、英文单词可能被拆成更多 token。

例如某个长英文词：

```text
transformation
```

大 tokenizer 可能：

```text
transformation
```

一个 token。

小 tokenizer 可能：

```text
trans
form
ation
```

三个 token。

因此：

- 序列变长
- Attention 计算变多
- PPL 的 token 单位发生变化

这也是为什么 tokenizer 是 LLM 系统设计的重要一部分。

<a id="origin-4098"></a>

## 46. Flash Attention 在这里真正是什么？

MiniMind 判断：

```python
self.flash = (
    hasattr(
        torch.nn.functional,
        'scaled_dot_product_attention'
    )
    and config.flash_attn
)
```

满足条件时：

```python
F.scaled_dot_product_attention(...)
```

更准确的表述是：

> 使用 PyTorch 的 SDPA 接口；后端在合适硬件和条件下可能选择 Flash Attention 等高效 kernel。

不要简单讲成：

> 这行一定就是某一个固定 FlashAttention 库。

MiniMind 没有依赖独立 `flash-attn` 包来实现核心 Attention。

## 47. 为什么 Attention 的复杂度是 $O(L^2)$？

Attention score：

$$
QK^\top
$$

shape：

$$
[L,d]\times[d,L]
\rightarrow
[L,L]
$$

所以每个 token 都和其他可见 token 计算关系。

复杂度：

$$
O(L^2d)
$$

memory 也容易受到：

$$
L^2
$$

影响。

例如长度从：

$$
340\rightarrow680
$$

score matrix 面积变为：

$$
4\times
$$

这就是长上下文成本高的重要原因。

## 50. 随机初始化意味着什么？

训练开始前模型并不知道：

```text
“北京”
```

和：

```text
“中国”
```

有什么关系。

Embedding 也是随机的。

例如初始：

```text
北京 → [0.01, -0.03, ...]
中国 → [-0.02, 0.01, ...]
```

这些数一开始没有语义。

经过大量梯度更新后，相似上下文中的 token 会形成有结构的表示空间。

所以 embedding 的语义：

> 不是人预先写进去的，而是通过 next-token prediction 学出来的。

## 51. 为什么 Pretrain 要大量数据？

假设只训练一句：

```text
北京是中国的首都
```

模型完全可以死记硬背。

但泛化不了。

当语料达到大量不同文本时：

> 单纯记住每个完整句子越来越困难。

模型必须学习可复用的统计结构：

- 语法
- 实体关系
- 模式
- 语义
- 推理结构

这就是规模化数据的重要性。

<a id="origin-4328"></a>
## 52. 数据质量为什么重要？

训练目标不会判断：

> 这句话是真的还是假的。

它只会学：

> 数据里什么 token 经常跟在什么上下文之后。

如果训练数据大量包含：

- 错误事实
- 垃圾重复
- 乱码
- 广告模板
- 极度低质量合成数据

模型就会学习这些分布。

所以：

$$
\boxed{
\text{Model Quality}
\neq
\text{Only Model Architecture}
}
$$

还高度取决于：

$$
\text{Data Quality}
$$

MiniMind README 也强调主线数据经过清洗、去重、长度控制和格式统一。

<a id="origin-4496"></a>
## 54. 初始 loss 大约会是多少？


如果模型完全随机，6400 个 token 大致均匀：

$$
P(correct)\approx\frac1{6400}
$$

loss：

$$
-\log\frac1{6400}
=
\log6400
$$

约：

$$
\boxed{8.76}
$$

所以一个完全随机、近似均匀的 6400 词表语言模型，CrossEntropy 常可粗略从 8~9 左右理解。

训练后如果 loss：

```text
8.7 → 6 → 4 → 3 → ...
```

说明模型对正确 token 的概率在不断提高。

注意真实初始化、数据分布、weight tying 等因素会使实际初始值不一定恰好等于 8.76。

---

<a id="origin-4534"></a>
## 55. Loss 降低到底意味着什么？

Cross entropy：

$$
L=-\log p
$$

粗略地：

$$
p\approx e^{-L}
$$

如果一个单独位置：

```text
loss = 8
```

对应正确 token 概率约：

$$
e^{-8}\approx0.000335
$$

如果：

```text
loss = 2
```

约：

$$
e^{-2}\approx0.135
$$

真实平均 loss 不能直接等同于每个位置都具有相同概率，但这个例子说明：

> loss 每下降一点，正确 token 的整体概率分布已经发生了明显改善。

<a id="origin-4578"></a>
## 56. 为什么训练时不关心 argmax 对不对？

假设正确 token：

```text
北京
```

两个模型：

A：

```text
北京 0.30
上海 0.29
```

B：

```text
北京 0.90
上海 0.02
```

两者 argmax 都正确。

但 B 显然更有信心。

Cross Entropy 会区分：

$$
-\log0.3
$$

和：

$$
-\log0.9
$$

因此训练语言模型不是仅仅优化：

```text
accuracy
```

而是在拟合完整概率分布。

<a id="origin-4628"></a>
## 57. 为什么生成时还要 temperature / top-p，而训练时不用？

训练目标：

> 对真实 token 最大化概率。

因此直接对完整 softmax 分布做 CrossEntropy。

生成时则要从：

$$
P(x_{t+1}|x_{\le t})
$$

中选择一个 token。

可以：

```text
argmax
sampling
temperature
top-k
top-p
```

所以：

> 训练解决“学概率分布”。

> decoding 解决“怎么从概率分布选择 token”。

两者不要混为一谈。

<a id="origin-4694"></a>
### 58.4 细节 4：Dataset 不创建 attention_mask

对于右侧 padding，Pretrain forward 没传显式 attention mask。

但因为：

- loss 对 padding target 做了 ignore
- causal mask 限制当前位置只能看左侧
- PAD 位于序列右侧

所以真实正文 token 不会看到未来的右侧 PAD。

PAD 自己产生的 hidden state 虽然会被计算，但其 target loss 被忽略。

这是一种简化实现。

<a id="origin-4712"></a>
## 59. 关于“没有 attention_mask”的更严谨解释

例如：

```text
BOS 我 爱 EOS PAD PAD
```

当位置：

```text
“我”
```

做 causal attention 时，它只能看：

```text
BOS
我
```

看不到右侧 PAD。

因此右 padding 不会污染正文 token 的表示。

PAD 位置本身可以看前文，但：

```text
它们的 labels = -100
```

所以不贡献语言模型 loss。

因此在这种：

> **全部 padding 都在右侧 + causal decoder**

的简单 pretrain 场景中，可以不显式传 padding attention mask。

---

<a id="origin-4753"></a>
## 60. 但什么时候 attention_mask 很重要？

例如：

- 左 padding
- packed sequences
- 多段样本拼接但不希望跨样本 attention
- 更复杂 batch packing
- 推理场景
- 不规则 padding

这时不能简单依赖 causal mask。

所以不要把 MiniMind 这里的简化结论推广成：

> Decoder LLM 永远不需要 attention mask。

<a id="origin-4772"></a>
## 61. 最后一个不满 accumulation_steps 的 batch

MiniMind 训练 epoch 结束时：

```python
if last_step % accumulation_steps != 0:
    ...
    scaler.step(optimizer)
```

所以不会丢掉最后残余的梯度。

但这里有一个很细的实现特点：

每个 micro-batch 都提前：

```python
loss /= accumulation_steps
```

即便最后只剩：

```text
3 个 micro-batch
```

仍然每个除以 8。

所以最后那个不完整 accumulation group 的梯度幅度会比“按实际 3 个 batch 平均”更小。

这是为了代码简洁可以接受的实现细节，但如果做严格大规模训练，可以对最后剩余 micro-batch 数重新归一化。

<a id="origin-4806"></a>
## 62. DDP + Gradient Accumulation 的通信细节

MiniMind 在梯度累积期间没有显式使用：

```python
model.no_sync()
```

因此 DDP 通常会在每个 backward 都进行梯度同步。

数学结果仍然可以正确累积，但通信效率不是最极致。

更典型的优化做法：

```text
前 7 个 accumulation micro-batch：
no_sync()

第 8 个：
正常 backward + all-reduce
```

这样能减少多卡通信。

MiniMind 的取舍很明显：

> 更重视代码清晰、易学，而不是把训练系统优化写得极其复杂。

## 67. 预训练的 12 个常见误区

<a id="origin-4978"></a>
### 67.1 误区 1
“Pretrain 的 label 是人工标的。”

错。

> label 就是文本下一个 token，自监督生成。

<a id="origin-4985"></a>
### 67.2 误区 2
“input_ids == labels，所以模型在抄答案。”

错。

> 模型内部 shift 一位。

<a id="origin-4992"></a>
### 67.3 误区 3
“模型每次只预测最后一个 token。”

错。

> 训练时一次 forward 并行预测几乎所有位置。

<a id="origin-4999"></a>
### 67.4 误区 4
“训练时可以看到完整句子，所以未来 token 泄漏了。”

错。

> causal mask 阻止每个位置看到未来。

<a id="origin-5006"></a>
### 67.5 误区 5
“CrossEntropy 输入的是 probability。”

错。

> PyTorch `F.cross_entropy` 输入 logits。

<a id="origin-5013"></a>
### 67.6 误区 6
“PAD 也应该预测。”

错。

> MiniMind 用 `-100` ignore。

<a id="origin-5020"></a>
### 67.7 误区 7
“Embedding 是预先就有语义的。”

错。

> 从随机参数经过预训练学出语义。

<a id="origin-5027"></a>
### 67.8 误区 8
“Pretrain 后就一定会像 ChatGPT 一样回答。”

错。

> Base Model 与 Instruction Model 不同。

<a id="origin-5034"></a>
### 67.9 误区 9
“RoPE 就是把 position embedding 加到 token embedding。”

错。

> RoPE 主要旋转 Q/K。

<a id="origin-5041"></a>
### 67.10 误区 10
“MiniMind 是普通 8-head MHA。”

不准确。

> Q=8 heads，KV=4 heads，是 GQA。

<a id="origin-5048"></a>
### 67.11 误区 11
“batch_size=32 就是实际更新 batch size。”

不完整。

> accumulation=8，所以单卡有效 batch 约 256。

<a id="origin-5055"></a>
### 67.12 误区 12
“模型是在记一句句答案。”

不完整。

> 参数通过共享统计结构来压缩和建模文本分布，记忆只是其中可能的一部分现象。

词表：

$$
V=6400

如果均匀预测：

## 72. 练习五：为什么 EOS 也要训练？

如果不训练 EOS：

> 模型只会学“接下来写什么”，却没有明确学习“什么时候结束”。

加入 EOS 后：

```text
文章最后一个正文 token
→ EOS
```

模型学习：

$$
P(EOS\mid\text{完整上下文})
$$

生成时才能合理停止。

## 73. MiniMind Pretrain 的一句话源码总结

如果把所有工程细节去掉，它做的事情就是：

$$
\boxed{
\text{Text}
\rightarrow
\text{Tokenizer}
\rightarrow
x_1,\ldots,x_T
\rightarrow
\text{Transformer}
\rightarrow
P(x_{t+1}|x_{\le t})
\rightarrow
CE
\rightarrow
\text{Backprop}
}
$$

其中训练目标：

$$
\boxed{
\min_\theta
-\sum_t
\log
P_\theta(
x_{t+1}
\mid
x_{\le t}
)
}
$$

这就是 MiniMind Pretraining 的数学本质。

## 76. 预训练的三个核心公式


<a id="origin-5397"></a>
### 76.1 公式一：自回归分解

$$
\boxed{
P(x_{1:T})
=
\prod_{t=1}^{T}
P(x_t|x_{<t})
}
$$

<a id="origin-5408"></a>
### 76.2 公式二：预训练 Loss

$$
\boxed{
\mathcal L
=
-\frac1N
\sum_t
\log
P_\theta(
x_{t+1}
\mid
x_{\le t}
)
}
$$

<a id="origin-5425"></a>
### 76.3 公式三：Causal Self-Attention

$$
\boxed{
\mathrm{Attention}(Q,K,V)
=
\mathrm{softmax}
\left(
\frac{QK^\top}{\sqrt{d_k}}
+
M_{\text{causal}}
\right)V
}
$$

这三个公式分别回答：

```text
语言概率如何分解？
模型到底在优化什么？
为什么训练时不能看到未来？
```

## 77. 一句话收尾

**MiniMind 的 Pretrain 并没有神秘的“知识注入”模块。**

它只是把海量文本变成海量：

```text
前缀 → 下一个 token
```

的预测任务，然后通过：

```text
Causal Transformer
+
Cross Entropy
+
Backpropagation
+
AdamW
```

不断调整约 6400 万个参数。

当这件简单的事被重复足够多次、使用足够多高质量文本之后，模型参数中逐渐形成了对语言、知识和各种模式的压缩表示。

这就是大语言模型预训练最核心的机制。
