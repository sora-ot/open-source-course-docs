# 55 · Rollout 从零到完整流程


<a id="origin-3"></a>
## 1. 序言：PPO 中的轨迹索引、Token Loss 求平均与梯度下降

<a id="origin-5"></a>
### 1.1 先明确训练范围：在本文的 PPO 代码中，Prompt 是给定的上下文，不作为要优化生成概率的动作目标，也不计入 PPO Token Loss 求平均的分母；直接产生这些损失的是模型生成的有效 Response Token（包含首个 EOS，排除后续补齐位置）。

<a id="origin-7"></a>
### 1.2 先区分两个下标：`i` 和 `t`

在经典强化学习中，一条轨迹通常写成：

$$
\tau_i=(s_{i,0},a_{i,0},s_{i,1},a_{i,1},\ldots,s_{i,T_i})
$$

- $i$：第 **几条轨迹**（Trajectory / Rollout）。
- $t$：这条轨迹中的第 **几个时间步**（生成第几个 Token）。
- $T_i$：第 $i$ 条轨迹的有效 Action（响应 Token）数量，包含首个 EOS，不包含 Prompt 和回答补齐位置。

在大模型中，这里的初始状态就是 Prompt，后续状态是 Prompt 加上此前已生成的回答前缀：

$$
s_{i,t}=(\text{Prompt}_i,a_{i,0},\ldots,a_{i,t-1})
$$

因此，$t=0$ 表示生成第一个 Response Token，而不是 Prompt 的第一个 Token；Prompt 自身的 Token 不占用这里的动作时间步。

**重要：$t$ 始终是单条轨迹内部的时间索引，并没有变成“所有轨迹连接起来后的全局序号”。**

假设相同 Prompt 生成两条轨迹，每条都生成 3 个 Token：

| 轨迹编号 $i$ | $t=0$ | $t=1$ | $t=2$ |
|---|---|---|---|
| $i=1$ | 答案 | 是 | 2 |
| $i=2$ | 答案 | 是 | 3 |

例如：

- $a_{1,2}$：第 1 条轨迹的第 3 个 Token，即“2”。
- $a_{2,1}$：第 2 条轨迹的第 2 个 Token，即“是”。

因此，两个轨迹、每条三个 Token，一共有 **6 个 Action 决策**，但并不是一条长度为 6 的轨迹。

<a id="origin-43"></a>
### 1.3 每个有效 Response Token 都有自己的 PPO Loss

这里的“每个 Token”都指模型生成的有效 Response Token，不包括输入的 Prompt。对于第 $i$ 条轨迹中的第 $t$ 个动作 Token，Rollout 保存旧策略的概率：

$$
\pi_{\mathrm{old}}(a_{i,t}\mid s_{i,t})
$$

更新 Actor 时，用当前模型对**同一个状态和已经采样的 Action**重新计算：

$$
\pi_{\theta}(a_{i,t}\mid s_{i,t})
$$

计算新旧概率比：

$$
\boxed{
 r_{i,t}(\theta)=
 \frac{\pi_{\theta}(a_{i,t}\mid s_{i,t})}
 {\pi_{\mathrm{old}}(a_{i,t}\mid s_{i,t})}
 }
$$

每个 Token 对应一个 Advantage $A_{i,t}$（可由 Critic 和 GAE 得到），并计算 PPO Clip Loss：

$$
\boxed{
\ell_{i,t}(\theta)
=-\min\left(
 r_{i,t}(\theta)A_{i,t},
 \operatorname{clip}(r_{i,t}(\theta),1-\epsilon,1+\epsilon)A_{i,t}
\right)
}
$$

**在一次 Actor 更新中，旧策略概率和已计算的 Advantage 被视为固定数据；需要反向传播的是当前策略 $\pi_\theta$。**

<a id="origin-81"></a>
### 1.4 整个 Batch 的 Loss 怎么求平均？

如果有 $N$ 条轨迹、每条恰好 $T$ 个有效 Token，那么：

$$
\boxed{
L_{\mathrm{PPO}}(\theta)
=\frac{1}{NT}
\sum_{i=1}^{N}
\sum_{t=0}^{T-1}\ell_{i,t}(\theta)
}
$$

外层的 $\sum_i$ 遍历**所有轨迹**；内层的 $\sum_t$ 只遍历**每条轨迹的有效 Response Token**；分母 $NT$ 是有效 Response Token 的总数，不包含 Prompt 的长度。

对于本例 $N=2,T=3$：

$$
\boxed{
L_{\mathrm{PPO}}
=\frac{1}{6}
\left(
\ell_{1,0}+\ell_{1,1}+\ell_{1,2}
+\ell_{2,0}+\ell_{2,1}+\ell_{2,2}
\right)
}
$$

如果轨迹长度不同，比如第一条有 3 个有效 Token、第二条有 2 个有效 Token，则常见的**全 Token 平均**写法是：

$$
\boxed{
L_{\mathrm{PPO}}
=\frac{1}{\sum_{i=1}^{N}T_i}
\sum_{i=1}^{N}\sum_{t=0}^{T_i-1}\ell_{i,t}
}
$$

即分母是所有有效响应 Token 的总数（本例为 5）。Padding 不应计入平均。注意：某些实现采用“先对每条轨迹求平均，再对轨迹求平均”，当轨迹长短不同时，两种加权方式不完全相同。

**把 Prompt 和含 0 的 Loss Mask 放在一起看。** 假设同一个 Prompt 的 ID 是 $[10,11,12]$，EOS 的 ID 为 2，PAD 的 ID 为 0。这次两条轨迹的有效回答长度分别为 3 和 2：

```text
                         Prompt         Response
完整输入 sample 1：   [10, 11, 12 | 51, 52, EOS]
完整输入 sample 2：   [10, 11, 12 | 61, EOS, PAD]

按目标 Token 对齐的完整 Loss Mask（示意）：
sample 1：            [ 0,  0,  0 |  1,  1,  1 ]
sample 2：            [ 0,  0,  0 |  1,  1,  0 ]
```

Prompt 对应的目标位置全部为 0；第一条回答有 3 个有效目标，第二条有 2 个，合计 5 个。虽然完整输入共有 12 个张量位置，**PPO Token Loss 的平均分母仍然是 5，而不是 12，也不是回答区域补齐后的 6。**

上面的完整 Loss Mask 用来展示哪些目标计入损失。正式代码先选出回答对应的 logp 和 Value，再使用只覆盖回答区域的 $[N,R]$ 掩码；本例 $R=3$：

```text
resp_policy_mask = resp_value_mask = [
    [1, 1, 1],
    [1, 1, 0],
]
```

若 $m_{i,t}$ 表示回答区域内的位置是否有效，则带补齐的写法是：

$$
\boxed{
L_{\mathrm{PPO}}
=\frac{\sum_{i=1}^{N}\sum_{t=0}^{R-1}m_{i,t}\ell_{i,t}}
{\sum_{i=1}^{N}\sum_{t=0}^{R-1}m_{i,t}}
}
$$

例如，假设逐 Token 的策略损失为 $[[0.2,0.3,0.5],[0.4,0.6,99.0]]$，第二条最后一列只是占位，则：

$$
L_{\mathrm{PPO}}
=\frac{0.2+0.3+0.5+0.4+0.6+0\times99.0}{5}
=0.4
$$

这里假设本批存在有效回答 Token；代码用有效掩码求和，并通过 $\operatorname{clamp}(\min=1)$ 保护分母。

**还要区分 Loss Mask 和 Attention Mask。** Prompt 是有效上下文，回答要通过 Attention 读取它，因此真实 Prompt Token 的 Attention Mask 通常为 1；Prompt 作为预测目标时的 Loss Mask 则为 0。

**Prompt 不直接产生 PPO Token Loss，不等于 Prompt 相关计算没有梯度。** 更新时仍把 Prompt + Response 一起送入模型，回答 Loss 可以沿着依赖 Prompt 的计算路径反向传播，更新共享参数。尤其是预测第一个 Response Token 的 logits 来自最后一个 Prompt 位置的输出：这个预测要计入回答 Loss，因为它的目标是第一个 Response Token，而不是要求模型重现 Prompt。

<a id="origin-168"></a>
### 1.5 为什么论文里有时只写 $\mathbb E_t$？

PPO 常把训练样本上的平均简写为：

$$
\mathbb E_t[\ell_t(\theta)]
$$

这是一种**省略了轨迹编号的记号**，意指对采样得到的时间步数据取期望/经验平均；不代表原来轨迹内的时间下标 $t$ 被重新定义为跨轨迹全局索引。

若要写得更严谨，可以用：

$$
\mathbb E_{\tau\sim\pi_{\mathrm{old}}}
\left[
\frac1T\sum_{t=0}^{T-1}\ell_t(\tau,\theta)
\right]
$$

在采样了 $N$ 条**等长轨迹**后，用样本平均近似：

$$
\frac1N\sum_{i=1}^N\frac1T\sum_{t=0}^{T-1}\ell_{i,t}(\theta)
$$

如果写程序时把二维的 `[N, T]` 展平成一维 `[N*T]`，一维的全局索引应另用 $j$ 来表示，避免与轨迹内时间 $t$ 混淆。

<a id="origin-195"></a>
### 1.6 最后如何梯度下降？

在固定长度的情况下，总 Loss 为：

$$
L(\theta)=\frac1{NT}\sum_{i=1}^N\sum_{t=0}^{T-1}\ell_{i,t}(\theta)
$$

由于求导具有线性性质：

$$
\boxed{
\nabla_\theta L(\theta)
=\frac1{NT}\sum_{i=1}^N\sum_{t=0}^{T-1}\nabla_\theta\ell_{i,t}(\theta)
}
$$

在我们“2 条轨迹 × 每条 3 个 Token”的例子中：

$$
\nabla_\theta L
=\frac16\left(
\nabla_\theta\ell_{1,0}+\nabla_\theta\ell_{1,1}+\nabla_\theta\ell_{1,2}
+\nabla_\theta\ell_{2,0}+\nabla_\theta\ell_{2,1}+\nabla_\theta\ell_{2,2}
\right)
$$

最后进行一次梯度下降（这里用最基本的 SGD 表达）：

$$
\boxed{
\theta_{\mathrm{new}}=\theta_{\mathrm{old}}-\eta\nabla_\theta L
}
$$

**直观地说：6 个 Token 分别对大模型共享参数产生梯度贡献，所有贡献汇总、平均之后，优化器用总梯度更新模型参数。** 不是为 6 个 Token 各训练一个模型，也不是必须每生成一个 Token 就更新一次参数。

<a id="origin-232"></a>
### 1.7 和 SFT 的异同

这里用只监督助手回答的 SFT 配置作对照：两者都可以只对整个 Batch 中有效的回答 Token 求平均，并执行一次 `loss.backward()`。下面的 $T$ 同样只统计回答 Token，Prompt 不作为直接的损失目标。SFT 也可以采用监督全部文本的其他配置，具体取决于 labels / Loss Mask；本文 PPO 代码优化的是回答动作。

**SFT：**

$$
L_{\mathrm{SFT}}
=-\frac1{NT}\sum_{i=1}^N\sum_{t=0}^{T-1}
\log\pi_\theta(a^{\mathrm{label}}_{i,t}\mid s_{i,t})
$$

**PPO（Actor 的 Clip Loss）：**

$$
L_{\mathrm{PPO}}
=-\frac1{NT}\sum_{i=1}^N\sum_{t=0}^{T-1}
\min\left(r_{i,t}A_{i,t},\operatorname{clip}(r_{i,t},1-\epsilon,1+\epsilon)A_{i,t}\right)
$$

区别不在“最后要不要反向传播”，而在于**每个 Token 的训练信号如何确定**：SFT 通常用示范答案作为标签；PPO 用采样的 Action、Advantage 和新旧策略概率比构造优化目标。

<a id="origin-254"></a>
### 1.8 一句话总结

> **$i$ 表示第几条轨迹，$t$ 表示该轨迹内部的第几个 Response Action。Prompt 作为上下文输入模型；PPO 只对有效 Response Token 直接计算 Token Loss，并按有效回答 Token 总数求平均，再反向传播、更新共享参数。Prompt 和回答补齐位置都不计入平均分母。**

*补充：真实 PPO 通常会对同一批 Rollout 做多个 Mini-batch / Epoch 更新；Actor Loss 之外，还可能单独训练 Critic 的 Value Loss。*



<a id="origin-262"></a>
### 1.9 对照公式：哪些量提前算好，哪些量在训练时重算？

“提前”指**本批 Rollout 已经生成，进入这批数据的 PPO 更新循环之前**。下面省略轨迹编号，只看一个回答位置 $t$；Prompt 是上下文，$a_t$ 是已生成的回答 Token。

**先从 PPO Loss 出发：为什么需要 $\log p_t^{\mathrm{old}}$？**

先看 Actor 要最小化的 PPO Clip Loss：

$$
L_{\mathrm{PPO}}(\theta)
=-\frac{\sum_t m_t\min\left[
\rho_t(\theta)\widetilde A_t,
\operatorname{clip}(\rho_t(\theta),1-\epsilon,1+\epsilon)\widetilde A_t
\right]}{\sum_t m_t}
$$

这里的 $\widetilde A_t$ 是本批提前算好的标准化 Advantage；$m_t$ 表示有效回答位置。**为了计算这个 Loss，首先需要新旧策略的概率比 $\rho_t$。** 本节用 $\rho_t$ 表示概率比，把 $r_t$ 留给后面的逐 Token 奖励。

$$
\rho_t(\theta)
=\frac{\pi_\theta(a_t\mid s_t)}{\pi_{\theta_{\mathrm{old}}}(a_t\mid s_t)}
=\frac{p_t^{\mathrm{new}}}{p_t^{\mathrm{old}}}
$$

分子、分母评价的是**同一个状态 $s_t$ 下、同一个已经采样出来的 Token $a_t$**：分子问“当前 Actor 给它多大概率”，分母问“采集本批 Rollout 时的旧 Actor 给它多大概率”。训练阶段固定这条回答，重新计算它的概率即可。

代码使用 log probability 来计算这个比值。由 $\log(x/y)=\log x-\log y$，得到：

$$
\boxed{
\rho_t(\theta)
=\exp\left(\log p_t^{\mathrm{new}}-\log p_t^{\mathrm{old}}\right),
\qquad
\log p_t^{\mathrm{old}}
\equiv\log\pi_{\theta_{\mathrm{old}}}(a_t\mid s_t)
}
$$

**这就是 $\log p_t^{\mathrm{old}}$ 的来历：它是 PPO Loss 中概率比分母的自然对数，记录旧 Actor 对该位置已选 Token 的评分。** 使用 logp 可以通过 `log_softmax` 直接取得这个值，并把概率相除写成“logp 相减，再取指数”。例如旧概率为 0.2、新概率为 0.3，则 $\exp[\log(0.3)-\log(0.2)]=1.5$。

因此，要在 Actor 更新后继续与**采集本批数据时的策略**比较，就需要提前保存旧 logp，并在本批多个 Mini-batch / Epoch 更新期间保持固定。如果每次都用更新后的 Actor 覆盖旧 logp，分母就不再代表本批 Rollout 的旧策略。代码对应：

```python
log_ratio = mb_resp_logp - old_resp_logp[inds]
ratio = torch.exp(log_ratio)
```

其中 `old_resp_logp` 来自 Rollout 保存的 `per_token_logps`，不需要梯度；`mb_resp_logp` 来自当前 Actor 的训练 Forward，需要保留梯度。下面沿着 Loss 所需的数据，继续区分哪些量可以提前计算。

**一、可以提前算好，并在本批 PPO 更新期间保持固定的量。**

旧 Actor 的 log probability、旧 Critic 的 Value：

$$
\log p_t^{\mathrm{old}}
=\log\pi_{\theta_{\mathrm{old}}}(a_t\mid s_t),
\qquad
v_t^{\mathrm{old}}=V_{\phi_{\mathrm{old}}}(s_t)
$$

完整回答的奖励及其对应的逐 Token 奖励：

$$
R^{\mathrm{seq}}=\operatorname{Reward}(\text{Prompt},\text{Response}),
\qquad
r_t=
\begin{cases}
0,&t<T-1\\
R^{\mathrm{seq}},&t=T-1
\end{cases}
$$

**回答已确定，旧 Actor、旧 Critic 和评分规则也已确定，因此旧 logp、旧 V 和奖励都能提前保存。**

GAE 展开为：

$$
\delta_t=r_t+\gamma v_{t+1}^{\mathrm{old}}-v_t^{\mathrm{old}}
$$

$$
\begin{aligned}
\hat A_t^{\mathrm{GAE}}
&=\delta_t+\gamma\lambda\delta_{t+1}
+(\gamma\lambda)^2\delta_{t+2}+\cdots\\
&=\sum_{l=0}^{T-t-1}(\gamma\lambda)^l
\left(r_{t+l}+\gamma v_{t+l+1}^{\mathrm{old}}-v_{t+l}^{\mathrm{old}}\right)
\end{aligned}
$$

这里的奖励 $r$、旧 Value $v^{\mathrm{old}}$、超参数 $\gamma,\lambda$ 都已知，**所以 TD Error 和整个 GAE Advantage 都能提前算好**。本节按终止状态 $v_T^{\mathrm{old}}=0$ 说明。

Critic 的固定回报目标为：

$$
\boxed{\hat R_t=\hat A_t^{\mathrm{GAE}}+v_t^{\mathrm{old}}}
$$

**因此，$\hat R_t$（returns）也能提前算好。** 本代码先计算这个目标，再把 GAE Advantage 标准化为 Actor 使用的 $\widetilde A_t$；标准化结果同样固定。有效回答掩码 $m_t$ 和冻结 Reference Policy 的 log probability 也可提前准备。

**二、每次训练 Forward 时，需要根据当前参数重新计算的量。**

当前 Actor 的新 log probability、当前 Critic 的新 Value：

$$
\log p_t^{\mathrm{new}}=\log\pi_\theta(a_t\mid s_t),
\qquad
v_t^{\mathrm{new}}=V_\phi(s_t)
$$

**旧 V 用来提前构造目标，新 V 是当前 Critic 要训练的预测，二者要区分。** 当前参数会变化，而且需要保留求导的计算图，所以新 logp、新 V 要重新计算。

随后计算概率比和 Actor 的 Clip Loss：

$$
\rho_t(\theta)
=\exp\left(
\underbrace{\log p_t^{\mathrm{new}}}_{\text{训练时重算}}
-\underbrace{\log p_t^{\mathrm{old}}}_{\text{提前保存}}
\right)
$$

$$
\ell_t^{\mathrm{clip}}
=-\min\left[
\rho_t(\theta)\underbrace{\widetilde A_t}_{\text{提前算好}},
\operatorname{clip}(\rho_t(\theta),1-\epsilon,1+\epsilon)\widetilde A_t
\right]
$$

Critic 用新 Value 拟合固定的回报目标；本代码还做 Value Clip：

$$
v_t^{\mathrm{clip}}
=v_t^{\mathrm{old}}
+\operatorname{clip}(v_t^{\mathrm{new}}-v_t^{\mathrm{old}},-\epsilon_V,\epsilon_V)
$$

$$
\ell_t^V
=\frac12\max\left[
\left(v_t^{\mathrm{new}}-\underbrace{\hat R_t}_{\text{提前算好}}\right)^2,
\left(v_t^{\mathrm{clip}}-\hat R_t\right)^2
\right]
$$

参考 KL 惩罚同样需要重算，因为其中包含当前 Actor 的新 logp：

$$
d_t=\underbrace{\log\pi_{\mathrm{ref}}(a_t\mid s_t)}_{\text{提前保存}}
-\log p_t^{\mathrm{new}},
\qquad
k_t=e^{d_t}-d_t-1
$$

**三、组合最终 Loss，再求梯度、更新参数。**

对当前 Mini-batch 的所有有效回答 Token 求平均：

$$
\boxed{
L_{\mathrm{total}}
=\frac{\sum_t m_t\left(\ell_t^{\mathrm{clip}}+\beta k_t+c_V\ell_t^V\right)}
{\sum_t m_t}
+L_{\mathrm{aux}}
}
$$

求和也覆盖 Mini-batch 中的所有 sample。Prompt 不作为动作目标，补齐位置的 $m_t=0$，都不计入平均分母。

用基本梯度下降表示：

$$
\theta\leftarrow\theta-\eta_\theta\nabla_\theta L_{\mathrm{total}},
\qquad
\phi\leftarrow\phi-\eta_\phi\nabla_\phi L_{\mathrm{total}}
$$

> **提前固定：旧 logp、奖励 R、旧 V、GAE Advantage、回报目标 returns、参考 logp 和掩码。训练时重算：新 logp、新 V，以及由它们组成的 Ratio、各项 Loss 和梯度。**

**四、节末汇总：可以提前算好的变量。**

下表的“固定”仅针对**同一批 Rollout 的 PPO 更新期间**；下一批 Rollout 要按新的轨迹和当时的模型重新准备。逐 Token 量按回答区域对齐，补齐位置由掩码排除。

| 提前准备的量 | 数学记号 | 本代码中的变量 / 来源 | 提前计算所需的信息 | 更新时的用途 |
|---|---|---|---|---|
| 固定的状态与动作序列 | $s_t,a_t$ | `gen_out`、`completion_ids`、`resp_labels` | Prompt 与本次已生成的 Response | 每次 Forward 都评价同一条旧轨迹 |
| 旧 Actor 的 log probability | $\log p_t^{\mathrm{old}}$ | `old_resp_logp`（来自 `per_token_logps`） | 旧 Actor、固定的状态与动作 | 作为 PPO Ratio 的固定分母；也用于新旧策略变化的诊断 |
| 序列级奖励 | $R^{\mathrm{seq}}$ | `rewards` | 完整 Prompt、Response 与评分规则 / 模型 | 构造逐 Token 奖励 |
| 逐 Token 奖励 | $r_t$ | `token_rewards` | 序列级奖励与末尾有效回答位置 | 计算 TD Error 和 GAE；本代码将序列奖励放在末尾有效 Token |
| 旧 Critic 的 Value | $v_t^{\mathrm{old}}$ | `old_resp_values` | 更新前的 Critic 与固定状态 | 构造 GAE、returns，并作为 Value Clip 的基准 |
| TD Error | $\delta_t$ | `delta`（GAE 循环中的中间量） | 逐 Token 奖励、旧 Value、$\gamma$ 与终止边界 | 递推 GAE；计算后无需单独缓存整张 TD Error 表 |
| 未标准化的 GAE Advantage | $\hat A_t^{\mathrm{GAE}}$ | `advantages`（标准化前） | TD Error、$\gamma,\lambda$ 与有效位置 | 先构造 returns，再用于优势标准化 |
| Critic 的回报目标 | $\hat R_t$ | `returns` | **未标准化**的 GAE Advantage + 旧 Value | 作为当前 Critic 拟合的固定目标 |
| 标准化后的 Advantage | $\widetilde A_t$ | `advantages`（标准化后） | 原始 GAE 与本批有效位置上的均值、方差 | 作为 Actor Clip Loss 的固定权重 |
| Reference Policy 的 log probability | $\log\pi_{\mathrm{ref}}(a_t\mid s_t)$ | `ref_resp_logp` | 冻结的参考模型与固定状态、动作 | 与新 logp 一起计算参考 KL 惩罚；参考模型与旧 Actor 各有用途 |
| 有效回答掩码 | $m_t$ | `resp_policy_mask`、`resp_value_mask` | 回答长度、首个 EOS 与补齐信息 | 排除无效位置，确定各项 Loss 求平均的分母 |

**边界再确认：新 logp、新 Value、Ratio、参考 KL 惩罚、Value Clip 和各项 Loss 都依赖当前参数，需要在训练 Forward 中重新计算。** 提前算好参考 logp，并不意味着参考 KL 惩罚也能固定；提前算好旧 Value 和 returns，也不意味着当前 Value Loss 能固定。

## 3. `rollout_engine.py` 在整个 PPO 训练中的位置

在 PPO 训练里，不能像 SFT 一样直接拿：

```text
Prompt + 标准答案
```

进行 Teacher Forcing。

PPO 必须先让**当前 Actor 自己真正生成回答**。

例如：

```text
Prompt：
浙江大学软件学院在哪里？

当前 Actor：
浙江大学软件学院位于宁波。
```

这一遍“当前 Policy 自己生成回答”的过程叫：

$$
\boxed{\text{Rollout}}
$$

但是 PPO 后面需要的不只是：

```text
"浙江大学软件学院位于宁波。"
```

这段文本。

还需要知道：

```text
1. Prompt 的 token 是什么；
2. Response 的 token 是什么；
3. Prompt + Response 的完整 token 序列是什么；
4. 每一个 Response token 当时在旧 Policy 下的 log probability；
5. Prompt 占多长；
6. Response 哪些位置是真实生成内容，哪些位置只是补齐。
```

所以整个关系可以先记成：

```text
train_ppo.py
    │
    │ 给出 Prompt IDs
    ▼
rollout_engine.py
    │
    ├─ 当前 Actor 真正生成 Response
    ├─ 切出 Response token
    ├─ 重新计算 Response 每个 token 的 old logp
    ├─ 解码 Response 文本
    ├─ 整理 prompt length
    └─ 整理 completion mask
    │
    ▼
RolloutResult
    │
    ▼
train_ppo.py
    │
    ├─ Reward
    ├─ Critic
    ├─ GAE
    ├─ PPO ratio
    ├─ PPO Clip
    └─ backward / optimizer.step()
```

所以这个文件最核心的任务可以浓缩成一句话：

$$
\boxed{
\text{把“当前 Policy 的一次真实生成”整理成 PPO 后面能直接训练的数据}
}
$$

## 4. 为什么 Rollout 不能只返回 Response 文本

假设 Actor 生成：

```text
A B C EOS
```

如果只是普通聊天系统，只需要最终文本：

```text
"A B C"
```

可能就够了。

但是 PPO 后面要计算：

$$
ratio_t
=
\frac{
\pi_{\text{new}}(a_t|s_t)
}{
\pi_{\text{old}}(a_t|s_t)
}
$$

所以必须知道 Rollout 当时：

```text
A 当时的 old logp
B 当时的 old logp
C 当时的 old logp
EOS 当时的 old logp
```

也就是说，Rollout 不仅是在“生成答案”。

它还在留下这一条旧 Policy 轨迹的历史记录。

可以把它理解成：

```text
回答内容
+
生成这份回答时旧 Policy 的证据
```

其中最关键的“证据”就是：

$$
\boxed{
\log\pi_{\text{old}}(a_t|s_t)
}
$$

<a id="origin-683"></a>
## 6. 为什么 Decoder-only 模型常用左 Padding？

假设有两个不同长度的 Prompt：

```text
Prompt 1：
[10, 11, 12, 13]

Prompt 2：
[21, 22]
```

为了组成一个 Batch，需要把它们补成相同长度。

---

<a id="origin-699"></a>
### 6.1 左 Padding

左 Padding 后：

```text
[10, 11, 12, 13]
[ 0,  0, 21, 22]
```

其中：

```text
0 = PAD
```

此时两个样本的**最后一个真实 Token 都在最右边**：

```text
样本 1：
10   11   12   13
                ↑
          最后一个真实 Token

样本 2：
PAD  PAD  21   22
                ↑
          最后一个真实 Token
```

这对于 Decoder-only 模型的自回归生成非常方便。

因为 Decoder-only 模型生成下一个 Token 时，本质上是：

```text
当前序列
↓
取最后一个有效位置的输出
↓
预测下一个 Token
```

所以左 Padding 可以让整个 Batch 中：

$$
\boxed{
\text{每个样本的最后一个真实 Token 都对齐在最右侧}
}
$$

---

<a id="origin-750"></a>
### 6.2 为什么这对 `generate()` 很方便？

假设模型输出：

```python
logits.shape = [B, T, V]
```

其中：

```text
B = Batch Size
T = Sequence Length
V = Vocabulary Size
```

生成下一个 Token 时，可以直观理解为主要使用：

```python
next_token_logits = logits[:, -1, :]
```

也就是：

> 取每个样本最后一个位置的 logits。

如果使用左 Padding：

```text
[10, 11, 12, 13]
[ 0,  0, 21, 22]
```

那么：

```text
sample 1 的最后位置 = 13
sample 2 的最后位置 = 22
```

两个位置都是真实 Token。

因此下一 Token 可以自然地接在：

```text
13
22
```

之后继续生成。

---

<a id="origin-803"></a>
### 6.3 如果使用右 Padding 会怎样？

如果改成右 Padding：

```text
[10, 11, 12, 13]
[21, 22,  0,  0]
```

那么：

```text
样本 1：
10   11   12   13
                ↑
          最后一个真实 Token

样本 2：
21   22   PAD  PAD
     ↑           ↑
最后真实 Token   最后一列
```

此时第二条样本的：

```python
logits[:, -1, :]
```

对应的是：

```text
PAD 位置
```

而不是：

```text
22 后面应该生成什么
```

因此生成逻辑就必须额外结合：

```text
attention_mask
最后一个非 PAD 位置
position_ids
```

来找到每条样本真正的生成起点。

实现会更麻烦。

---

<a id="origin-858"></a>
### 6.4 左 Padding 的核心好处

所以对于 Decoder-only 模型的批量自回归生成：

$$
\boxed{
\text{左 Padding 可以让所有 Prompt 的最后一个真实 Token 对齐到同一列}
}
$$

这样：

```text
不同长度 Prompt
        ↓
左侧补 PAD
        ↓
真实文本全部靠右
        ↓
每个样本最后一个真实 Token 都在最右侧
        ↓
方便统一预测下一个 Token
```

---

<a id="origin-884"></a>
### 6.5 对 `rollout_engine.py` 还有一个额外好处

假设 Padding 后 Prompt 的统一宽度是：

```text
P = 4
```

那么输入：

```text
[10,11,12,13]
[ 0, 0,21,22]
```

生成后可以统一组织成：

```text
[10,11,12,13 | 51,52,EOS]
[ 0, 0,21,22 | 61,62,EOS]
```

也就是：

```text
[padded Prompt | Completion]
```

于是代码可以直接：

```python
prompt_len = prompt_ids.size(1)

completion_ids = output_ids[:, prompt_len:]
```

因为：

```text
所有 Prompt 的 Padding 后宽度都是 4
```

所以都可以统一从第 4 个位置之后切出 Completion。

例如：

```text
output_ids：

[10,11,12,13,51,52,EOS]
```

执行：

```python
output_ids[:, 4:]
```

得到：

```text
[51,52,EOS]
```

因此左 Padding 也让整个 Batch 的：

```text
Prompt 区域
Completion 区域
```

边界更加整齐。

---

<a id="origin-959"></a>
### 6.6 右 Padding 完全不能用吗？

不是。

右 Padding 当然也可以使用。

例如在：

```text
SFT
Causal Language Modeling 训练
```

中，右 Padding 很常见。

因为训练时通常是一次性做 Teacher Forcing：

```text
token1 → token2
token2 → token3
token3 → token4
...
```

然后通过：

```text
attention_mask
labels = -100
```

把 PAD 位置排除掉即可。

但是在：

```text
自回归 generate
```

阶段，左 Padding 往往更加方便。

原因还是：

$$
\boxed{
\text{生成时最关心的是每个样本最后一个真实 Token 在哪里}
}
$$

左 Padding 可以天然保证：

```text
最后一个真实 Token
=
最右侧 Token
```

---

<a id="origin-1018"></a>
### 6.7 一句话总结

```text
左 Padding：

PAD PAD A B C
        ↑     ↑
     真实内容  最后真实 Token
```

它的核心优势就是：

> **让不同长度 Prompt 的真实内容统一向右对齐，使每条样本的最后一个真实 Token 都位于最右端，从而方便 Decoder-only 模型进行批量自回归生成。**

所以可以记成：

$$
\boxed{
\text{训练阶段右 PAD 很常见；生成阶段左 PAD 往往更方便。}
}
$$

## 10. 第三步：为什么生成完以后还要再跑一次模型

**先记住这两个阶段：第一次通过采样，得到“这次实际生成了什么轨迹”；第二次固定这条轨迹，计算“这些已经生成的 token，在原始 Policy 下各自的概率是多少”。**

**第一阶段：调用 `generate()`，逐 Token 采样，把轨迹生成出来。**

生成时，每一步都先计算下一个 Token 的 logits，再按生成配置处理概率并选择 Token。例如，配置了 temperature、top-k / top-p 时，过程可以理解成：

```text
当前 Prompt + 已生成前缀
↓
模型计算原始 logits
↓
temperature 调整、top-k / top-p 过滤（是否使用取决于配置）
↓
随机采样一个 Token
↓
把这个 Token 接到前缀后面，继续生成
```

**由于存在随机采样，在开始生成之前，并不知道这一次最终会走出哪条轨迹。** 即使 Prompt 和模型参数相同，两次采样也可能得到不同的回答；前面采到的 Token 不同，后面的上下文和生成结果也会跟着变化。

例如，这一次最终生成了：

```text
Prompt：[10, 11, 12, 13]
Response：[51, 52, EOS]
```

到了生成结束，实际走过的轨迹才完整确定下来。

**第二阶段：固定刚才的轨迹，再 Forward，计算它的逐 Token log probability。**

把已经确定的完整序列送进模型：

```text
[10, 11, 12, 13, 51, 52, EOS]
```

使用因果掩码，读取对应位置的原始 logits，经 `log_softmax` 后，用 `gather` 取出这次实际生成的 Token 的 log probability：

```text
log P_policy(51  | 10, 11, 12, 13)
log P_policy(52  | 10, 11, 12, 13, 51)
log P_policy(EOS | 10, 11, 12, 13, 51, 52)
```

**此时 Token 已经确定，第二阶段不再采样，而是对同一条轨迹计算概率。** 完整序列中的各个位置可以通过一次 Forward 并行计算；因果掩码保证每个位置仍然只使用它前面的上下文。

PPO 后面需要的是这些固定状态、动作上的：

$$
\log\pi_{\mathrm{old}}(a_t\mid s_t)
$$

这里的 old Policy 就是生成这批 Rollout 时的 Policy。当前实现会把原始模型算出的逐 Token log probability 保存下来，供后续 PPO Update 比较新旧 Policy 的概率。

**还要区分“原始模型概率”和“经过 temperature / top-p 等处理后的采样概率”：本文件第二阶段计算的是前者。** 生成过程中每一步本来就有 logits，也可以专门保存所需的原始 log probability；本实现选择在轨迹确定之后统一重新计算。

因此，这里的“第一次、第二次”指生成和概率评估两个阶段：`generate()` 内部通常要多次 Forward 才能逐步生成完整回答，之后才对固定序列再做一次 Forward。Rollout 中这两个阶段都在 `torch.no_grad()` 下执行，不更新模型参数。

> **第一次：采样出轨迹。第二次：轨迹固定后，求这条轨迹中每个已选 Token 的概率（代码保存的是 log probability）。**

## 12. 第五步：保存 Prompt Length

## 13. 第六步：构造 Completion Mask

**一定要看一个含 0 的例子：1 表示有效回答位置，0 表示补齐的占位位置。** 假设这一批有两条回答，长度不同，补齐到相同宽度 3：

```text
Completion A：51 EOS        → 补齐后：[51, EOS, PAD]
Completion B：61 62 EOS     → 补齐后：[61,  62, EOS]

如果按真实回答长度标记有效区域，completion_mask 应为：
[
    [1, 1, 0],   ← A 的最后一列是补齐位置
    [1, 1, 1]
]
```

**第一个 EOS 本身是有效动作，保留为 1；EOS 后面的补齐位置标为 0。** 张量虽然都是 `[2, 3]`，但实际有效回答 Token 总数是 $2+3=5$，不是 6。

**再对照本文件的实际实现：PyTorch Rollout 返回的 `completion_mask` 此时先全置为 1。** 即使存在上面的短回答，当前代码仍返回：

```text
rollout_result.completion_mask：
[
    [1, 1, 1],
    [1, 1, 1]
]
```

它先把切出的 Completion 区域都标为候选有效位置。随后 `train_ppo.py` 根据首个 EOS 的位置，再结合传入的 `completion_mask`，构造最终用于训练的掩码：

```text
resp_policy_mask = resp_value_mask：
[
    [1, 1, 0],   ← 首个 EOS 后的占位不参与对应的 PPO 策略损失、价值损失
    [1, 1, 1]
]
```

**因此要区分：上面含 0 的 `completion_mask` 展示的是按真实长度标记的含义；当前 PyTorch 路径先返回全 1，再由训练代码生成含 0 的最终训练掩码。** [两条 sample 的完整 Rollout：短回答补齐后，哪些位置变成 0？](/minimind/b20-01#origin-3749)给出两条 sample 的完整 Rollout 案例，并展示最终含 0 的训练掩码。

## 14. 最终输出：`RolloutResult`

一轮 Rollout 最后不是返回一个 Tensor，而是返回一个统一结果对象。

对于上面的例子：

```text
RolloutResult
│
├─ output_ids
│  [
│    [10,11,12,13,51,52,EOS],
│    [0,0,21,22,61,62,EOS]
│  ]
│
├─ completion_ids
│  [
│    [51,52,EOS],
│    [61,62,EOS]
│  ]
│
├─ per_token_logps
│  [
│    [-0.50,-0.20,-0.10],
│    [-0.80,-0.30,-0.40]
│  ]
│
├─ completions
│  ["2。", "..."]
│
├─ prompt_lens
│  [4,4]
│
└─ completion_mask
   [
     [1,1,1],
     [1,1,1]
   ]
```

这就是这个文件最核心的“输入 → 输出”。

## 15. 用形状再看一遍整个 Rollout

假设：

```text
B = batch size
P = padded prompt length
R = completion length
V = vocabulary size
```

最核心的形状变化：

```text
输入：

prompt_ids
[B, P]
```

```text
[B, R]
```

```text
[B, R, V]
```

```text

[B, R]
```

```text
prompt_lens
[B]

[B, R]

completions
List[str]
```

## 16. 如果一个 Prompt 要生成多个回答，会发生什么

假设输入：

```text
B = 2

P1
P2
```

并设置：

```text
num_generations = 3
```

那么在生成前先复制成：

```text
P1
P1
P1
P2
P2
P2
```

所以实际进入 `generate()` 的 batch size 变成：

$$
B'
=
B\times num\_generations
$$

也就是：

$$

$$

之后所有输出的第一维也都会变成 6。

```text

[6, P+R]

[6, R]

[6, R]
```

这个步骤的意义就是：

> 同一个 Prompt 可以真实采样多条不同 Response。

## 17. RolloutResult 交给 `train_ppo.py` 以后发生什么

`rollout_engine.py` 到这里基本完成任务。

后面的 PPO 训练不是这个文件的核心职责。

但是必须知道这些数据为什么有用。

例如 Rollout 保存：

$$
\log\pi_{\text{old}}(a_t|s_t)
$$

之后 Actor 经过 PPO 更新阶段重新 Forward，会得到：

$$
\log\pi_{\text{new}}(a_t|s_t)
$$

于是：

$$
\log ratio_t
=
\log\pi_{\text{new}}
-
\log\pi_{\text{old}}
$$

所以：

$$
ratio_t
=
e^{
\log\pi_{\text{new}}
-
\log\pi_{\text{old}}
}
$$

也就是：

$$
\boxed{
ratio_t
=
\frac{
\pi_{\text{new}}(a_t|s_t)
}{
\pi_{\text{old}}(a_t|s_t)
}
}
$$

所以 Rollout 时保存 old logp，正是为了后面 PPO Ratio。

<a id="origin-1595"></a>
## 18. 为什么 Rollout 时的 old logp 不需要梯度

Rollout 的目标是：

> 记录“当时旧 Policy 对这些已发生 Action 的概率”。

它是历史数据。

因此：

```text
Old logp
=
Rollout 时的快照
=
不需要通过它更新旧模型
```

所以 Rollout 可以在：

```python
torch.no_grad()
```

下面运行。

<a id="origin-1623"></a>
## 19. 为什么 PPO Update 时还必须重新 Forward

后来 PPO 真正更新的是“现在的 Actor”。

所以必须重新计算：

$$
\log\pi_{\text{new}}(a_t|s_t)
$$

而且这一遍必须和当前 Actor 参数连着计算图：

```text
Current Actor 参数
      ↓
Forward
      ↓
new logp
      ↓
PPO Loss
      ↓
backward
      ↓
参数更新
```

因此：

```text
old logp：
Rollout 阶段算
不需要梯度

new logp：
PPO Update 阶段重新算
必须有梯度
```

这也是为什么不能直接拿 Rollout 阶段的 old logp 做 backward。

## 22. 为什么用 `@dataclass`

**用了 `@dataclass`，声明好字段后，Python 就会自动生成接收这些字段并保存到对象上的 `__init__` 等方法。** 对这里的 `RolloutResult`，最直接的效果就是不用手写六次 `self.xxx = xxx`。

例如，源码这样写：

```python
from dataclasses import dataclass
from typing import List
from torch import Tensor

@dataclass
class RolloutResult:
    output_ids: Tensor
    completion_ids: Tensor
    per_token_logps: Tensor
    completions: List[str]
    prompt_lens: Tensor
    completion_mask: Tensor
```

**只看初始化和保存字段的效果，大致相当于手写下面这个普通类：**

```python
class RolloutResult:
    def __init__(
        self,
        output_ids,
        completion_ids,
        per_token_logps,
        completions,
        prompt_lens,
        completion_mask,
    ):
        self.output_ids = output_ids
        self.completion_ids = completion_ids
        self.per_token_logps = per_token_logps
        self.completions = completions
        self.prompt_lens = prompt_lens
        self.completion_mask = completion_mask
```

因此，`rollout()` 最后可以直接把已经算好的变量交给它：

```python
result = RolloutResult(
    output_ids=output_ids,
    completion_ids=completion_ids,
    per_token_logps=per_token_logps,
    completions=completions,
    prompt_lens=prompt_lens,
    completion_mask=completion_mask,
)

# 之后通过属性读取保存的结果
result.output_ids
result.per_token_logps
```

这里 `output_ids=output_ids` 左边是构造函数接收的字段名，右边是之前算好的变量；自动生成的初始化方法会执行 `self.output_ids = output_ids`。其余字段同理。本例没有给字段设置默认值，因此创建对象时需要提供全部六个字段。

`@dataclass` 默认还会生成 `__repr__`，方便打印对象时看到字段名和值；上面的普通类只展示了初始化部分的对应关系。字段上的 `Tensor`、`List[str]` 是类型标注，不会自动把传入的数据转换成对应类型，也不会自动完成 Rollout 计算。

> **这里的效果就是：把 Rollout 的六项结果装进一个对象，自动完成初始化，后续用 `result.字段名` 取出来。**

## 23. 工厂模式（Factory Pattern）：原理与代码示例

<a id="origin-1843"></a>
### 23.1 什么是工厂模式？

**工厂模式的核心思想：把“创建对象”的逻辑封装起来，调用者只告诉工厂自己需要什么，而不必关心对象如何创建。**

例如，一个大模型推理系统可能支持：

- HuggingFace
- vLLM
- SGLang

这些推理引擎实现不同，但上层代码希望通过统一的 `generate()` 接口使用它们。

<a id="origin-1855"></a>
### 23.2 不使用工厂模式

先定义三个引擎：

```python
class HFEngine:
    def generate(self, prompt):
        return "HF: " + prompt


class VLLMEngine:
    def generate(self, prompt):
        return "vLLM: " + prompt


class SGLangEngine:
    def generate(self, prompt):
        return "SGLang: " + prompt
```

调用者直接创建对象：

```python
engine = VLLMEngine()
print(engine.generate("你好"))
```

当不同位置都需要根据配置选择引擎时，可能到处出现：

```python
if engine_type == "hf":
    engine = HFEngine()
elif engine_type == "vllm":
    engine = VLLMEngine()
elif engine_type == "sglang":
    engine = SGLangEngine()
```

**问题：** 对象创建逻辑散落在各处。新增引擎时，可能要修改许多调用位置。

<a id="origin-1895"></a>
### 23.3 使用工厂模式

将对象创建逻辑集中到一个工厂中：

```python
class EngineFactory:
    @staticmethod
    def create(engine_type):
        if engine_type == "hf":
            return HFEngine()
        elif engine_type == "vllm":
            return VLLMEngine()
        elif engine_type == "sglang":
            return SGLangEngine()
        else:
            raise ValueError(f"不支持的引擎：{engine_type}")
```

使用时：

```python
engine = EngineFactory.create("vllm")
result = engine.generate("你好")
print(result)
```

流程：

```text
调用者
  |
  | EngineFactory.create("vllm")
  v
EngineFactory
  |
  | 根据 engine_type 判断
  +-------- HFEngine
  +-------- VLLMEngine  ← 本次选择
  +-------- SGLangEngine
  |
  v
返回引擎对象
  |
  v
engine.generate("你好")
```

调用者不需要写 `VLLMEngine()`，只需要指定类型。

<a id="origin-1944"></a>
### 23.4 工厂模式解决了什么问题？

| 不使用工厂模式 | 使用工厂模式 |
|---|---|
| 调用者自己判断、创建对象 | 工厂统一判断、创建对象 |
| 创建逻辑分散在多个地方 | 创建逻辑集中管理 |
| 切换实现可能要修改多处代码 | 通常修改配置即可切换 |
| 调用者依赖具体实现类 | 调用者可以只依赖统一接口 |

**注意：** 工厂模式并没有自动消除 `if/else`，而是把它们集中到一个位置；增加新引擎时，以上简单工厂仍需要修改创建逻辑。

<a id="origin-1955"></a>
### 23.5 为什么大模型系统常用工厂模式？

例如，Rollout Engine 有不同的推理后端：

```python
# 选择 SGLang
engine = EngineFactory.create("sglang")
responses = engine.generate("你好")

# 切换到 vLLM
engine = EngineFactory.create("vllm")
responses = engine.generate("你好")
```

这里是教学示意代码；实际 Rollout Engine 的 `generate()` 可能接收一批 Prompt、采样参数等，而非一个字符串。

只要各引擎遵守相同的调用接口，上层训练流程通常就无需依赖某个特定推理后端的创建细节。

两个概念要区分：

- **工厂模式**解决“由谁创建对象”。
- **多态／统一接口**解决“不同对象如何以相同方式使用”。

<a id="origin-1978"></a>
### 23.6 简单工厂与工厂方法的区别

上面的 `EngineFactory.create(type)` 属于常说的**简单工厂（Simple Factory）**。

严格来说，经典 GoF 设计模式中的**工厂方法（Factory Method）**会定义一个创建接口，再让不同子类决定具体创建哪一种对象。

例如：

```python
from abc import ABC, abstractmethod


class EngineCreator(ABC):
    @abstractmethod
    def create(self):
        pass


class VLLMCreator(EngineCreator):
    def create(self):
        return VLLMEngine()


class SGLangCreator(EngineCreator):
    def create(self):
        return SGLangEngine()


creator = VLLMCreator()
engine = creator.create()
print(engine.generate("你好"))
```

两者都把创建过程封装起来，只是扩展方式不同。

<a id="origin-2013"></a>
### 23.7 一句话总结

**工厂模式就是把 `对象 = 某个类()` 改成 `对象 = 工厂.create(类型)`（简单工厂写法），让对象的创建逻辑与使用逻辑分离。**

## 27. 为什么 Rollout 用 `torch.no_grad()`

Rollout 的任务是：

```text
生成数据
```

不是：

```text
在这里计算 PPO Loss 并反向传播
```

所以没有必要为生成过程保存完整 Autograd Graph。

使用：

```python
with torch.no_grad():
```

主要好处：

```text
减少显存占用
减少 Autograd 开销
```

注意：

> `no_grad()` 不等于模型不会 Forward。

模型照样会正常算 logits、正常生成。

只是：

> 不保存 backward 所需要的梯度图。

```text
  ↓

  ↓
model.module
  ↓
真正模型
```

所以这里的意思是：

> 如果外面有 DDP Wrapper，就先拿到内部真正模型。

这样后面调用模型自己的 Forward 参数，例如：

```python
logits_to_keep
```

更直接。

## 36. `input_ids.is_inference()` 为什么要 `detach().clone()`

代码：

```python
input_ids = (
    input_ids.detach().clone()
    if input_ids.is_inference()
    else input_ids
)
```

有些 Tensor 可能是在：

```python
torch.inference_mode()
```

里面创建的。

这种 Tensor 会带有：

```text
Inference Tensor
```

身份。

即使离开：

```python
with torch.inference_mode():
```

之后，这个 Tensor 本身也不会自动变回普通 Tensor。

---

<a id="origin-2593"></a>
### 36.1 什么叫“为了后面安全使用”

这里的“安全”不是：

```text
防止内存泄漏
防止程序被攻击
```

而是：

> 防止一个专门为推理优化的 Inference Tensor，后面进入普通 Autograd 场景时触发限制。

Inference Tensor 为了推理效率，不维护普通训练 Tensor 所需要的某些 Autograd / Version Tracking 信息。

即使 `input_ids` 自己是整数，不需要梯度，后续某些算子也可能需要把输入保存下来供 backward 使用。

例如 Embedding 前向：

```text
input_ids = [5,8,12]
↓
Embedding
↓
取 weight 的第 5、8、12 行
```

反向传播时需要知道：

```text
刚才到底用了第几行
```

因此某些 Autograd 路径可能需要保存这个输入。

Inference Tensor 在这类普通训练环境中可能受到限制。

所以这里重新得到一个普通 Tensor。

---

<a id="origin-2634"></a>
### 36.2 `detach()` 和 `clone()` 分别做什么

```python
detach()
```

表示：

> 不继承任何旧计算图关系。

而：

```python
clone()
```

表示：

> 重新复制一份独立 Tensor。

对于 `input_ids` 这种整数 Tensor：

```text
detach 更多是防御式处理

clone 才是重新物化独立普通 Tensor 的关键步骤
```

因此这一段可以理解成：

```text
如果 input_ids 是 Inference Tensor
        ↓
detach
        ↓
clone
        ↓
得到后续更适合作为普通 Tensor 使用的独立副本
```

## 38. 先理解 Decoder-only 的 next-token prediction 错位

完整序列：

```text
index:
0   1   2   3   4   5   6

token:
10  11  12  13  51  52  EOS
                └───────────┘
                 Completion
```

Transformer 在某个位置输出的 logits，预测的是：

> 下一个 Token。

所以：

```text
位置0 logits → 预测 token[1] = 11
位置1 logits → 预测 token[2] = 12
位置2 logits → 预测 token[3] = 13

位置3 logits → 预测 token[4] = 51
位置4 logits → 预测 token[5] = 52
位置5 logits → 预测 token[6] = EOS

位置6 logits → 预测 EOS 后面的下一个 token
```

我们需要 Completion：

```text
51
52
EOS
```

所以真正需要的是：

```text
logits[3]
logits[4]
logits[5]
```

<a id="origin-2742"></a>
## 39. 为什么先保留 `R+1` 个 logits

这里：

```text
R = n_keep = 3
```

如果只通过“保留最后若干 logits”的接口取数据，为了包含预测第一个 Completion token 的前一个位置，就要多取一个。

因此：

```python
logits_to_keep=n_keep+1
```

即：

```text
3 + 1 = 4
```

先取最后四个位置：

```text
logits[3]
logits[4]
logits[5]
logits[6]
```

然后：

```python
.logits[:, :-1, :]
```

把最后一个：

```text
logits[6]
```

去掉。

最后剩：

```text
logits[3]
logits[4]
logits[5]
```

正好对应：

```text
51
52
EOS
```

所以：

$$
\boxed{
n\_keep+1
}
$$

的根本原因就是：

$$
\boxed{
\text{Decoder-only 模型的 logits 与目标 Token 存在一个位置的 next-token shift}
}
$$

## 40. `[:, :-1, :]` 到底是什么意思

假设：

```text
logits.shape = [B, R+1, V]
```

代码：

```python
logits[:, :-1, :]
```

分三维看：

```text
第一维 `:`：
所有 batch

第二维 `:-1`：
从开头取到最后一个之前

第三维 `:`：
整个词表
```

所以：

$$
[B,R+1,V]
\rightarrow
[B,R,V]
$$

表示：

## 44. 回到 PPO：为什么 `log_softmax + gather`

**直接看一个小词表：`log_softmax` 给出每个位置对整个词表的 log probability；`gather` 按已经生成的 Token ID，每行取出一个对应的值。**

假设词表只有 4 个 Token，编号仅用于演示：

| Token ID（列下标） | Token |
|---:|---|
| 0 | 北京 |
| 1 | 杭州 |
| 2 | 浙江 |
| 3 | EOS |

这一次已经生成的 Response 是：

```python
ids_row = torch.tensor([2, 1, 3])  # 浙江、杭州、EOS
```

因此 $R=3$，词表大小 $V=4$。对这条固定轨迹重新 Forward，并完成 next-token 位置对齐后，假设得到以下 logits：

```python
import torch

logits_row = torch.tensor([
    [1.0, 2.0, 3.0, 0.0],  # 位置 0：根据 Prompt，评估第一个回答 Token
    [3.0, 1.0, 0.0, 2.0],  # 位置 1：根据 Prompt + 浙江，评估第二个 Token
    [0.0, 1.0, 2.0, 3.0],  # 位置 2：根据 Prompt + 浙江 + 杭州，评估第三个 Token
])  # [R, V] = [3, 4]

logps = logits_row.log_softmax(dim=-1)
```

`dim=-1` 表示每一行沿词表维计算。以第一行为例：

$$
\log P(\text{浙江}\mid\text{Prompt})
=3-\log(e^1+e^2+e^3+e^0)
\approx-0.4402
$$

**完整的 `log_softmax` 结果如下，所有数值均保留 4 位小数：**

| Response 位置（行） | token 0：北京 | token 1：杭州 | token 2：浙江 | token 3：EOS | 这一行实际生成的 ID |
|---|---:|---:|---:|---:|---:|
| 0：Prompt 之后 | −2.4402 | −1.4402 | **−0.4402** | −3.4402 | 2 |
| 1：浙江之后 | −0.4402 | **−2.4402** | −3.4402 | −1.4402 | 1 |
| 2：杭州之后 | −3.4402 | −2.4402 | −1.4402 | **−0.4402** | 3 |

现在需要按 `[2, 1, 3]` 取出表格中加粗的三个值。先把索引从 `[3]` 变成 `[3, 1]`：

```python
ids_row = torch.tensor([2, 1, 3])
index = ids_row.unsqueeze(1)

# index:
# tensor([[2],
#         [1],
#         [3]])
```

然后沿词表的列方向取值：

```python
selected = torch.gather(logps, dim=1, index=index)

# selected，形状 [R, 1] = [3, 1]：
# tensor([[-0.4402],
#         [-2.4402],
#         [-0.4402]])

per_token_logps = selected.squeeze(1)
# tensor([-0.4402, -2.4402, -0.4402])，形状 [R] = [3]
```

**`gather` 在这里具体做的就是：**

```text
第 0 行，按 index[0, 0] = 2，取 logps[0, 2] → -0.4402
第 1 行，按 index[1, 0] = 1，取 logps[1, 1] → -2.4402
第 2 行，按 index[2, 0] = 3，取 logps[2, 3] → -0.4402
```

特别看第 1 行：原始模型概率最高的是 token 0“北京”，但这条轨迹实际采到的是 token 1“杭州”，所以取的是“杭州”对应的 −2.4402。**`gather` 根据给定 ID 取值，不负责挑概率最大的 Token，也不负责重新采样。**

与源码对应起来，就是这一行：

```python
per_token_logps = torch.gather(
    logits_row.log_softmax(dim=-1),
    1,
    ids_row.unsqueeze(1),
).squeeze(1)
```

> **`log_softmax` 算出整张词表概率表的对数；`gather` 根据已经生成的 Token ID，每个位置只取它对应的那个 log probability。**

```text

↓
```

所以：

$$

## 57. 后面 PPO 为什么正好需要这些输出

假设 PPO 更新 Actor 后，对同样的旧轨迹重新 Forward：

```text

[-0.45,-0.18,-0.08]
```

第一个 Token：

```text
old logp = -0.50
new logp = -0.45
```

那么：

$$
log\_ratio
=
-0.45-(-0.50)
=
0.05
$$

所以：

$$
ratio
=
e^{0.05}
\approx1.051
$$

意思：

> 新 Policy 现在给这个旧 Action 的概率，比 Rollout 当时提高了约 5.1%。

这正是为什么 Rollout 必须保存 old logp。

### 57.1 两条 sample 的完整 Rollout：短回答补齐后，哪些位置变成 0？

**前面只有一条 sample，这里把一个 Batch 的两条 sample 从输入、RolloutResult 到最终含 0 的训练掩码完整列出来。** 每一行是一条 sample，每条 sample 都有自己的 Prompt、生成轨迹和逐 Token logp。

假设 `PAD=0`、`EOS=2`，本批有两个 Prompt，每个 Prompt 生成一个回答，即 `num_generations=1`。Token ID 和 logp 都是教学示例，文本也只是假想解码结果。

**输入：两条 Prompt，左补齐到宽度 $P=4$。**

```text
prompt_ids = [
    [10, 11, 12, 13],   ← sample 0：4 个真实 Prompt Token
    [ 0,  0, 21, 22],   ← sample 1：2 个真实 Prompt Token，左侧补了 2 个 PAD
]

attention_mask = [
    [1, 1, 1, 1],
    [0, 0, 1, 1],
]
```

**生成：sample 0 提前结束，sample 1 多生成一个 Token。**

```text
sample 0 实际回答：[51, EOS]       → 补齐后：[51,  2, 0]
sample 1 实际回答：[61, 62, EOS]   → 补齐后：[61, 62, 2]

                    Prompt 区域       Completion 区域
sample 0：       [10, 11, 12, 13 | 51,  2, 0]
sample 1：       [ 0,  0, 21, 22 | 61, 62, 2]
                                      ↑
                         sample 0 的最后一列只是 PAD
```

本批 $B=2$，回答统一宽度 $R=3$，所以 `output_ids` 形状为 `[2, 7]`，`completion_ids` 和逐 Token logp 的形状均为 `[2, 3]`。

**PyTorch 路径实际返回的 `RolloutResult`，六个字段完整写出来如下：**

```python
result = RolloutResult(
    output_ids=torch.tensor([
        [10, 11, 12, 13, 51,  2, 0],
        [ 0,  0, 21, 22, 61, 62, 2],
    ]),
    completion_ids=torch.tensor([
        [51,  2, 0],
        [61, 62, 2],
    ]),
    per_token_logps=torch.tensor([
        [-0.50, -0.10, -1.20],
        [-0.60, -0.30, -0.10],
    ]),
    completions=["回答 A", "回答 B"],
    prompt_lens=torch.tensor([4, 4]),
    completion_mask=torch.tensor([
        [1, 1, 1],  # 当前 PyTorch Rollout 原始返回值：暂时全 1
        [1, 1, 1],
    ]),
)
```

`prompt_lens=[4, 4]` 保存的是统一的 Prompt 宽度，所以两条回答都从 `output_ids` 的第 4 列开始切。sample 1 的真实 Prompt 长度虽然是 2，这里仍然记 4。

**然后一定要把“含 0 的有效位置”接着算出来。** 如果按真实回答长度标记 `completion_mask`，这一批的有效区域应当是：

```text
按真实长度标记的 completion_mask：
[
    [1, 1, 0],   ← sample 0：51、首个 EOS 有效，后面的 PAD 无效
    [1, 1, 1],   ← sample 1：61、62、首个 EOS 都有效
]
```

当前 PyTorch 路径通过训练代码完成这一步：读取上面原始返回的全 1 `completion_mask`，再根据首个 EOS 截断，得到：

```text
首个 EOS 的列下标 eos_pos = [1, 2]
有效回答长度 resp_lengths = [2, 3]    # 包含首个 EOS

resp_policy_mask = [
    [1., 1., 0.],
    [1., 1., 1.],
]

resp_value_mask = [
    [1., 1., 0.],
    [1., 1., 1.],
]
```

**训练代码新建了这两个掩码，并没有把 `result.completion_mask` 原地改成含 0 的版本。** 最终有效区域与上面“按真实长度标记的 completion_mask”一致。

把 Completion、old logp 和最终训练掩码放在一起看，就能看出每一列的用途：

| sample | 回答内位置 | Token | 示例 old logp | 最终训练 mask | 是否计入对应的策略、价值损失 |
|---|---:|---|---:|---:|---|
| 0 | 0 | 51 | −0.50 | 1 | 是 |
| 0 | 1 | EOS（2） | −0.10 | 1 | 是，结束回答也是一个动作 |
| 0 | 2 | PAD（0） | −1.20 | **0** | **否，只是补齐位置** |
| 1 | 0 | 61 | −0.60 | 1 | 是 |
| 1 | 1 | 62 | −0.30 | 1 | 是 |
| 1 | 2 | EOS（2） | −0.10 | 1 | 是 |

sample 0 的 PAD 位置即使被模型算出了一个 logp，也不代表这是实际采样出的有效动作；它会被最终的 0 掩码排除。对有效位置计算 PPO Ratio 时，仍然比较同一个 sample、同一个位置的已选 Token。例如 sample 0 的第一个 Token：

```text
old logp = -0.50
new logp = -0.45
ratio = exp(-0.45 - (-0.50)) ≈ 1.051
```

**这一批共有两条 sample、6 个矩形张量位置，但只有 5 个有效回答 Token。** 对本批有效 Token 求平均时，分母是最终 mask 的和 5；sample 0 的最后一列既不贡献对应的损失，也不增加分母。

> **一个 Batch 的 Rollout 可以保存多条轨迹：每条 sample 占一行，短回答通过补齐变成矩形张量；最终 mask 中的 0，明确告诉 PPO 哪些列只是占位。**

## 66. 最重要的三个“为什么”

<a id="origin-4111"></a>
### 66.1 为什么生成完还重新 Forward？

因为要拿：

$$
\log\pi_{\text{old}}(a_t|s_t)
$$

而且这里重新评估的是已生成 Token 在原始 Policy 下的 log probability。

---

<a id="origin-4123"></a>
### 66.2 为什么 `n_keep+1`？

因为 Decoder-only 是：

> 当前位置 logits 预测下一个 Token。

所以第一个 Completion token 的预测位置在它前面一位。

需要多保留一个位置，再去掉最后无关位置。

---

<a id="origin-4135"></a>
### 66.3 为什么 PPO Update 还要再次 Forward？

因为 Rollout 保存的是：

```text
old logp
历史值
无梯度
```

PPO 真正要更新当前 Actor，需要重新计算：

```text
new logp
带梯度
```

然后才能：

```text
new logp
-
old logp
↓
ratio
↓
PPO Loss
↓
backward
```

## 68. 一句话理解这个文件

`rollout_engine.py` 的本地 PyTorch 路径，本质上就是：

$$
\boxed{
\text{Prompt}
\rightarrow
\text{当前 Policy 真正生成 Response}
\rightarrow
\text{保存这条旧轨迹每个 Token 的 old logp}
\rightarrow
\text{整理成 RolloutResult}
}
$$

它最重要的输出不是单纯的 Response，而是：

$$
\boxed{
\text{Response Token}
+
\log\pi_{\text{old}}(a_t|s_t)
}
$$

因为下一阶段 PPO 会重新计算：

$$
\log\pi_{\text{new}}(a_t|s_t)
$$

再构造：

$$
\boxed{
ratio_t
=
\frac{
\pi_{\text{new}}(a_t|s_t)
}{
\pi_{\text{old}}(a_t|s_t)
}
}
$$

所以只要抓住：

```text
生成一条旧 Policy 轨迹
↓
把 old logp 留下来
↓
后面训练时重新算 new logp
```

就抓住了这个文件在 PPO 中存在的根本原因。
